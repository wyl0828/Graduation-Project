## 1. 文档目的与使用规则

本文回答系统做什么、谁能操作、业务边界是什么、如何验收，为原型、总体设计、数据库、API 和测试文档提供需求编号。本文不代替最终表结构、接口契约或完整测试用例。

文档权威口径：SRS 是当前业务需求、角色权限、未决事项和需求验收追踪的主要依据；其中只有经评审确认的条款构成已确认业务规则。总体设计基线据此落实架构与技术设计，不得自行覆盖或新增未经批准的业务规则；《需求基线冻结前置清单》跟踪待决事项、文档同步、专项设计门槛及验收证据，不替代 SRS，也不构成批准记录；原始毕设全案仅供背景和历史方案参考，与当前已确认需求冲突时不直接沿用。本轮明确要求优先于旧文档中的推进顺序。原始方案中的“终身自动登录”“五张表足够”“真实设备直接接入”等表述不作为本期需求承诺。本文不引用未经核实的政策统计或宣称已达到适老化法规认证。

需求来源分为 **继承**（基线已有）、**建议**（提出时待评审）、**已确认**（用户明确确认的业务决定）。继承不代表已通过正式需求评审；建议规则不能默认为用户已批准。历史评审记录中的“建议/待确认”须按第 9.23—9.26 节后续决定判断现行状态，不能反向覆盖已批准规则。Q01 确认范围见第 9.1 节，Q07 见第 9.5 节，Q02 见第 9.7 节，Q03/Q04 见第 9.10/9.12 节；业务批准不扩大为整个 SRS 已正式冻结或技术实现、验收通过。

优先级：**P0** 为身份、授权、核心业务闭环及安全一致性前置要求；**P1** 为本期必须交付但可后续迭代的功能；**P2** 为可选增强，不阻塞本期验收。P1 不等于不做。下表中每条验收条件均为未来测试目标，当前无通过记录。

## 2. 目标、角色与范围

系统面向居家老人、异地子女和社区工作人员，以社区服务闭环为主线，把健康记录、用药确认、主动求助和上门服务连接起来。成功标准是授权用户能够完成业务并追溯处理过程，而不只是页面可访问。

| 角色 | 使用入口 | 目标及数据范围 |
| --- | --- | --- |
| 老人 | Uni-app 小程序老人模式 | 本人健康信息、用药任务、SOS、服务进度和帮助 |
| 子女 | 同一小程序子女模式 | 有效绑定且授权范围内的老人健康、用药、预约与进度 |
| 网格员/护工 | Vue 3 Web 工作区 | 当前分配给自己的工单，以及执行服务必需的老人资料 |
| 社区管理员 | Vue 3 Web 管理区 | 所属社区档案、绑定管理、告警、调度、审核、统计与配置 |

系统维护人员属于运维身份，不新增第五类业务用户，不默认获得健康数据查看权限。账号与老人档案分离，允许先建档后关联老人账号。角色切换只改变当前工作入口，不能产生新权限。

**本期范围**：M01—M12；服务端确定来源的人工与仿真体征输入；站内通知和前台短轮询；本地受控文件存储；健康、用药、告警与工单统计；仅使用虚构或合成数据的隔离毕业设计演示环境。备份与恢复为该环境的待验收目标。

**不纳入本期**：真实硬件采购及设备数据接入、生产数据保留期限与生产级生命周期管理、临床诊断与自动处方、紧急救援到场时限保证、微服务和复杂消息中间件、服务计费与商城、库存管理、自动排班、医院挂号平台对接、服务评价体系。未来如用于真实社区业务，须另行批准生产数据保留期限、清理与匿名化流程、法律及运营责任边界，并完成设计和验证。服务计费、库存和自动排班已由 Q06 确认不纳入首期；医院挂号平台对接和服务评价体系暂不纳入，范围扩展另行评审；原始表中的 rating 字段不构成已确定功能。微信订阅消息、设备通道均为可选扩展，不能成为本期正常使用的唯一依赖。

**约束**：沿用 Uni-app + Vue 3、Vue 3 + Element Plus + ECharts、Spring Boot、MyBatis-Plus、MySQL 8.0 和单体分层架构。具体运行版本由开发与部署说明冻结。暂不制作高保真视觉稿，不以“必须恰好九页”限制必要表单、详情和工作入口。

SOS 初始紧急工单从 PENDING_DISPATCH 开始。健康告警本身不进入工单状态机，社区核查后由本社区管理员手动创建关联的普通服务工单；同一创建请求不能重复建单。健康告警和工单独立结案，互不自动关闭。普通改派只允许 PENDING_ACCEPT；ACCEPTED/PROCESSING 须记录责任交接并保留进度，不通过退回待派单抹除既有工作。SOS 工单未进入 PROCESSING 前可由本社区管理员以专门操作进入 VOIDED；PROCESSING 后不得快捷终止。CLOSED 是正常审核完成，CANCELLED 是符合规则的预约取消，VOIDED 是无效 SOS 管理终止，三者语义独立。REJECTED 属预约业务终态，不代表工单处理完成。预约取消及服务中止按 Q06 规则处理。未列动作仍须专项定义，不可互相套用终态。

确认后且尚未接单的预约只有经管理员审批通过方可取消；与确认、派单、接单并发时须以原子状态迁移决定唯一结果：取消先成功则后续接单拒绝，接单先成功则普通取消失效并转独立中止流程。由原申请人或当前承接人提出的服务中止申请由本社区管理员审核；中止保留原因、已完成内容、未完成事项、后续安排及申请/审核人员与时间。中止的具体状态名、合法迁移和失败反馈留专项设计。

未接单超时从每次成功派单进入 PENDING_ACCEPT 的服务端时刻计算；SOS 5 分钟、普通服务 30 分钟。超时通知管理员，不自动改派/结案，超时后仍可接单；重派重置该次期限。有效状态与当前分配须在超时处理时复核，具体提醒频率与实现转 M06 专项。

### 5.2 其他业务生命周期

- 亲情绑定业务阶段区分申请待核验、拒绝、有效授权、争议冻结、解绑/正式撤销；拒绝后可补充材料重新申请，批准可授予固定子女权限；冻结期间暂停该关系权限，核验后恢复或正式撤销；解绑与正式撤销后的重新建立条件待 E03。此处是业务语义，具体状态码、表结构与并发控制转专项设计；不得把冻结等同于撤销或自动解除争议。
- 用药任务区分未确认和已确认；已生成的当日任务在提醒前可由本人确认实际服用并标记“提前确认”，迟到则记录实际确认时间及迟到标识，二者均保留服务端实际确认时间。次日 00:00:00.000 起未确认任务进入 `OVER_WINDOW_UNCONFIRMED`，不是已漏服；具体秒级边界见 G-13/Q03-X02。计划修改/停用不取消或覆盖当日已生成任务；任务快照及已发生提醒/打卡历史保留。
- 健康告警独立维护“待处理、处理中、已结案”；仅本社区管理员可使待处理进入处理中或直接结案、处理中结案，结案结果按 G-19 填写；已结案不重开，无工单可独立核查结案，工单结案不自动关闭告警。正常体征不自动改变既有告警状态，见 G-17/Q04-X02；不用工单状态替代告警状态。
- 网络超时代表客户端不知道结果；SOS 重试必须使用原请求标识查询或重放既有结果。数据库已提交但响应丢失时，不得在前端直接判为从未提交。

## 6. 数据与外部接口需求

数据库专项文档至少覆盖：账号与角色、老人档案与绑定、体征与规则版本、告警与关联工单、用药计划与日期任务及打卡、预约信息、分配与处理历史、通知、文件元数据和审计。逻辑实体不要求一实体一表。

API 专项文档沿用 `/api/v1` 方向，逐项定义方法、路径、字段类型、必填/可空、时间格式、分页排序、成功/错误响应、数据权限、幂等范围与保留期限、并发版本、事务边界。区分认证失败、授权失败、参数错误、对象不可用、状态冲突和系统异常，但不得通过错误详情泄露无权对象内容。

本期无真实设备输入依赖；通知默认站内记录与前台短轮询，小程序后台/退出状态下不承诺准时弹窗。文件本地保存但不公开映射整个目录。平台登录、订阅消息和音频能力的真机约束需验证，不以代码静态检查代替平台测试。

### 9.23 2026-10-24 三批业务边界决策记录

本节记录项目负责人授权采纳建议后形成的业务决定，作为 G-01—G-13、G-18—G-20 的追踪依据。此处“已决策”只表示业务规则已明确，不表示实现、专项设计或验收通过。

**第一批｜亲情授权与老人身份激活（G-01—G-05）**

- **G-01 合法代理：** 接受可核验的法律监护/代理依据或老人有效书面授权；核验身份、授权范围、有效期与事项范围。亲属身份本身不等于代理权。核验不足时暂缓/拒绝，不默认批准；记录必要核验元数据，不默认保存证件照片。
- **G-02 授权争议：** 老人、关系中的子女或经核验的合法代理人可提出争议；工作人员可报告可信风险。具体争议、意愿冲突或疑似冒用可触发本社区管理员临时冻结，记录理由与依据；5 个工作日内复核，逾期继续冻结并记录原因，不自动恢复。恢复/撤销均需依据和审计。
- **G-03 重新建立关系：** 子女主动解绑后可重新申请，但须作为新申请重新核验；管理员正式撤销后，须证明原原因已处理并重新核验，方可新建关系。旧授权不自动复活。
- **G-04 老人无法操作：** 能表达意愿时尽可能直接向老人确认并记录；不能表达时，须核验合法监护/代理权限且范围覆盖该事项。仅有亲属身份、意愿不明、材料冲突或无法核验时暂缓/拒绝。
- **G-05 特殊激活码：** 默认当面向老人交付，必要时在老人本人在场时协助输入。特殊签发须核验老人身份与合法代理权限，记录原因、方式、操作者和结果；无法核验不签发。未使用的疑似泄露码立即作废重签；已使用则走账号恢复。工作人员不得代替老人完成身份关联。

**第二批｜档案、既有业务与紧急事件（G-06—G-11）**

- **G-06 档案恢复：** 本社区管理员按原因办理并审计；恢复后按当前账号、角色、绑定和计划状态校验。只恢复未来应生成的任务和常规提醒；不补造停用期间任务、不补发过期提醒。已生成的当日任务仅在截止前可正常确认；过窗后保持未确认状态。
- **G-07 紧急停档：** 本期不提供跳过未结工单结案/责任交接前置的紧急停档通道。紧急风险可按现有账号/关系安全流程限制访问，但必须另行完成有记录的责任交接，不得丢弃既有责任。
- **G-08 体征纠错/补录：** 停档后不允许补录此前采集但从未入库的体征。已存在记录的纠错可由本社区管理员走独立审计流程，填写原因并保留原值、新值、操作者和时间；原始证据不得被静默覆盖或删除。
- **G-09 计划接手：** 所有当前有效且未冻结的授权子女均可维护既有用药计划；原子女解绑后立即失去权限，其他有效子女可继续处理。修改/停用按次日生效规则，任务快照与历史不覆盖；并发冲突由服务端拒绝冲突写入并要求刷新。
- **G-10 档案字段/唯一性：** 核心字段为姓名、性别（允许未知/未说明）、出生日期（无法核实时可标未知并记录原因）、所属社区、居住地址、档案状态、系统档案编号。联系电话与紧急联系人信息按实际情况填写，缺失记录原因并提示管理员。身份证件号码可选，若采集则掩码展示、限制访问并用于重复识别；同一规范化号码不得重复建档。无证件号码时管理员核查候选重复项后才可建档；跨社区重复应核验/变更归属，不创建第二份档案。一个老人只保留一份业务档案，激活账号关联既有档案。
- **G-11 停档 SOS/告警：** 档案停用禁止一般新业务，但账号仍有效且老人身份已认证时，允许 SOS 作为唯一窄范围新业务例外并标记停档状态。账号停用/认证无效时明确拒绝并显示备用联系方式。已接受 SOS、既有健康告警及停档前已保存体征的异步评估继续处理；停档后不允许普通新业务或人工体征新增。

**第三批｜时间语义、告警权限与幂等（G-12/G-13/G-18—G-20）**

- **G-12 全系统时区：** 全系统业务日期与时间统一使用 `Asia/Shanghai`，包括计划/任务、截止、关怀通知、预约、超时、服务端日期归属与审计；服务端时间为权威，客户端时间仅辅助。此为本系统业务口径，不宣称外部系统天然使用同一时区。
- **G-13 服药截止：** 界面显示截止为当日 23:59，实际提交区间包含 23:59:59.999；次日 00:00:00.000 起拒绝普通打卡。仍未确认的任务进入“未确认、超过普通打卡窗口”（状态码 `OVER_WINDOW_UNCONFIRMED`），不得描述为漏服。截止后不开放普通补打，只允许独立历史纠错流程。
- **G-18 告警权限：** 仅本社区管理员可将健康告警置为处理中/已结案，也可直接结案。网格员/护工可按授权查看必要信息、提交核查事实，但不能直接改变告警状态或结案。无工单告警由本社区管理员核查后可独立结案，不要求额外二次审批。
- **G-19 结案结果：** 必须选择结果分类并填写事实摘要。分类为“已联系核查、暂不需新增服务”“已完成现场核查”“已创建普通服务工单”“未能完成核查、已安排后续跟进”“其他”。未能完成核查须填写原因与后续措施；其他须补充说明。结案只表示告警核查流程结束，不表示医疗问题已解决。
- **G-20 幂等冲突：** 相同幂等标识、相同规范化请求内容返回原结果；同标识不同内容拒绝并返回明确状态冲突（HTTP 409 Conflict），不覆盖原结果、不创建新业务对象，并记录最小必要审计信息。不同真实 SOS 使用新标识。
