# 第一部分：项目定位与范围

## 1. 项目基本信息

### 1.1 毕业设计题目

当前以原始方案基本信息中的题目为准：

**《基于 Spring Boot 与适老化设计的社区居家养老服务系统设计与实现》**

原始文档标题中曾出现"健康管理与服务系统"，后续开题报告、系统名称、论文题目和答辩材料应统一口径，最终以学校审批题目为准。

### 1.2 项目定位

系统面向社区居家养老场景，服务对象包括：

-   社区独居或空巢老人；
-   异地监护子女；
-   社区网格员或护工；
-   社区管理员。

系统不是单纯的健康数据展示平台，而是通过健康信息管理、异常事件处理和社区服务调度，把老人、子女和社区工作人员连接起来。

### 1.3 核心目标

1.  **健康信息可管理**：维护老人健康档案、体征记录和用药计划。
2.  **异常事件可处理**：根据配置规则对体征数据进行判断，并支持老人主动发起
    SOS。
3.  **社区服务可闭环**：完成派单、接单、上门处理、结果审核、结案和结果查询。
4.  **老人操作可理解**：通过适老化信息呈现、简化交互、明确提示和语音引导降低使用难度。

其中，**社区服务闭环是系统最重要的业务主线**；健康与用药模块提供数据和事件来源；适老化设计贯穿老人端。

### 2.1 明确不作为本期目标的事项

-   采购或部署真实智能手环等硬件；
-   接收真实设备体征及声称具备可信设备来源验证能力；
-   生产数据保留期限与生产级生命周期管理；本期仅为使用虚构/合成数据的隔离毕业设计演示环境；
-   实现医疗诊断或宣称临床准确性；
-   建设微服务架构；
-   引入 Kafka、RabbitMQ 等复杂消息中间件作为前置条件；
-   为追求页面数量而堆砌无业务价值的功能；
-   将尚未验证的未来硬件接入能力描述为已经实现。

### 2.2 仿真数据规则

仿真数据用于验证数据接入、规则判断、告警和工单业务链路。本期只接收人工登记和仿真数据，来源由服务端依据实际接收路径确定；普通客户端提交的 `DEVICE` 或类似标识不能形成可信设备记录。仿真数据不得伪装成真实设备采集或医疗诊断证据。按 S-01 停止仿真仅停止后续执行，不撤销已经被系统接受的样本；已接受样本继续正常校验、评估、告警及相关业务处理，已形成的业务记录不得因停止而回滚。未来设备接入须另行确定身份注册、接入认证、数据完整性和撤销机制，见 SRS BR-04/C-07。

小程序采用方案 A：**Uni-app + Vue 3**，该选择已确认。

## 4. 总体架构

采用单体分层架构，不采用微服务。所有核心业务由统一的 Spring Boot
后端处理，前端通过 RESTful API 通信。

### 4.1 客户端层

-   **老人端小程序**：健康信息、服药打卡、SOS、帮助与服务进度。
-   **子女端小程序**：健康监护、用药计划、服务预约、绑定管理。
-   **社区 Web
    端**：档案管理、告警处理、派单、工单审核、统计和仿真控制。

### 4.2 应用层

建议按以下职责分层：

-   Controller：接收请求、基础参数校验、调用应用服务；
-   Service：执行业务规则、事务处理、权限与状态转换；
-   Mapper：使用 MyBatis-Plus 访问数据库；
-   Scheduler：服药提醒、超时检查、仿真数据生成；
-   公共支撑：统一异常、文件处理、通知、权限检查、审计日志。

### 4.3 数据与基础设施层

-   MySQL：业务实体、状态、关联关系、通知记录和操作日志；
-   本地文件目录：处理照片等文件，数据库保存文件元数据；
-   定时任务：按计划生成提醒、检查超时或产生仿真数据；
-   规则处理：体征校验、告警判断和去重。

### 4.4 总体架构约束

1.  前端负责展示和收集操作，不负责最终授权判断。
2.  工单状态流转必须由后端控制。
3.  仿真和人工数据应尽量通过同一套业务处理链路。
4.  外部通知失败不能导致已合法接受的 SOS 业务被回滚。
5.  本期优先保证可运行、可演示、可测试，不引入不必要的基础设施。

## 6. 模块依赖关系

-   M01 为全部业务模块提供身份认证与权限检查。
-   M02 为健康、用药、告警和工单提供老人档案及授权关系。
-   M03 可产生健康异常事件，进入 M05。
-   M04 产生服药提醒和打卡记录，超时关怀可触发通知。
-   M05 对已合法接受的 SOS 原子创建告警与初始紧急工单；普通健康告警不自动建单，社区核查后由本社区管理员决定是否手动创建关联普通工单，M06 负责后续调度。
-   M07 创建普通服务预约，实际调度复用 M06。
-   M06 状态变化可通过 M11 通知授权用户，并为 M09 提供统计数据。
-   M10 产生带仿真标记的数据，用于验证 M03、M05、M06 的业务链路。
-   M12 为规则变更、关键业务操作提供审计与配置管理。

  角色              数据范围                                 主要权限                               禁止事项
  ----------------- ---------------------------------------- -------------------------------------- ----------------------------------------
  老人              本人档案、健康记录、用药计划、相关工单   查看、打卡、发起 SOS                   查看他人档案、修改审核结果

  子女              已绑定且授权范围内的老人                 查看健康信息、设置用药计划、预约服务   查看未绑定老人、代替社区审核结案

  网格员/护工       分配给自己的工单及必要的老人信息         接单、拒单、更新处理状态、提交结果     任意查看全社区健康档案、审核自己的工单

  社区管理员        所属社区业务数据                         建档、绑定管理、派单、审核、统计       越权访问其他社区数据

  系统维护人员      必要的系统配置和运行信息                 配置维护、故障排查                     默认获得全部健康数据的业务访问权限
  ------------------------------------------------------------------------------------------------------------------------------------------

## 8. 用户账号、老人档案与绑定关系

必须区分以下概念：

-   **用户账号**：可以登录系统的主体；
-   **老人档案**：被服务老人的业务资料；
-   **亲情绑定关系**：子女账号与老人档案之间的授权关系。

社区可以先为尚未注册账号的老人建档；老人之后可以绑定自己的使用身份；子女也可以在获得授权后建立亲情关联。

Q01 已确认：子女自行申请，管理员可协助发起并记录依据；管理员轻量核验亲属关系及老人授权意愿后批准，记录核验信息，不默认保存证件照片。老人身份激活与亲情授权分离，未激活老人也可先建立经核验的亲情关系；批准后子女即可访问 SRS 固定角色范围，无需等待激活，也不增加逐功能授权开关。重复申请去重，拒绝后可补充材料重新申请。老人无法明确表达意愿时默认不批准新绑定，待核验合法代理授权或其他充分依据后再决定。

子女可解除自己的绑定；老人登录后可解除指定子女，未激活或不能操作时申请社区核验。管理员撤销须限定适用情形并记录原因与审计；争议关系可临时冻结权限，核验后恢复或正式撤销，冻结不等于撤销。解绑立即撤销原子女访问权限，不自动取消预约、终止工单、停用用药计划或删除历史；有相应权限的主体继续处理，其他有效亲情关系不受影响。代理认定、争议程序、解绑后重建及代理办理例外已由 SRS G-01—G-05 明确业务边界，身份核验渠道、证据保护和并发仍待 M01/M02 专项设计。

## 9. 权限检查规则

涉及老人 ID、工单 ID、用药计划 ID
的请求，必须经过服务端数据权限检查。至少验证：

1.  当前账号已通过身份认证；
2.  目标业务对象存在，且对象状态允许当前操作；停用档案按现行授权允许历史查询及已合法交接工单的继续处理，不得笼统拒绝所有访问；

前端隐藏按钮不属于安全控制，不能替代后端校验。

换号须验证原、新手机号控制权；原号不可用转人工核验，不能仅凭新号接管旧账号；新号必须唯一，已被占用则拒绝，不自动合并账号。成功后保留原账号 ID、角色、老人档案关联、亲情关系与历史记录，授权不扩大；撤销全部旧会话并用新号重新登录。记录时间、操作主体与处理方式。按 FZ-02，成功后必须向已验证新号发送安全通知；原号仍可达时也通知，不可达时记录原因。通知不带老人业务详情；失败留结果，不回滚成功换号。该 M01 安全通知独立于 N-01 的业务通知矩阵；验证渠道、可达性、发送重试与失败恢复由 M01 专项设计。

### 9.3 Q07 多角色与运维边界（已确认）

多角色须由有权限的管理员明确分配：老人+子女允许，各自身份上下文与数据授权独立；网格员/护工+社区管理员按实际岗位需要有条件允许，禁止审核自己执行的工单并保留记录；家庭角色与工作人员角色首期使用不同账号；运维身份独立，不合并为业务角色。角色切换只改变入口，不能绕过审核分离、社区范围和亲情约束；角色撤销立即阻断对应权限，旧会话失效。

运维可部署、启停、排查技术故障，按职责管理测试环境和脱敏演示数据，查看必要运行状态与技术日志；日志避免密码、令牌及不必要健康信息。默认不能通过业务界面浏览或修改老人档案、亲情绑定、工单及用药计划，也不得借运维身份日常处理业务。重大故障需接触业务数据时，须明确授权、限定目的与范围并审计。

首期不建设复杂特权访问审批平台；部署专项必须区分应用业务权限和底层数据库、服务器权限，不以隐藏前端入口替代隔离，不宣称拥有底层权限的人在技术上绝对无法读取数据。技术隔离、审计实现、多角色校验及执行/审核分离测试转专项设计。

### 9.4 Q02 档案维护与状态联动（本轮已确认范围）

**档案维护（Q02-B、FZ-01）**：管理员维护身份、社区和档案状态字段；老人本人修改联系信息、地址和紧急联系人；当前有效未冻结的授权子女只能提交含字段、建议值和原因的更正申请，不能直接修改。本社区管理员核验后可批准并按核验内容办理该次更正，或填写原因拒绝；申请人按现行授权查询处理结果。未批准不改档，审批前须复核授权、字段约束及当前档案值，失权或现值冲突不能静默覆盖。申请、审批、修改前后值、人员和时间留痕；状态码、数据库/API 与并发机制留 M02 专项。

**档案停用（Q02-C）**：管理员按原因停用；禁止新业务，保留历史，当前账号有效且仍有权限的用户可以查询允许访问的历史。档案停用不等于删除老人账号。已有计划和工单不自动取消，已结工单、审核记录、照片和结果保留。

1. **用药计划与任务**：档案停用保留计划、已生成任务、打卡及通知历史，暂停生成新服药任务与新的常规提醒；恢复后不自动补造停用期间任务。未完成任务保留原状态，不自动标记已服药或已漏服；恢复后的未来任务、关怀通知及过窗打卡按 SRS Q02-EX01、G-06/G-13/G-14 已确认边界执行，具体调度与并发由 M04 专项设计；不能将系统停用解释为老人无需服药。

# 第四部分：核心业务流程

## 10. 流程 A：SOS 紧急求助

1.  老人在客户端长按 SOS 满 2 秒；
2.  服务端验证登录身份、请求参数和幂等标识；
3.  服务端在同一数据库事务内创建告警记录和关联紧急工单；
4.  社区后台展示待派单任务；
5.  管理员派单；
6.  网格员接单；拒单时填写原因并退回重新派单；
7.  网格员上门处理；
8.  普通上门服务网格员提交处理说明及至少一张有效证据照片；免照例外须说明原因并经管理员审核。SOS 不以先拍照作为紧急处置前置条件；
9.  管理员审核；不符合要求时退回补充；
10. 审核通过后结案，并向授权用户提供处理结果。

### SOS 规则

-   同一请求因网络重试不得重复创建工单。
-   不同的真实求助不能仅因时间接近就被无条件合并。
-   求助提交成功表示服务器已接受请求，不代表社区已接单或已到场。
-   SOS 失败时明确告知未确认成功，并提供重试和备用联系方式。
-   已接受的 SOS 不能通过普通预约取消接口直接删除。
-   告警与工单分别记录，通过关联关系连接。

## 11. 流程 B：健康数据与异常告警

1.  本期数据来自仿真或本社区管理员人工登记；未来设备接入另行设计；
2.  接入路径由服务端校验参数并确定来源，不信任普通客户端自报可信设备类型；
3.  保存体征记录；
4.  后端按配置规则判断是否触发告警；
5.  未触发告警时保留健康记录；
6.  触发告警时创建或更新告警事件；
7.  健康告警默认进入社区核查，不自动建单；核查后可手动创建普通服务工单；
8.  向授权用户展示告警及后续处理状态。

必须区分：

-   **体征记录**：某次测量或模拟得到的数据；
-   **告警事件**：满足某项预设规则、需要关注的事件；
-   **服务工单**：社区需要执行的处理任务。

不是每条体征记录都会触发告警，也不是每个告警都必须创建上门工单。告警阈值属于可配置业务规则，不应宣称系统具有医疗诊断能力。

### 11.1 Q04 技术校验与演示阈值

收缩压、舒张压分别记录，单位 mmHg；心率单位次/分钟。首期只接受整数：收缩压 50—300、舒张压 30—200、心率 20—250，均含上下限，且收缩压必须大于舒张压。采集时间不得晚于服务器当前时间，允许合法历史时间。非法数据返回字段校验错误，不保存正式体征、不生成健康告警。上述是软件技术接受范围，不是医学正常范围。

| 告警类别 | 已确认演示触发条件 |
| --- | --- |
| 血压偏高 | 收缩压 ≥160 mmHg，或舒张压 ≥100 mmHg |
| 血压偏低 | 收缩压 ≤90 mmHg，或舒张压 ≤60 mmHg |
| 心率偏高 | 心率 ≥120 次/分钟 |
| 心率偏低 | 心率 ≤50 次/分钟 |

六项比较阈值组成四类告警，等号触发；一次测量可触发不同类别并分别建事件，同类多个原因归并于同一事件并保留全部依据。这些条件仅用于首期软件演示及验收，不宣称医疗诊断能力。

### 11.2 Q04 版本、幂等、历史与失败恢复

规则变更仅影响其生效时间之后**新建的首次评估任务**；创建任务时按服务端接受时刻与版本生效时间固定规则版本，不自动重算或关闭历史告警；历史保留触发版本及原始证据。相同请求重试只留一条有效体征与对应评估结果，不同请求即使数值相同也独立保留。按 FZ-03，管理员明确选择历史或实时录入路径，服务端固定类别并分别保存采集时间与评估时间；历史体征可保存并评估，但不自动触发实时紧急通知或紧急上门工单。历史输入若首次建立健康告警，只沿 N-01 已批准的管理员站内事件供普通核查，不新增矩阵外事件；停档后未入库的历史数据不得借纠错补录。

体征被服务端接受并创建首次评估任务时，以服务端接受时刻和规则生效时间固定且保存规则版本；评估失败保留体征和失败状态，恢复重试沿固定版本保持幂等，不能改用重试时最新版本。历史体征按本次首次评估任务创建时生效的版本评估，采集时间另存；无法确定并保存版本时不得静默给出不确定结果。体征保存成功不等于告警评估成功。相同幂等标识且规范化请求内容一致时返回原结果；同标识不同内容拒绝并返回状态冲突（HTTP 409 Conflict），不覆盖原结果、不创建新业务对象，并记录最小必要审计信息。版本选择与任务创建的原子性、失败恢复留 M03/M12 专项；历史/实时的受控路径、不可变类别和副作用在接入契约中落实，不自行添加时间阈值。

### 11.3 Q04 合并、生命周期与手动建单

仅同一老人、同一告警类别、同一规则版本，且目标仍处活动状态时参与合并。以首次触发告警的体征采集时间为固定锚点，采集时间绝对差≤30 分钟允许合并；窗口不滚动延长，新记录不重置锚点。不同类别分别成事件；SOS 不参加健康告警合并。迟到体征命中多个合格目标时，依次选锚点距离最近、创建时间较早、不可变告警 ID 升序的唯一目标；无合格目标按既有规则新建，处理乱序不得改变选择结果。并发选择机制留 M03/M05 专项。

告警独立维护待处理、处理中、已结案状态；待处理可开始处理或直接结案，处理中可结案，结案必须留处置结果；已结案不重新打开，不参与活动合并，后续异常按新事件规则处理。无工单告警也可独立核查结案；工单结案不自动关闭关联告警。

健康告警默认社区核查，核查后由本社区管理员手动创建关联普通服务工单，同一创建请求不得重复建单；自动转单须另行批准明确规则。告警、工单分别维护状态、处理和结案结果。后续正常体征独立保存，不自动改变或关闭已有告警；管理员可将其作为核查事实，不能仅凭一次正常测量宣称先前风险消除。仅本社区管理员可改变告警状态或结案；网格员/护工只能按授权提交核查事实。无工单告警可由本社区管理员独立结案，不要求额外二次审批。结案须选择结果分类并填写事实摘要；“未能完成核查”须填写原因与后续措施，“其他”须补充说明。G-16/G-17/G-21 的业务规则已确认；建单幂等、状态并发、版本持久化和审计转专项。

## 12. 流程 C：服药计划与打卡

1.  仅当前有效且关系未冻结的授权子女设置用药计划；本期管理员不得代设或修改、停用、重启；
2.  系统按计划生成对应日期的服药任务，并保证当日任务在其原定提醒时刻前可供本人确认；具体预生成时机和调度机制由 M04 专项确定；
3.  定时任务检查提醒时间；
4.  系统向老人端提供提醒；
5.  老人确认实际服用后保存独立打卡记录；对已生成的当日任务允许在提醒前明确提前确认；
6.  未打卡时检查超时规则；
7.  达到关怀提醒条件后创建通知并提醒子女；
8.  保存计划、任务、打卡和通知之间的关联关系。

### 用药规则

-   一份计划可以持续多天，每天的执行情况必须独立记录。
-   修改计划不得随意覆盖历史打卡记录。
-   超时未打卡只表示系统尚未收到确认，不代表已确认漏服。
-   重复提交打卡不能产生多条有效记录。
-   订阅消息取决于平台授权和业务条件，不能作为唯一提醒保障。

### 12.1 Q03 计划生效与日期任务

每天一个或多个固定提醒时刻，首期不支持复杂周期表达式。新建默认次日生效，可指定更晚日期；修改、停用、重新启用均次日生效。修改/停用不覆盖当日已生成任务，其原计划快照、提醒、打卡和历史继续保留；停用次日起不生成新任务，重启不补造停用期间任务。

当日任务必须在原定提醒时刻前生成并可供老人确认，不能只在提醒时刻才创建。M04 专项须确定具体预生成时机、调度与失败恢复，不能留给实现阶段自行猜测。老人仅可对本人已生成的当日任务，在明确确认已经实际服用后于提醒前提前打卡；不得为关闭提醒而预先确认，也不得确认未来日期任务。保存服务端实际确认时间并标记“提前确认”，不以计划提醒时刻代替实际时间，不改变原提醒、任务快照及后续计划。重复/并发提交只保留一条有效打卡；系统记录的是本人确认，并非已经验证实际服药。

所有业务时间统一采用 `Asia/Shanghai`。老人可对本人当日任务迟到确认，界面截止显示当日 23:59，实际提交区间包含 23:59:59.999；次日 00:00:00.000 起拒绝普通打卡。仍未确认任务进入“未确认、超过普通打卡窗口”（状态码 `OVER_WINDOW_UNCONFIRMED`），不得推断漏服。首期不允许普通历史补打，历史纠错走独立审计流程。

### 12.2 Q03 关怀通知与停机恢复

原定提醒时刻后 45 分钟仍未确认，触发一次关怀通知；发送给所有当前有效、账号可用且关系未冻结的亲情绑定子女。同任务同阶段只创建一个逻辑通知，逐收件人结果与重试另行设计，不重复制造通知。无有效收件人记录“无有效收件人”，并提示管理员工作台，不自动发送私人消息。

正常运行时，即使 45 分钟阈值跨入次日也按规则通知一次。系统停机恢复自动补建所有缺失任务，使用对应日期实际生效的计划版本，不能用最新版本覆盖历史，已有任务不重复，补建不等于打卡也不开放历史补打。恢复仅对当前日期任务重新判断关怀条件，过去日期不自动补发。

系统停机补建不同于计划/档案停用：补建只覆盖按历史有效计划及业务状态应有而缺失的任务，停用期间不应生成的任务不补造。档案停用后的常规提醒暂停及恢复边界仍按 Q02；计划重启的次日生效不自动确认档案业务恢复。按 G-14/G-15，无收件人时记录原结果并提示管理员，新绑定不补发旧通知；每次实际发送或重试前复核账号、关系和冻结状态，失权者跳过并逐人留痕，后来恢复授权亦不补发旧通知。逐收件人状态及失败恢复留 M04/M11 专项。

Q03 四项一致性检查通过仅指业务逻辑评审。版本管理、唯一约束、补建中断恢复、并发打卡、通知授权复核和失败重试均转专项设计；具体用例按 SRS AT-21—23 展开，不代表已运行验证。

## 13. 流程 D：助老服务预约

1.  子女为有效授权老人选择当前启用的助餐、助医或助洁服务，填写期望时间、地址和备注；
2.  后端校验绑定关系、服务项状态、至少提前 2 小时且不超过 7 天、上午 09:00–12:00 或下午 14:00–17:00 的时间范围，以及相同老人/服务/日期/时段是否已有有效预约；
3.  同一请求按幂等规则处理，只创建一次。成功申请生成待确认预约；申请时间只是期望时段，不表示资源已锁定或服务已承诺；
4.  社区管理员确认后进入派单；拒绝待确认预约须填写原因并通知申请人，记录为 `REJECTED`；
5.  待确认预约仅原申请人可取消。确认后尚未接单的取消由原申请人申请、管理员审批；通过后阻止派单/接单，拒绝则保留有效预约并记录原因、通知申请人。管理员主动取消也留原因与审计。已接单或正在执行的服务由原申请人或当前承接人提出独立中止申请、管理员审核，不能使用普通预约取消；
6.  每个有效预约只进入一条服务执行流程，网格员接单并执行服务；
7.  网格员提交处理结果，管理员审核并结案；子女按当前授权查看进度和结果。

管理员可启停服务目录项；停用只阻止新申请。待确认预约仍可按原规则确认或拒绝，已确认、待派、待接单、已接单及执行中业务保留、可查并继续按合法路径处理；确实无法继续时走取消审批或独立中止，不直接删改历史。`PENDING_CONFIRMATION`、已确认及关联执行未终结属于有效业务；`REJECTED`/`CANCELLED` 不再阻止符合条件的新申请，正常完成或审核中止的旧预约不能再次生成执行流程。预约与工单终态分开建模，物理实体留专项。本期不建设服务计费、库存或自动排班。SOS 被服务端接受后不能通过普通预约取消流程删除；无效求助保留原始记录并按专门管理流程处理。

# 第五部分：工单状态机

## 14. 工单与预约状态

下表中，`REJECTED` 与 `CANCELLED` 表示预约业务终态，`VOIDED` 表示无效 SOS 紧急工单终态；服务中止是独立结果，不能伪装成这些终态或正常完成的 `CLOSED`。预约与工单的状态实体及中止状态码留专项设计，不得把终态混为同一业务含义。

| 新增状态 | 业务含义 | 规则 |
| --- | --- | --- |
| `REJECTED` | 管理员拒绝待确认预约 | 原因为必填，并通知申请人；与用户取消 `CANCELLED` 区分。确认后取消请求由管理员审批。 |
| `VOIDED` | 管理员终止无效 SOS 紧急工单 | 本社区管理员专门操作；只允许进入 `PROCESSING` 前；记录原因、操作者、时间与依据，保留原 SOS；处理开始后须核实并走正常审核。 |

  状态码                    含义                     主要操作方
  ------------------------- ------------------------ ------------
  `PENDING_CONFIRMATION`    预约待社区确认           管理员
  `PENDING_DISPATCH`        等待派单                 管理员
  `PENDING_ACCEPT`          已派给网格员，等待接单   网格员
  `ACCEPTED`                已接单                   网格员
  `PROCESSING`              正在处理                 网格员
  `PENDING_RESULT_REVIEW`   处理结果待审核           管理员
  `RETURNED`                审核退回，需要补充       网格员
  `CLOSED`                  审核通过并结案           管理员确认
  `CANCELLED`               符合规则的预约取消       原申请人（待确认）/管理员（审批后）

SOS 初始紧急工单进入 `PENDING_DISPATCH`。健康告警本身不进入工单状态机，也不自动建单。按已确认的 Q05-06，社区核查后由本社区管理员手动创建关联的普通服务工单，沿用待派单方向；同一创建请求不得重复建单。告警状态操作权限与结案结果字段已按 SRS G-18/G-19 明确：仅本社区管理员可改变告警状态或结案，结案结果分类与事实摘要必填；技术权限校验和审计仍待专项设计。

## 15. 状态流转规则

-   `PENDING_CONFIRMATION` → `PENDING_DISPATCH`；
-   `PENDING_CONFIRMATION` → `REJECTED`（管理员拒绝，原因必填并通知申请人）；
-   `PENDING_DISPATCH` → `PENDING_ACCEPT`；
-   `PENDING_ACCEPT` → `ACCEPTED`；
-   `PENDING_ACCEPT` → `PENDING_ACCEPT`（管理员改派，保留分配历史并为新承接人重新计时）；
-   `PENDING_ACCEPT` → `PENDING_DISPATCH`（拒单并记录原因）；
-   `ACCEPTED` → `PROCESSING`；
-   `PROCESSING` → `PENDING_RESULT_REVIEW`；
-   `PENDING_RESULT_REVIEW` → `CLOSED`（审核通过）；
-   `PENDING_RESULT_REVIEW` → `RETURNED`（审核退回）；
-   `RETURNED` → `PROCESSING`（补充处理）；
-   `PENDING_CONFIRMATION` → `CANCELLED`（仅原申请人可取消）；
-   已确认且尚未接单 → `CANCELLED`（原申请人申请、管理员审批通过；管理员主动取消亦须原因与审计；批准后阻止后续派单/接单）；
-   SOS 工单尚未进入 `PROCESSING` 时 → `VOIDED`（本社区管理员专门管理终止，原因、操作者、时间和依据必填）。

确认后取消审批拒绝时预约保持有效，记录拒绝原因并通知申请人。已接单或正在执行的服务禁止普通预约取消，由原申请人或当前承接人申请独立中止、本社区管理员审核；记录中止原因、已完成内容、未完成事项、后续安排、申请人与审核人及时间。取消与接单并发只可有一个合法结果：取消先成功则拒绝后续接单，接单先成功则转中止流程。具体中止状态名、合法迁移、原子更新和冲突反馈留 M06/M07 专项设计。拒绝、取消、中止和 SOS VOIDED 不能互相套用或静默覆盖历史。

Q05 已确认的额外流转规则：管理员可在 `PENDING_ACCEPT` 阶段改派，保留原分配并为新承接人重新计时；`ACCEPTED` 或 `PROCESSING` 阶段不能通过普通改派丢弃进度，须有记录的责任交接。责任交接的状态保持、接交人确认和审计字段由 M06 专项设计落实。

每次派单成功进入 `PENDING_ACCEPT` 时记录服务端起算时间：SOS 5 分钟、普通服务 30 分钟。超时提醒管理员，不自动改派/结案，超时后仍可接单；改派重置该次期限。接单时限不代表到场时限或救援承诺。

工作人员账号停用立即失去业务访问权限，不能因仍持有工单而继续处理；未结责任依记录流程交接。该业务决定闭环 SRS 的 Q02-EX05，具体调度实现留 M06。

普通上门服务默认至少一张有效处理照片。免照须填写原因与说明，经管理员审核批准后才可结案；SOS 不以拍照为紧急处置前置条件。Q08 已确认仅 JPEG/PNG、单张不超过 5 MB、每次处理结果最多 5 张；证据保留与访问规则见第 27 节。

健康告警默认社区核查，随后由本社区管理员手动创建关联的普通服务工单，同一请求不得重复建单。告警与工单的状态、处理记录及结案结果相互独立，不自动互相关闭。告警权限与结案字段已由 G-18/G-19 明确；多目标选择、正常体征影响及首次版本固定点已由 G-16/G-17/G-21 明确业务规则，原子性与失败恢复仍待专项设计。

Q05-01—07 已确认；责任交接、超时提醒的技术调度、状态实体映射、事务/并发及照片文件约束在 M06/M07/M11 专项落实。Q06 确认后取消审批及服务中止的技术状态、并发和验收细节转 M06/M07；预约时间统一使用 `Asia/Shanghai`，与 SRS BR-11 及 G-12 一致。Q08 的文件和备份恢复参数已确认，执行及验证要求见第 27 节。

### 15.1 状态主体与终态不可混用（本轮对齐说明）

- **健康告警**采用独立的“待处理/处理中/已结案”生命周期；是否关联普通服务工单不改变其状态主体。
- **SOS** 为主动求助事实；被接受后关联告警和初始紧急工单，不能因工单被管理终止就删除原求助。
- **预约**独立拥有待确认、拒绝、取消和确认后的后续执行关联；`REJECTED`、`CANCELLED` 是预约语义，不能当作所有工单的通用终态。
- **工单**包含派单、待接单、接单、处理、送审/退回、审核结案；`VOIDED` 仅用于规定条件下的无效 SOS 紧急工单管理终止；服务中止有独立业务事实与审批，不能替代 `CLOSED`、`REJECTED`、`CANCELLED` 或 `VOIDED`。
- 一次已确认预约最多进入一条执行流程；取消审批与接单竞争只有一个合法提交结果。具体存储实体、状态码和迁移细节仍由 E-04/E-05 专项确定，不能以本节越过模块详细设计门槛。

## 16. 状态控制约束

1.  所有状态转换由后端执行。
2.  状态转换前校验当前状态、操作角色、数据权限和必要字段。
3.  拒单与退回必须记录原因。
4.  已结案工单不得通过普通接口直接重新打开或覆盖。
5.  重要状态变化写入工单操作记录。
6.  不同来源工单的取消规则不同，不允许无条件取消所有类型的工单。
7.  工单结案只表示社区处理流程结束，不代表医疗问题已解决。
8.  按 BR-10，同一业务对象的冲突状态迁移、唯一性检查和写入只能提交一个合法结果；失败方得到状态冲突或符合幂等规则的原结果，不覆盖成功方。状态、必要审计和业务副作用须一致；各接口具体错误反馈与技术机制在模块专项明确。

  系统管理   配置、审计日志、仿真配置       规则、关键操作和仿真参数

以上是逻辑实体清单，不等于最终数据库表必须与实体一一对应。最终表结构在逐模块详细设计时确定。

**SRS 决策要求补充识别的逻辑事实（不是新增物理表承诺）：** 档案更正申请及批准/拒绝/字段前后值证据（FZ-01）；账号会话撤销和手机号变更安全通知处理结果（FZ-02）；人工体征历史/实时录入类别、首次评估版本与失败状态（FZ-03/G-21）；幂等请求标识及同键异内容审计（BR-07/10）；亲情争议冻结、责任交接、预约取消审批与独立中止记录（G-02/Q05/G-23）；通知事件与逐收件人结果（N-01/G-14/G-15）；仿真停止和执行结果（S-01）；文件版本与联动恢复依据（Q08/G-24）。这些事实必须在后续对应模块的逻辑/物理设计与测试中有可追溯的持久化载体，具体表数和字段结构此阶段不冻结。

## 18. 核心实体关系

-   一个老人档案可对应多条体征记录；
-   一个老人档案可拥有多份用药计划；
-   一份用药计划可生成多个日期的服药任务；
-   每个服药任务最多对应一条有效打卡记录；
-   一个老人可产生多条告警事件；
-   一个告警可以没有工单，也可能关联多个后续处理任务；
-   一个工单包含多条状态操作记录；
-   一个用户可通过多条绑定记录关联多个老人，前提是授权有效；
-   文件可以关联工单或处理记录，文件元数据与实际存储分开管理。

## 19. 数据设计统一规则

-   业务表采用统一的主键、创建时间和必要的更新时间字段。
-   体征记录保存来源类型、采集时间及必要的数据质量状态。
-   服药任务具有可唯一识别的执行实例，防止重复生成与重复打卡。
-   工单状态变化单独记录，不只覆盖当前状态。
-   文件元数据与实际文件分开存储。
-   账号、绑定、工单关联等字段按查询需求建立索引。
-   账号停用、绑定解除或档案状态变化不得导致重要历史记录被随意删除。
-   对关键业务事实设置必要的唯一约束和事务保护。

后续重点评估以下候选表：

-   `sys_user`
-   `sys_role`
-   `sys_user_role`

这是候选清单，不能直接视为最终建表结果。需要逐模块确定字段、外键、索引、唯一约束和保留策略后再冻结。

# 第七部分：API 与后端规范

## 21. API 分组

统一使用 `/api/v1` 前缀。

  分组       建议路径                        用途
  ---------- ------------------------------- ------------------------
  身份认证   `/api/v1/auth`                  登录、退出、身份信息
  老人档案   `/api/v1/elders`                建档、查询、修改
  亲情绑定   `/api/v1/family-bindings`       绑定、解除、授权检查
  健康记录   `/api/v1/vitals`                体征查询与上报
  用药计划   `/api/v1/medication-plans`      计划管理、任务查询
  服药打卡   `/api/v1/medication-checkins`   打卡和历史查询
  告警       `/api/v1/alerts`                告警查询与处理
  SOS        `/api/v1/sos-alerts`            主动求助创建
  工单       `/api/v1/service-orders`        派单、接单、处理、审核
  通知       `/api/v1/notifications`         通知查询与确认
  仿真控制   `/api/v1/simulator`             仿真启停和场景触发
  社区统计   `/api/v1/dashboard`             社区统计数据

路径为总体设计建议，具体方法、请求字段、响应字段和错误码在模块详细设计阶段确认。

## 22. 关键接口方向

### 22.1 首页聚合查询

`GET /api/v1/elder/home-summary`

建议返回：

-   `elderId`
-   `displayName`
-   `serverTime`
-   `activeAlerts`
-   `medicationTasks`
-   `latestVitals`
-   `latestServiceOrder`
-   `dataSource`

接口按当前登录身份与数据权限查询。没有记录时返回明确空状态，不构造默认健康值。

### 22.2 服药打卡

`POST /api/v1/medication-checkins`

候选请求字段：

-   `planId`
-   `occurrenceId`
-   `clientRequestId`

服务端记录实际确认时间、操作人和关联计划。重复请求应返回可识别的既有结果，不能创建第二条有效记录。**候选字段并非完整 API 契约**：M-01 已批准的提醒前提前确认必须在请求及交互中取得老人“已经实际服用”的明确声明；未来日期任务、过窗普通打卡应拒绝。实际字段、校验和错误反馈进入 M04 API 专项，不在本稿擅自定名。

### 22.3 SOS 求助

`POST /api/v1/sos-alerts`

候选请求字段：

-   `triggerSource`
-   `clientRequestId`
-   `triggeredAt`（客户端时间仅作辅助信息）

老人身份由服务端登录态确定。**仅在告警与初始紧急工单均已原子持久化后才返回 SOS 受理成功**；成功响应须包含告警 ID、初始紧急工单 ID 及受理状态。任一创建失败不得返回成功或留下半成功业务事实；网络超时应按原幂等标识核实/重试，不应被客户端直接解释为提交失败。

### 22.4 工单状态操作

工单状态变化应使用明确的业务操作接口，例如派单、接单、拒单、开始处理、提交审核、退回、结案等。不得允许客户端通过普通更新接口任意修改状态字段。

## 23. 统一 API 规范

-   统一成功和失败响应结构；
-   统一参数校验与业务错误码；
-   统一分页结构；
-   未登录、无权限、数据不存在、状态冲突和系统异常应明确区分；
-   不向客户端暴露 SQL、数据库结构细节或异常堆栈；
-   重要创建操作支持幂等处理；
-   任何数据权限都在服务端校验；
-   接口字段以最终模块设计为准，不能把本章候选字段当作已经冻结的契约。

## 24. 事务边界

重点保护以下操作的一致性：

1.  创建 SOS 告警与紧急工单；
2.  完成服药打卡与任务状态更新；
3.  更新工单状态与保存操作日志；
4.  创建亲情绑定与更新授权状态；
5.  审核通过与工单结案。

数据库事务可以保证数据库内部操作一致，但不能自动保证微信消息或文件上传等外部操作与数据库处于同一个事务。外部通知应采用独立的可重试处理，不应因通知发送失败而回滚已经合法接受的
SOS 请求。

# 第八部分：定时任务、通知与文件

## 25. 定时任务

本期建议使用 Spring `@Scheduled`：

-   当日服药任务预生成及缺失任务补建检查（必须保证每个当日任务在其提醒时刻前生成并可用；具体时点/调度/故障恢复留 M04 专项）；
-   服药提醒检查；
-   服药超时与关怀通知检查；
-   IoT 仿真数据生成；
-   必要的异常任务检查及经批准的数据保留策略检查；首期不得自动清理业务历史。

定时任务应配合数据库约束与幂等机制，避免重复生成任务或重复通知。任务执行失败应记录原因，必要时支持重试和人工排查。

按 S-01，管理员停止仿真后不再启动新的仿真执行单元，取消已排队但未开始的单元；当前已开始的单个单元允许完成原子写入。失败不得留下部分提交的业务记录，须留执行结果和失败原因。停止操作及各执行结果可追溯，页面提示“已停止后续仿真，当前执行中的样本可能完成”。已经接受的样本继续按正常业务链路处理，不因停止而回滚体征、评估、告警或相关业务记录。停止标志、排队取消、原子写入及恢复方案由 M10 专项明确。

## 26. 通知机制

本期优先采用数据库通知记录配合前端短轮询。

-   社区后台可以每 3--5 秒检查待处理告警和工单变化；
-   小程序在前台运行时刷新提醒与服务状态；
-   微信订阅消息作为可选增强能力，取决于平台授权、规则和实际配置。

不把消息队列作为本期前置条件。重点是保证通知生成、状态查询、发送结果记录和失败追踪。服药关怀按 G-14/G-15：阈值时无有效收件人留事件与结果并提示管理员，新绑定只接收生效后的新通知；每次发送和重试前复核账号、关系、冻结及接收权限，无权者跳过并逐人留痕，其他有效者不受影响，后来恢复授权不补发旧通知。同任务同阶段不重复逻辑通知；逐收件人状态和发送失败恢复留 M11 专项。

首期业务通知事件与接收角色按 N-01 批准，须与 SRS §4.11 保持一致：

| 事件 | 已批准接收角色 | 说明 |
| --- | --- | --- |
| 服药到点/超时关怀 | 本人老人/所有当前有效、账号可用且关系未冻结的绑定子女 | 关怀为原时刻后 45 分钟仍未确认；按 Q03 正常跨日/停机恢复规则区分；无有效收件人留结果并提示管理员，新绑定不补发旧通知；每次发送/重试前复核授权并逐收件人留痕，见 Q03-X03/X04 |
| SOS 接受 | 本社区管理员 | 受理成功由客户端直接反馈；管理员通知不是受理的前提 |
| 健康告警首次建立 | 本社区管理员 | 不新增绑定子女通知；历史体征不自动触发实时紧急通知 |
| 派单/改派生效 | 新承接网格员；改派另通知旧承接人 | 旧承接人只收到分配撤销提示，不继续获得对象详情权限 |
| 拒单/接单超时 | 本社区管理员 | 超时条件由 Q05 冻结 |
| 提交处理结果 | 本社区管理员 | 提醒审核，不代表结案 |
| 审核退回 | 当前承接网格员 | 展示需补充事项 |
| 工单结案 | 本人老人和当前有效授权子女 | 仅可查看各自授权范围内的结果 |

通知读取及每次实际发送、失败重试仍依 G-14/G-15 复核当前权限；无有效收件人记录结果并提示管理员，新绑定不补发旧通知。历史体征如首次建健康告警，只沿用矩阵中的本社区管理员站内事件，不额外生成普通核查通知或实时紧急通知。M01 换号安全通知按 FZ-02 独立处理，不携带老人业务详情，也不扩大本矩阵。系统内通知与前端短轮询为本期业务通知方案，微信订阅消息仍是可选增强，不作为验收前提。各事件的去重、逐收件人状态及失败恢复由 M11 专项确定，不能由此扩大通知范围。

## 27. 文件管理

开发阶段可使用本地目录，例如 `D:/app/uploads/`，但必须：

-   首期仅接受 JPEG、PNG 工单处理照片，单文件不超过 5 MB，每次处理结果最多 5 张；由服务端生成唯一文件名，同时校验扩展名、声明类型及实际内容；
-   数据库保存文件标识、存储路径、上传者和业务关联；
-   文件读取必须重新校验当前角色、社区范围、老人授权关系及工单权限，不能默认公开静态目录或让链接绕过校验；
-   已提交照片和审核材料不得由普通业务操作静默覆盖或物理删除；替换时保留旧版本和审核历史。确需废弃或清理时须走授权的独立流程并留审计；
-   普通上门服务默认至少需要一张有效处理照片；免照须说明原因并经管理员审核批准；SOS 不以拍照作为紧急处置前置条件。

### 27.1 业务数据保留

首期不设置自动物理清理业务历史。老人档案、亲情授权历史、体征、服药任务与打卡、告警、SOS、工单、预约和审计记录，不因解绑、账号/档案停用或工单结案而自动删除。本期仅为使用虚构/合成数据的隔离毕业设计演示环境；不承诺永久保存，也不提供生产数据保留期限或生产级生命周期管理。未来真实社区使用须另行批准保留期限、清理/匿名化及法律与运营责任边界，并完成设计和验证，见 G-24。

### 27.2 测试数据重置

数据重置仅能由有权限人员通过独立操作选择隔离开发、测试或演示环境内明确标记的虚构/合成数据。处于生产环境或无法确认环境/数据范围时必须拒绝；不得将真实老人资料、关系或业务记录放入可重置集合。重置保留系统配置、角色权限基础数据及目标范围外数据，并记录操作者、时间、范围和执行结果。

### 27.3 备份与恢复

- MySQL 逻辑备份每日执行一次，重大变更前额外备份；业务文件单独备份，最近 7 份每日备份保留；
- 备份与运行数据分开存放并限制访问，必要配置另行保护；
- 恢复验收目标为 RPO≤24 小时、RTO≤4 小时。通过隔离环境的实际演练，验证数据库、业务文件和关联关系能够共同恢复并记录实测结果；
- 在恢复演练通过前，目标不得记作已达成；该目标不是生产级灾备承诺。

### 32.1 Q09 看板指标与统计边界

| 指标 | 统计口径 | 空值和边界 |
| --- | --- | --- |
| 有效老人数 | 当前授权社区内有效且未停用的老人档案数，按老人档案去重；绑定数量不影响计数 | 当前时点快照，不扩展年龄分布、趋势或跨社区排名 |
| 待处理健康告警 | 当前社区状态为“待处理”的健康告警事件数；每事件只计一次 | 处理中、已结案不计；SOS 独立，不混入告警数 |
| 服药打卡率 | 有效确认的日期级服药任务 ÷ 应纳入的有效日期级任务 ×100%；符合 Q03 的迟到确认计入；历史按任务日期实际生效的计划版本统计 | 当日只纳入提醒时刻已到的任务；分母为零显示“无数据”；未确认不等于漏服 |
| 首次接单响应 | 首次有效接单时间减工单创建时间，统计区间按创建时间确定；展示平均值、已接单数及当前仍未接单的有效工单数 | 从未接单且取消或管理终止的工单不进入平均值；不得静默隐藏未接单数；无有效样本显示“无数据”；SOS 与普通工单可分开筛选。指标不代表到场或完成 |

全系统业务日期与时间统一采用 `Asia/Shanghai`；看板按该时区自然日 `[00:00:00, 次日 00:00:00)` 统计，以服务端时间归属并展示更新时间。服务端仅统计当前用户有权访问的社区，不接受前端参数绕过范围校验；仿真来源提供“全部（含仿真）/非仿真/仅仿真”，默认全部且明确标识。数量无记录显示 `0`，比率/平均值无有效样本显示“无数据”，查询失败展示错误状态，来源不明的数据明确标记或排除。验收使用固定数据手算并与页面一致，详见 SRS AT-37。

## 33. 最重要的端到端验收链路

**模拟或人工体征输入 → 异常告警 → 社区核查 → 手动创建普通服务工单 → 工单派发 → 网格员处理 → 管理员审核 →
授权子女查看结果。**

这条链路是系统最重要的综合验收场景。它能够验证客户端、后端业务、数据库、权限、通知和工单状态机是否协同工作。

另需单独验证 SOS
主动求助流程，避免健康异常自动告警与老人主动求助两种来源被混为一谈。

## 38. 每个模块的统一设计模板

每个模块都按以下结构输出：

1.  **模块目标与范围**：解决什么问题，不负责什么。
2.  **参与角色与权限**：谁能查看、创建、修改、审核和删除。
3.  **业务规则**：正常路径、边界条件、失败路径。
4.  **状态流转**：明确状态、触发动作和合法转换。
5.  **数据模型**：实体、字段、关系、约束、索引和历史保留。
6.  **API 契约**：方法、路径、请求、响应、错误码和幂等要求。
7.  **事务与一致性**：哪些操作需要事务，如何处理外部副作用。
8.  **异常处理**：重复请求、并发、超时、权限不足、数据不存在。
9.  **测试用例**：正常、边界、异常、安全和重复操作。
10. **验收标准**：明确可观察、可复现的完成条件。
11. **跨模块依赖**：需要哪些模块提供数据或服务。
12. **论文对应内容**：需求分析、系统设计、实现和测试章节分别如何呈现。

## 39. 2026-10-24 三批业务边界决策同步

本节与 SRS 第 9.23 节保持一致，记录业务决策，不替代专项设计、代码实现或验收。

1. **亲情授权（G-01—G-05）：** 合法代理须有可核验的法律监护/代理依据或老人有效书面授权；亲属身份不足以证明代理权。争议可临时冻结并在 5 个工作日内复核，逾期不自动恢复。主动解绑后重申请、管理员撤销后重建均须重新核验。老人无法操作时优先直接确认老人意愿，不能表达时须核验合法代理范围。特殊激活码需核验身份和代理权限、记录依据，不能核验不签发。
2. **档案与既有业务（G-06—G-11）：** 档案恢复由本社区管理员按原因办理；只恢复未来任务/常规提醒，不补造停用期任务或补发过期提醒。停档不提供跳过未结工单交接的紧急通道。已存在体征可审计纠错，但停档后不补录从未入库的历史测量。其他当前有效子女可维护既有计划。档案字段、重复识别和单老人单档案原则按 SRS G-10。档案停用时，仅允许仍有效且已认证的老人账号提交 SOS；已接受 SOS、既有告警及停档前体征的异步评估继续处理。
3. **时间、告警与幂等（G-12/G-13/G-18—G-20）：** 全系统业务时间使用 `Asia/Shanghai`。服药截止显示当日 23:59，包含 23:59:59.999；次日 00:00:00.000 起拒绝普通打卡，过窗状态不表示漏服。仅本社区管理员可改变健康告警状态/结案；结案须结果分类和事实摘要。相同幂等标识的同内容重试返回原结果；同标识异内容拒绝并审计，不覆盖、不重复创建。

### 43.3 跨模块必须保持的架构不变量

1. **权限一致：** RBAC 只给出角色方向；每次服务端请求还必须按账号、老人档案、社区、对象归属、绑定/分配有效性检查；列表、详情、文件、统计及关键写入都适用。账号停用与档案停用不得混淆；档案停用时仅符合 SRS G-11 的 SOS 窄范围例外允许新业务。
2. **业务事实独立：** 体征、健康告警、SOS、预约、工单、通知与操作审计不是同一状态实体。健康告警不能自动创建普通工单；SOS 的告警与紧急工单原子建立；告警和工单独立结案。
3. **时间和版本：** 所有业务自然日与时限基于服务端权威时间和 `Asia/Shanghai`；首次评估任务创建时固定当时生效的规则版本；停机任务补建使用对应日期当时生效的计划版本，不能用最新版本覆盖历史。
4. **幂等和并发：** 同键同规范化内容复用结果；同键异内容 HTTP 409 并审计；冲突操作只允许一个合法状态提交且不覆盖成功者；通知失败不得回滚已接受 SOS，文件和数据库关联需考虑失败补偿。
5. **通知范围：** N-01 的八行首期业务事件及角色不可扩张；无收件人留结果，新绑定不补旧消息，每次发送/重试前重新复核授权；FZ-02 换号成功安全通知为独立的 M01 规则。
6. **演示数据和文件：** 人工/仿真来源由服务端固定，真实设备未接入；数据仅限虚构/合成演示环境；证据文件按权限读取、保留历史；恢复须联合验证数据库与文件，RPO/RTO 均未测。
