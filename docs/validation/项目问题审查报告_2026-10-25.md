## 1. 一句话结论

> **后端业务骨架与数据库结构是完整的，但"外壳"（认证授权）和"证据"（数据真实性）两件事没有做**：登录有后门、39 个接口无鉴权、任意用户可读他人档案、大屏 KPI 是编的、审计签名是假的、照片与幂等只存在于文档里。前端则是"能点、能走流程、但不落库"的原型级实现。作为**答辩演示**勉强可用（靠后门与假数据），作为**论文所述系统**目前无法自证。

**F-13 会话完全不落库、不校验过期、不可撤销【静态】**

### 3.2 状态机与并发
- **工单状态机不校验**：`WorkOrderServiceImpl` 的 dispatch/accept/reject/start/submit/review 六个方法只判"是不是责任人"，**没有一处校验 `fromStatus`**；`ORDER_STATUS_INVALID` 定义了从未抛出。已 `CLOSED` 可被重新派单；`PENDING_DISPATCH` 可直接开始服务。
- **乐观锁形同虚设**：`@Version` 已注册，但 MyBatis-Plus `updateById` 版本不匹配时**返回 0 行而不抛异常**，所有服务都忽略返回值（`ElderProfile`、`ElderFamilyLink`、`ElderCorrectionRequest`、`ServiceReservation`、`WorkOrder`）→ 并发覆盖静默发生。
- `MedicationPlanServiceImpl:131-148`：版本号 `currentVersionNo+1` 无锁无重试，并发编辑撞 `uk_med_plan_version` → 500；更新时把 `frequencyType` 硬编码成 `DAILY`；旧版本 `end_date` 从不关闭；无 `plan.status` 校验（暂停的计划仍可编辑）；**没有 disable/enable 接口**，计划状态永远出不了 `ACTIVE`。

- `KinshipServiceImpl`：`FROZEN` 状态下重新申请会把状态改回 `PENDING` 并清空冻结原因（争议可被"再申请一次"洗掉）；审批不校验 `currentApplicationId`，可批准过期申请把旧关系救回 `ACTIVE`；解绑/复核不写原因。
- `CommunityDashboardServiceImpl:162,192` 的 `.last("LIMIT " + limit)`：`limit` 未夹逼，负数直接 SQL 语法 500。

### 3.3 分页与 N+1
- **`PageResult.of` 参数顺序写反**：`ElderArchiveServiceImpl:108`、`HealthAlertServiceImpl:78` 传的是 `(items, total, current, size)`，签名是 `(items, page, pageSize, total)` → **老人列表和告警列表的分页元数据整体错位**（实测 `GET /elder/archives?page=1&size=1` 返回 `"page":3,"pageSize":1`）。审计模块的调用顺序是对的。

### 3.4 健康评估
- `AssessmentServiceImpl:37-139` 把 ACTIVE `alert_rule_version` 读出来**只用于盖章 `rule_version_id`**，阈值全部硬编码：血压 160/100、血糖 11.1/7.8、心率 >100/<50；而种子里规则写的是 `fasting_high: 7.0`、`bradycardia: 55`。→ **可配置规则是装饰品，结果与种子自相矛盾**；无规则时回落 `ruleVersionId = 1L`（:45），未播种库会因外键失败整笔回滚。

## 5. MEDIUM / LOW（择要）

- **全局异常处理缺 404/405/415/400**：访问不存在路径实测返回 **500** 而不是 404；`ConstraintViolationException` 也变 500。
- **CORS**：`allowedOriginPatterns("*")` + `allowCredentials(true)`（`WebMvcConfig.java:30-38`），而过滤器确实支持 Cookie 鉴权。
