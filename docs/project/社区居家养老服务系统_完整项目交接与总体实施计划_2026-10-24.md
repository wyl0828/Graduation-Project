## 一、项目定位与最终交付目标

### 1.1 课题名称

当前暂定：

《基于 Spring Boot 与适老化设计的社区居家养老服务系统设计与实现》

最终题目以学校审批结果为准。开题报告、系统名称、论文封面和答辩 PPT 应保持一致。

### 1.2 系统定位

系统面向社区居家养老场景，主要服务四类业务角色：

- 老人：查看健康信息、服药任务、发起 SOS、查看服务进度。
- 子女：在有效授权范围内查看老人信息、维护用药计划、预约助老服务。
- 网格员/护工：接收分配的工单、提交处理记录和相关证据。
- 社区管理员：维护档案与授权、处理告警、调度工单、审核结果、管理配置和查看统计。

核心不是简单地展示健康数据，而是建立一条可验证的业务闭环：

**老人档案与授权 → 体征及用药数据 → 告警或 SOS → 社区核查与工单处理 → 审核结案 → 老人、子女查询处理进度。**

其中，社区服务闭环是系统的核心业务主线；健康、用药、通知、仿真与统计模块为其提供支撑。

### 1.3 最终应交付的成果

1. 可运行的前端、后端及数据库。
2. 老人端与子女端小程序，以及社区 Web 管理端。
3. 数据库建表、初始化和演示数据脚本。
4. API 契约、配置说明和部署运行说明。
5. 模块详细设计、测试计划和可执行测试用例。
6. 功能、权限、异常、并发、适老化、性能、部署复现和备份恢复的真实测试证据。
7. 完整本科毕业论文及与实际系统一致的截图、表格和测试结果。
8. 答辩 PPT、演讲稿、演示流程和答辩问题准备材料。

不得把设计文档、界面原型或预期测试指标当成已完成的软件成果。

## 二、技术路线与范围边界

### 2.1 当前技术基线

- 小程序：Uni-app + Vue 3，老人模式与子女模式。
- 社区后台：Vue 3 + Element Plus + ECharts。
- 后端：Java + Spring Boot，采用单体分层架构。
- 数据访问：MyBatis-Plus。
- 数据库：MySQL 8.0。
- 定时任务：Spring `@Scheduled`。
- 文件存储：本地文件目录，数据库保存文件元数据。
- 通知刷新：以前端短轮询为首选轻量方案，具体实现遵循通知专项设计。
- 数据来源：人工录入与仿真数据；服务端负责确定来源类别。

除非发现明确的技术障碍并经讨论确认，不随意更换技术栈。

### 2.2 本期范围

核心功能包括：

- M01 身份认证与权限。
- M02 老人档案与亲情绑定。
- M03 健康档案与体征管理。
- M04 用药计划与打卡。
- M05 告警与 SOS。
- M06 社区工单与调度。
- M07 助老服务预约。
- M08 适老帮助与服务进度。
- M09 社区数据看板。
- M10 IoT 仿真与演示。
- M11 通知与文件管理。
- M12 系统配置与审计。

M11、M12 是公共支撑能力，不需要拆成独立服务。

### 2.3 明确不做的事情

本期不以以下内容为交付条件：

- 真实智能手环、血压计等设备的接入。
- 医疗诊断、自动处方或临床准确率验证。
- 微服务架构、复杂消息中间件。
- 生产环境的数据生命周期管理。
- 医院挂号平台对接、商城、计费、库存和自动排班。
- 真实救援到场时限保证。
- 为追求页面数量而添加缺乏业务价值的功能。

本期使用隔离的毕业设计演示环境，只使用虚构或合成数据。仿真数据必须明确标识，不能冒充真实测量结果。

当前没有独立的完整交互设计交付物，应建立一份可用于开发的交互说明。

不要求先做完整高保真视觉稿，也不要求强行限制为九个页面。

### 阶段 5：数据库设计

在业务边界和模块交互明确后，确定物理数据库方案。

交付物至少包括：

- 完整 ER 图。
- 数据字典。
- 建表与初始化 SQL。
- 主键、外键、唯一约束和索引。
- 关键状态、审计历史和幂等标识的持久化设计。
- 合成演示数据。
- 数据重置、备份与恢复涉及的范围约束。

重点保证老人档案、授权关系、体征、服药任务、告警、工单、预约、通知、文件元数据和审计记录之间的一致性。

**不得直接沿用原始全案的“五张核心表足够”方案。** 应以当前业务需求和真实数据关系确定表结构。

### 阶段 6：API 契约设计

所有前后端交互使用统一的 API 规范，默认沿用 `/api/v1` 路径前缀。

每个接口必须明确：

- HTTP 方法与路径。
- 请求参数及校验规则。
- 响应结构和错误语义。
- 登录、角色、对象归属及数据范围检查。
- 状态迁移条件。
- 幂等标识与重复请求处理。
- 事务、并发冲突和失败恢复。
- 文件上传、下载与访问权限。

不能只写接口名称或示例 JSON 就认定 API 设计完成。

### 阶段 7：测试设计

测试设计必须在对应模块开工前具备可执行的最小版本，并随开发同步扩充。

每条用例至少包括：

- 用例编号与关联需求编号。
- 前置条件和测试数据。
- 执行步骤。
- 预期结果。
- 必要的数据库断言。
- 异常注入或并发验证方式。
- 实际结果、证据位置和结论。

全部使用虚构或合成测试数据。

- **AT-40：** 固定数据规模和并发条件，测量查询、写操作、看板 P95、失败率和状态更新可见时间。
- **AT-41：** 在干净环境中按说明重新初始化数据库并启动前后端，复现核心流程。
- **AT-36：** 实际验证数据库、业务文件和关联关系的备份恢复；**A-06：** 归档对应测试状态与证据。

备份目标包括每日逻辑备份、重大变更前备份、最近 7 份每日备份保留，以及 RPO≤24 小时、RTO≤4 小时的恢复目标。只有完成实际演练，才能报告实测结果。

所有测试记录只能标记为“通过、失败、未测、阻塞”。不得虚构结果，也不得删除失败样本或把未执行项目标记为通过。

## 八、论文与答辩计划

论文不应等到全部开发结束才开始准备，但涉及实现与测试的章节必须以真实成果为依据。

建议采用以下章节组织：

1. **绪论：** 研究背景、研究意义、相关工作和本文主要工作。
2. **相关技术与理论基础：** Spring Boot、Vue 3、MySQL、权限控制、适老化设计等。
3. **需求分析：** 用户角色、业务流程、功能需求、非功能需求和系统边界。
4. **系统总体设计：** 架构、模块、权限、数据库与业务流程设计。
5. **系统详细设计与实现：** 核心模块、关键接口、状态控制和关键实现。
6. **系统测试与结果分析：** 测试环境、测试用例、结果、缺陷与修复情况。
7. **总结与展望：** 已完成工作、实际限制和未来扩展方向。

该目录是后续论文写作建议，最终按学校论文模板和导师要求调整。

论文与开发同步的建议：

- 需求冻结后整理需求分析章节。
- 总体设计、数据库和 API 定稿后整理系统设计章节。
- 模块实现后补充关键代码说明、流程图和界面截图。
- 系统测试完成后填写真实测试数据和结果。
- 最后统一术语、题目、图表编号、参考文献和格式。

答辩材料必须区分“已实现”“已测试通过”和“未来扩展”。不得将仿真数据描述为真实设备数据，不得将规则告警描述为医疗诊断，也不得将未测性能指标写成实测结果。
