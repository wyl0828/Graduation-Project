## 1. 复核范围和结果边界

复核将 E-01—E-07 v0.1 初稿作为整体，交叉对齐共享实体、字段和约束、历史保留、API/错误/幂等、权限、锁序候选、事务边界、状态映射及 BR/FR/NFR/Q/G/E/AT 追踪。

本轮完成的是**文档级集成设计**，不是物理数据库/API 冻结、模块详细设计、业务代码或运行验收。当前工作区只有文档；所有实现仍为“未开始”，AT-01—AT-41 及 A-01—A-06 均为“未测/证据缺失”。下表中的“已统一”表示已有唯一文档口径，具体 DDL、端点和并发正确性仍需后续验证。

## 2. 首轮发现的处置结果

| 编号 | 首轮问题 | 集成处置 | 当前残余门槛 |
| --- | --- | --- | --- |
| IR-01 | E-01/E-02 的 elder_identity_link 字段和生命周期不同 | 由 M02 定义单一模型：link_id、elder_id、user_id、linked_by_activation_ticket_id、linked_at；elder_id/user_id 双向唯一，不设 SRS 未定义的独立 status；M01 激活流程调用该模型。 | DDL 落实双向唯一、激活票据唯一消费和一致外键；身份解绑需先走需求变更。 |
| IR-02 | E-02/E-03/E-04/E-05 锁顺序不完整 | 基线 v1.1 §2.4 细化 00—120 级候选顺序；拟采用维护门闩（若 D1 选用）→幂等记录→业务对象。预约竞争顺序为预约→申请→执行关联→工单。该顺序仍是静态候选。 | 在 D1 决定门闩或等效方案；按每个事务列出真实 SQL/锁行，做死锁审查和并发验收；验证前不得放行高风险跨模块写入。 |
| IR-03 | M11 逻辑通知/逐人投递/outbox 分散 | 统一 notification_event + notification_delivery 契约并加入 policy_scope；N01_BUSINESS 严格遵守 N-01，FZ02_SECURITY 独立遵守 FZ-02，可共用逻辑契约和投递基础设施。 | D2 冻结物理表映射、有限重试策略；完成 AT-11/22/23。 |
| IR-04 | 通用审计与领域事件命名/职责混用 | M12 统一逻辑契约命名为 audit_log；elder_archive_event、alert_action_log、工单/预约操作历史是领域历史，不代替通用审计，也不再另建重复的 audit_event。 | DDL/审计字段脱敏评审；关键状态与审计同事务的故障注入待执行。 |
| IR-05 | API 前缀、响应、错误码和隐藏策略不同 | 统一完整 `/api/v1`、`code/message/traceId/data`、401/403/404/409/422/429/5xx 分类、同一幂等冲突码和授权对象隐藏规则；保留具体领域 409 码。 | 各模块完整方法/字段/分页/错误清单在 D3 API 冻结点完成；当前专项端点草案仍须映射。 |
| IR-06 | 时间类型、精度和留存规则不同 | 统一有符号 BIGINT 内部主外键、DATETIME(3) UTC、DATE/TIME(0) Asia/Shanghai；业务历史、文件版本、演示重置和备份保留分层。 | 工程基座如存在既有 ID 规范须在 D1 整体核对；临时对象 TTL、备份保留细节和运行验证待补。 |
| IR-07 | M06/M07 状态和终态映射不清 | 统一预约、执行关联和工单为独立状态主体；预约确认是预约 `CONFIRMED` + M06 工单 `PENDING_DISPATCH` 同事务，执行关联不复制工单状态；明确 `CLOSED`、`VOIDED`、`REJECTED`、`CANCELLED`、`TERMINATED_PRE_ACCEPTANCE`、`SERVICE_STOPPED` 的区别及取消/接单竞争。 | M06 普通工单全生命周期详细设计尚缺；M06 编码前阻塞。 |
| IR-08 | 缺少跨专项追踪矩阵 | 已建 BR、FR、NFR、Q、G、C/FZ/N/M/S、E-01—E-07 与 AT-01—AT-41 矩阵，逐项标设计状态、测试入口和未测/证据状态。 | 矩阵随模块详细设计、实际开发和验收结果持续更新；当前运行证据均缺失。 |
| IR-09 | 七份 E 初稿没有完整 M06 普通工单设计；M08/M09 也不在 E 范围 | 在矩阵中将 M06-01—07 标为缺少完整专项，将 M08/M09 标为 E 范围外待专项，不把片段覆盖描述成完整设计。集成基线提出 M06 工单交接/状态映射方案供 M06 详细设计承接。 | M06 详细专项是 M06、E-04 SOS、E-05 预约和 E-06 证据链的前置门槛；M08/M09 在对应模块开工前补设计。 |
| IR-10 | API 版本字段、分页字段及幂等范围不一致 | 基线 v1.1 统一 `expectedVersion`、`items/page/pageSize/total` 和 `(principal_scope, operation_scope, key)`；幂等键仅使用 `Idempotency-Key` 请求头，operation scope 包含 HTTP 方法和版本化路由模板。 | D2 冻结匿名安全上下文的存储映射；D3 更新完整端点和 DTO。 |
| IR-11 | 全局锁序存在“幂等记录末尾”与“维护门闩”两套方案 | v1.1 将幂等记录前移到业务对象锁之前；维护门闩保留为工程候选，需与覆盖全部写入口的等效方案择一。 | 通过真实 MySQL 事务、索引、执行计划及并发/死锁用例验证；候选顺序不得标为已冻结。 |
| IR-12 | SOS 事实在文档中出现 `sos_event` / `sos_request` 两种名称 | 采用 `sos_event` 作为唯一 SOS 事件事实名称；E-04 中的 `sos_request` 表述已归一，SOS 不与 `health_alert` 或工单共用状态。 | D2 核对 E-04 的物理表映射与唯一约束。 |
| IR-13 | 新建议稿将预约确认后建工单时点留给后续专项 | 保留当前基线：预约转 `CONFIRMED`、创建 M06 `PENDING_DISPATCH` 工单及唯一执行关联必须同一事务提交；失败整体回滚，不异步补建。 | M06 专项冻结状态/表/API 后，执行预约确认原子性与取消/接单并发验收。 |
| IR-14 | 新专项稿仍处于“待回写”状态，含待确认技术参数 | 已采纳项并入基线 v1.1；INT-API/LOCK/STATE 已加入需求追踪矩阵并关联 AT。门闩、MySQL 锁行为、重试参数和技术终态仍未冻结。 | INT-LOCK-12 仍需补可执行 AT 子项；其余 INT 也须拆成步骤、数据、断言与证据位置。运行证据仍未产生。 |
