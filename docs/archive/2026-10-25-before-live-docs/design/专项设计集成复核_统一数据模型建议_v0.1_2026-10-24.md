## 1. 本轮结论

本轮按 E-01---E-07
初稿实际内容进行静态交叉核对。建议把下列规则作为全项目统一数据模型约定，再逐份回写专项文档：

1.  **`elder_identity_link` 由 M02 定义，E-01 引用同一模型。**
    统一主键、老人/账号双向唯一约束、激活票据关联字段；不保留没有已批准生命周期语义的独立
    `status`。
2.  **内部关系型主键统一使用 `BIGINT`。** `CHAR(36)`
    等不透明标识只用于明确需要对外暴露或不宜顺序枚举的票据、会话等标识；同一外键两端类型必须完全一致。
3.  **统一时间字段语义。** 表示时间瞬间的 `*_at` 字段统一为
    `DATETIME(3)`，按 UTC 约定存储；业务自然日和提醒时刻按
    `Asia/Shanghai` 解释；API 时间戳必须携带时区。
4.  **通知采用共同的逻辑事件/逐接收目标/投递结果契约。**
    M04、M05、M06、M07 等模块不各自定义一套互不兼容的 outbox。N-01
    业务通知白名单与 FZ-02 换号安全通知必须保持独立策略范围。
5.  **M12 统一审计使用 `audit_log` 契约。**
    `elder_archive_event`、`alert_action_log`、工单操作历史等业务历史仍按需保留；它们不替代通用审计，也不再各自新建一张语义重复的通用
    `audit_event` 表。
6.  **E-06 文件模型只保留一种权威业务关联。** 建议采用
    `business_file_link` 指向具体 `file_asset_version`；避免同时在
    `file_asset`、`file_asset_version`
    和关联表中重复保存互相可能冲突的业务对象关系。
7.  **业务历史、文件版本、演示数据重置和备份保留分开管理。**
    不自动物理清理已提交业务历史；演示重置只处理明确标记的虚构/合成数据；最近
    7 份每日备份是备份保留规则，不是业务数据保留期限。
8.  **M06 工单状态与 M07 预约状态分别拥有唯一真源。**
    `reservation_execution_link`
    只表达关联，不另存一个独立且可能失配的执行状态；具体状态映射放到第二步
    API/状态机集成设计中完成。

以上为推荐统一方案。实施前应把被采纳的约定写回对应 E
文档，并在集成复核记录中标记版本与差异；不得仅凭本文件宣称全部专项已冻结。

## 2. 全局数据模型约定

### 2.1 标识与命名

  --------------------------------------------------------------------------------------------------------------------------------------
  项目                    统一建议                   说明
  ----------------------- -------------------------- -----------------------------------------------------------------------------------
  内部主键                `BIGINT`，由 MySQL 生成    本期为单体/模块化后端，不引入雪花 ID 或分布式 ID 的额外复杂度

  外键                    与被引用主键类型完全一致   不混用 `BIGINT`、`BIGINT UNSIGNED`、字符串数字

  外部不透明 ID           仅在有明确用途时采用       例如激活票据、会话标识；不替代内部关系型主键
                          `CHAR(36)` 等              

  表名                    统一 `snake_case`          保留已有 `sys_` 系统表前缀；业务表不额外混用 `t_` 前缀

  主键字段                使用表内明确的             新表选定后在数据字典中固定，不在同一实体的不同专项中混用
                          `<entity>_id` 或 `id`      

  幂等键                  HTTP Header                请求正文不再另定义含义相同但命名不同的幂等字段；历史/内部任务可使用独立业务唯一键
                          `Idempotency-Key`          

  请求追踪                `trace_id`                 贯穿 API、业务日志、通知投递、审计和作业证据

  并发版本                `row_version`              可变聚合根采用乐观锁时使用；业务版本序号另用 `version_no`

  社区标识                `community_id BIGINT`      同一项目中所有引用使用同一类型；必须由服务端校验范围
  --------------------------------------------------------------------------------------------------------------------------------------

内部主键使用 `BIGINT` 是工程简化建议，不是 SRS
业务要求。若实现环境有已存在的统一 ID
规范，应在编码前一次性确认，并确保全部专项一致；不能由单个模块自行选择不同主键类型。

### 2.2 时间字段与业务时区

统一如下：

-   `created_at`、`updated_at`、`occurred_at`、`accepted_at`、`reviewed_at`、`sent_at`、`expires_at`
    等表示**时间瞬间**的字段，统一使用 `DATETIME(3)`，应用层按 **UTC**
    写入与读取。
-   数据库连接与运行环境应明确 UTC 约定，避免 MySQL
    会话时区导致时间转换不一致。`DATETIME` 本身不携带时区，UTC
    是应用层约定，必须写进部署配置与测试。
-   业务自然日使用 `DATE`，按 `Asia/Shanghai`
    划分；提醒时刻等墙上时刻使用 `TIME`，并明确它属于 `Asia/Shanghai`。
-   API 时间戳使用 ISO-8601 且必须带时区。建议服务端以 UTC `Z`
    形式输出时间瞬间，客户端按 `Asia/Shanghai` 展示。
-   服务端时间是授权、过期、截止、调度和验收计算的权威时间。客户端时间仅作为辅助事实保存，不能决定服务端业务状态。
-   如需保存用户报告的采集时间与服务器接受时间，应分别保存
    `collected_at` 和
    `accepted_at`；历史录入/仿真/实时来源仍由服务端固定标记。
-   不得混用 `TIMESTAMP(3)`、`DATETIME`、`DATETIME(3)`
    表达相同类型的瞬间。建议全部统一到 `DATETIME(3)` UTC
    约定，避免不同专项的隐式时区行为不同。

### 2.3 历史与删除

  ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------
  数据类别                                                                   统一规则
  -------------------------------------------------------------------------- ---------------------------------------------------------------------------------------------------------
  老人档案、亲情授权历史、体征、服药任务/打卡、告警、SOS、工单、预约、审计   不因账号停用、档案停用、解绑、结案或普通业务操作自动物理删除

  已提交文件与历史版本                                                       不静默覆盖或物理删除；替换生成新版本，历史证据引用保持可追踪

  暂存上传对象                                                               可按明确的临时会话有效期和清理规则处理；该期限仍需在统一配置/部署设计中确定，不能扩展到已提交证据

  演示数据重置                                                               仅隔离环境内明确标记的虚构/合成数据，且范围明确、授权充分；真实或来源不明数据、生产环境、范围不明均拒绝

  重置作业记录与审计                                                         重置不能删除自身审计、系统配置、备份清单和范围外内容

  每日备份                                                                   保留最近 7 份已验证每日备份；新备份未验证前不得淘汰旧有效备份

  重大变更前备份                                                             独立标识；具体保留期限在部署规范中明确，SRS 未冻结该期限

  生产数据保留期限                                                           不在本期确定；未来真实部署须另行批准，不推定永久保存
  ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------

业务历史保留与备份保留是两套规则：七份备份不代表业务记录只保存七天；演示重置也不能清理备份保留集合。

## 5. 冲突一：统一 `elder_identity_link`

### 5.1 冲突事实

-   E-01 §7.3 定义了
    `elder_id`、`user_id`、`linked_at`、`linked_by_activation_ticket_id`，没有
    `link_id` 和 `status`。
-   E-02 §8.2 定义了
    `link_id`、`elder_id`、`user_id`、`linked_at/by`、`status`，没有明确包含激活票据关联。
-   SRS
    的业务规则是老人通过一次性激活码首次关联既有档案；账号停用不删除档案/关系；已使用激活码走账号恢复；没有批准一个独立的"身份关联解绑"业务流程。

### 5.2 统一建议

由 M02 的数据模型定义 `elder_identity_link`，E-01
不再重复定义字段，只引用此契约并负责激活事务。

  -------------------------------------------------------------------------------------------------------------------------------------------
  字段                               类型建议                 约束/说明
  ---------------------------------- ------------------------ -------------------------------------------------------------------------------
  `link_id`                          `BIGINT`                 主键

  `elder_id`                         `BIGINT NOT NULL`        外键到 `elder_profile.elder_id`；`UNIQUE(elder_id)`

  `user_id`                          `BIGINT NOT NULL`        外键到 `sys_user.user_id`；`UNIQUE(user_id)`

  `linked_by_activation_ticket_id`   `CHAR(36) NOT NULL`      外键到
                                                              `elder_activation_ticket.ticket_id`；唯一，保证同一激活票据只产生一次身份关联

  `linked_at`                        `DATETIME(3) NOT NULL`   UTC；成功建立关联的服务端时间

  `created_at`                       `DATETIME(3) NOT NULL`   UTC；如与 `linked_at` 无独立用途，可合并为一个字段，物理 DDL 时择一固定
  -------------------------------------------------------------------------------------------------------------------------------------------

### 5.3 不设置独立 `status` 的原因

1.  SRS 未定义老人身份关联的停用、解绑、撤销或重新激活状态机。
2.  `sys_user.status` 表示账号是否可登录；`elder_profile.status`
    表示档案是否停用；二者均不能通过身份关联状态替代。
3.  `elder_family_link.status`
    表示子女授权关系，不得与老人身份关联混用。
4.  若未来批准身份关联解绑或重新关联流程，须先变更
    SRS/业务规则，再扩展身份关联状态机与唯一性策略；本期不预埋未经批准的业务状态。

**必须保持的约束：**

-   一个老人档案最多关联一个老人账号；一个账号最多关联一个老人档案。
-   老人激活只关联既有档案，不创建亲情绑定。
-   账号停用/恢复不删除、不重建该关联。
-   角色分配中必须存在 `ELDER`，但角色分配不替代身份关联。
-   激活票据消费、身份关联、`ELDER` 角色分配、幂等结果与必要审计必须按
    E-01 的原子性要求处理。
-   E-01
    激活流程在需要同时操作档案与票据时，需遵循下一阶段统一冻结的锁顺序。

### 5.4 必须回写的地方

-   **E-01 §7.3：** 删除独立字段表，改为"引用 M02 `elder_identity_link`
    统一模型"；激活票据外键使用 `linked_by_activation_ticket_id`。
-   **E-02 §8.2：** 使用上述统一字段与约束；移除没有 SRS 生命周期支撑的
    `status`；说明账号状态、档案状态和亲情关系状态独立。
-   **总体设计 §17/§18：**
    保留"账号与老人档案一对一身份关联"逻辑关系，不宣称每个逻辑实体必须单独建表。

## 6. 公共模型：通知、审计与幂等

### 6.1 通知逻辑事件与投递结果

E-03 已区分逻辑通知事件和逐接收人投递；E-04/E-05 使用较宽泛的
`notification_outbox`；E-01 使用
`security_notification_outbox`。建议统一为一套**共同逻辑契约**，并在实现时由
M11 统一管理。

#### `notification_event`（逻辑事件/outbox）

至少包含：

-   `notification_event_id`
-   `policy_scope`：如 `N01_BUSINESS`、`FZ02_SECURITY`
-   `event_code` / `event_family`
-   `business_object_type`、`business_object_id`
-   `phase`（适用时）
-   `dedupe_key`（唯一）
-   `created_at`、`triggered_at`
-   `event_status` / `event_outcome`
-   必要的最小通知载荷或安全引用
-   `trace_id`

约束：

-   业务状态、逻辑事件和待投递记录须在同一数据库事务提交。
-   外部发送不在业务事务中同步执行；由 M11 在事务提交后投递。
-   同一业务事件按冻结规则去重；重试不得创建第二个逻辑事件。
-   `N01_BUSINESS` 的 `event_code` 和接收角色必须严格来自 SRS N-01
    白名单。
-   `FZ02_SECURITY` 用于手机号变更安全通知，必须独立执行 FZ-02
    的目标手机号核验/可达性规则，不能视为新增 N-01 业务事件。
-   无有效收件人时记录事件级结果；不能通过新增未经批准的接收角色来"解决"无收件人问题。

#### `notification_delivery`（逐接收目标投递）

至少包含：

-   `delivery_id`、`notification_event_id`
-   `recipient_kind`、`recipient_user_id`（适用时）
-   `destination_ref_type/id/role`（适用于需引用受保护目标的通知，如
    FZ-02 新/旧手机号；不在通用日志写明文号码）
-   `channel`
-   `delivery_status`
-   `attempt_count`、`next_attempt_at`
-   `last_error_code`、`skip_reason`
-   `last_authorization_check_at`
-   `sent_at`、`trace_id`

建议约束：

-   同一事件、接收目标和渠道只保留一条逻辑投递记录；重试更新该记录并追加必要尝试结果，不重复创建逻辑通知。
-   `N01_BUSINESS`
    每次发送/重试前重新检查当前账号、社区范围和亲情授权；失权接收人应跳过并留痕。
-   `FZ02_SECURITY`
    通过换号申请中的受保护目标引用选择新/旧号码；不能从已变更后的账号手机号推断旧号码，也不能把号码明文写入日志。
-   `SENT` 仅表示发送通道已接受，不代表用户已读。
-   外部服务不支持幂等时，不承诺绝对"恰好一次"；通过逻辑事件去重、有限重试和投递结果记录实现可追踪的投递行为。
-   重试次数、间隔、过期窗口属于技术参数，应由 M11
    统一确定并实测，不能由 E-03/E-04/E-05 分别设置冲突值。

### 6.2 M12 统一审计 `audit_log`

建议统一审计字段契约：

  ------------------------------------------------------------------------------------------------
  字段                                            用途
  ----------------------------------------------- ------------------------------------------------
  `audit_id`                                      内部主键

  `trace_id`                                      关联本次请求/作业

  `actor_type`、`actor_user_id`                   用户、系统任务或受控运维主体；系统任务可无用户
                                                  ID

  `actor_role_code`、`community_id`               操作时角色/范围快照（适用时）

  `action_code`                                   稳定、可检索的动作编码

  `object_type`、`object_id`                      目标对象

  `outcome`、`error_code`                         成功、拒绝、失败或部分结果

  `reason_code`、`reason_summary`                 原因与审批依据摘要（适用时）

  `before_state_summary`、`after_state_summary`   必要状态摘要，不复制无关敏感信息

  `occurred_at`                                   UTC 服务端时间

  `metadata`                                      最小必要的结构化附加信息
  ------------------------------------------------------------------------------------------------

规则：

-   关键业务状态变更与必需审计记录按同一数据库事务提交；若审计无法可靠写入且
    SRS 要求留痕，该敏感操作必须失败关闭。
-   业务用户不能普通编辑/删除审计记录；演示数据重置不得清除审计记录。
-   不记录密码、令牌、验证码、激活码明文、会话
    token、无关完整健康信息或文件物理路径。
-   `elder_archive_event`、`elder_family_link_event`、`alert_action_log`、工单操作历史、预约审批历史是领域历史，继续服务于状态查询与业务解释；它们不替代
    `audit_log`。
-   E-04 中通用 `audit_event` 应改为引用 `audit_log`
    契约，避免并行创建两套通用审计表。若某领域确需专用业务事件表，必须明确其业务语义和与
    `audit_log` 的区别。

### 6.3 统一幂等逻辑

建议所有可重试的写接口统一使用 `Idempotency-Key`
请求头，业务层复用统一幂等服务/记录契约：

-   作用域至少包含主体、操作范围和幂等键。
-   保存规范化请求摘要、处理状态、结果对象定位和必要的原响应信息。
-   同键同规范化内容：返回原结果或可追踪的当前处理状态，不重复创建业务事实。
-   同键不同规范化内容：返回 HTTP 409、`IDEMPOTENCY_KEY_REUSED`。
-   不同真实 SOS 必须使用不同幂等键；不能按时间邻近自动合并。
-   领域唯一约束仍须独立存在，例如同一日期/计划任务唯一、同一预约时段占用唯一；幂等键不能代替业务唯一性约束。
-   E-05 的 `reservation_idempotency`
    可在物理实现中合并到统一记录，但必须保留预约业务唯一约束；E-06
    上传会话的幂等字段也须遵循相同的键与摘要语义。
-   对匿名激活/注册流程，幂等主体需绑定票据/挑战等安全作用域，不能仅用一个可被不同主体共享的全局键。

是否所有幂等记录物理合并成单表，在 DDL 阶段确认；逻辑行为必须统一。

## 7. E-06 文件模型去重

### 7.1 当前重复表达

E-06 §5.2 的 `file_asset` 同时包含
`file_object_id`、`business_type`、`business_id`；§5.3 的
`file_asset_version` 又包含
`file_object_id`、`business_result_id`/`review_record_id`；§5.5 另提供
`business_file_link`，并说明该表可以作为直接归属字段的替代方案。

如果三处同时保存业务归属和对象引用，容易产生以下冲突：

-   `file_asset.file_object_id` 与当前版本指向不同物理对象；
-   `file_asset.business_id` 与 `business_file_link.business_id`
    不一致；
-   文件替换后审核记录不清楚究竟引用旧版还是新版；
-   重置/恢复时无法判断哪一条关系才是权威关联。

### 7.2 统一建议：使用 `business_file_link` 作为唯一业务关联

#### `file_object`：物理内容对象

保存 `id`、唯一
`storage_key`、`storage_backend`、`content_sha256`、`byte_size`、服务端检测的
`detected_media_type`、`storage_state`、创建/校验时间。

#### `file_asset`：逻辑资产

保存
`id`、`owner_user_id`、`community_id`、`asset_status`、`current_version_id`、创建/更新者和时间。

-   移除 `file_object_id`：物理对象应由当前版本指向，避免双重真源。
-   移除 `business_type`、`business_id`：业务归属只由
    `business_file_link` 表达。
-   `community_id`
    仅作为资产的归属/分区辅助字段，不是授权依据；访问时必须重新校验关联业务对象的当前社区和权限。

#### `file_asset_version`：不可覆盖的版本

保存
`id`、`asset_id`、`version_no`、`file_object_id`、上传者/时间、验证结果、`version_status`、`supersedes_version_id`
等。

-   `(asset_id, version_no)` 唯一。
-   由 `file_asset.current_version_id` 指定当前版本。
-   `SUPERSEDED` 只表示不是当前版本，不等于历史证据无效。
-   文件内容摘要和大小以 `file_object`
    为物理内容真源；如果版本表保留摘要快照，必须明确它是不可变校验快照且与物理对象摘要一致，不能各自独立更新。
-   审核记录必须引用实际审核的
    `file_asset_version_id`，不能只引用"当前文件资产"。

#### `business_file_link`：业务对象与版本的唯一关联

至少包含
`id`、`business_type`、`business_id`、`file_asset_id`、`file_asset_version_id`、`link_role`、`created_at`、`created_by`。

-   该表是业务归属和具体版本引用的唯一权威关系。
-   文件替换后旧链接和审核引用保留；新版本的业务提交创建新链接或按明确事务更新关联，但不得丢失旧证据链。
-   链接创建、业务结果提交和必要审计应在同一数据库事务中提交。
-   对同一业务对象、版本和角色设置防重复约束；具体唯一索引在物理 DDL
    设计时冻结。

#### `file_upload_session`：暂存阶段

只表达上传主体、目标业务上下文、暂存对象、验证结果、幂等键、有效期和提交结果定位。上传成功/验证成功不等于业务提交成功；暂存对象不出现在正式证据列表。

### 7.3 必须回写的地方

-   **E-06 §5.2：** 移除
    `file_object_id`、`business_type`、`business_id` 的重复真源定义。
-   **E-06 §5.3：** 明确版本表与 `file_object`
    的摘要真源；审核事实引用具体版本。
-   **E-06 §5.5：** 将 `business_file_link`
    从"可选替代方案"改为本项目统一方案。
-   **E-04/E-05：** 不直接保存文件物理路径或自行发明附件授权；通过 M11
    文件资产/版本/业务链接契约引用证据。
-   **E-07：** 备份清单以 `file_asset_version` 和 `file_object`
    的对应关系为基础；恢复时校验具体版本和业务链接，而非只核对文件数量。

## 8. M06/M07 的数据所有权边界

当前需要统一的是数据所有权，不应在本轮直接把所有状态枚举一次性冻结。

### 8.1 规范边界

-   `service_reservation.status` 是 M07 预约状态的唯一真源。
-   `work_order.status` 是 M06 工单/执行状态的唯一真源。
-   `reservation_execution_link` 只表示预约与工单的一对一关联，保留
    `reservation_id`、`work_order_id`、关联时间和必要终止原因。
-   建议移除 `reservation_execution_link.execution_status`
    作为独立状态字段。若为查询性能保留派生快照，必须明确它只是可重建的派生值，不能用于授权或状态裁决。
-   `reservation_id`
    唯一，保证一个预约最多关联一条执行工单；`work_order_id`
    唯一，保证一条工单不被多个预约重复关联。
-   预约取消、取消审批和服务中止申请各有自己的申请状态，不复用工单状态或
    SOS 的 `VOIDED`。
-   M06 接单必须与 M07
    当前预约状态及取消审批结果做原子校验；通知发送失败不回滚已提交业务状态。

### 8.2 尚待第二步完成的内容

以下不能由本数据模型文件单独冻结：

-   M06 工单完整状态枚举及迁移表；
-   M07 预约状态到工单执行状态的逐项映射；
-   `CANCELLED`、`REJECTED`、`SERVICE_STOPPED`、`COMPLETED` 与 SOS
    `VOIDED` 的边界用例；
-   M06/M07 并发接单、取消审批、中止审批的统一锁顺序与事务步骤；
-   对应 API 的 HTTP 状态码、错误码和返回字段。

第二步必须依据 SRS §5 与 E-05
的规则形成正式状态映射表；不能仅通过改名把不同语义的终态合并。

## 9. 全局锁顺序：本轮登记，第二步统一冻结

E-02、E-03、E-04 已各自给出局部锁顺序；E-05 的预约竞争流程使用"预约 →
预约执行关联 → 工单"的顺序。若跨模块事务不遵循统一顺序，存在死锁风险。

本轮不把未经全量事务路径验证的猜测直接写成最终锁表。第二步应完成：

1.  列出所有跨模块写事务：激活、换号、亲情冻结/解绑、档案停用/恢复、用药计划/打卡、体征接收/评估/告警、SOS
    建单、预约取消/接单/中止、文件提交、演示重置。
2.  为每个事务列出实际需要锁定的行、是否只读、锁定顺序和提交边界。
3.  统一公共实体与业务聚合根的顺序；同类型多行按主键升序。
4.  明确不需要锁定的对象不得为了"统一"无条件扩大锁范围。
5.  对需要跨档案与业务对象的事务，先按冻结顺序锁定档案/关系，再锁业务对象。
6.  将外部通知、短信、文件网络 IO 等放在事务外，通过
    outbox/补偿协议处理。
7.  通过 MySQL
    并发测试验证：取消与接单只成功一个、冻结/解绑与授权写入串行化、SOS
    原子创建、任务生成不重复、仿真停止不回滚已接受样本。
8.  死锁重试必须重新读取状态并重新校验权限、版本与审批条件；不能盲目重放旧
    SQL。

在锁顺序完成前，跨模块高风险写操作不应进入大规模编码。
