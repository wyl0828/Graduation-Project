## 1. 核心结论

项目当前的主要工作是完成需求基线的实际评审与批准，再将已批准需求落实为总体设计、模块设计、数据/API 契约和可执行测试。应按阶段和模块设置冻结门槛，不必等全部模块详细设计结束后才开始编码；但每个模块必须先满足自己的开工条件。

文档齐全、静态复核完成或设计稿写完，都不等于需求已正式冻结、功能已实现或测试已通过。未执行的验收必须继续标为“未测”。

### 建议的目录组织

以下是目标结构建议，不代表现在必须一次性创建全部空文件：

```text
docs/
├── requirements/   # SRS、冻结评审记录、变更记录、冻结前置清单
├── design/         # 总体设计、原型交互、数据库设计、modules/
├── api/            # 唯一权威 API 契约
├── testing/        # 测试计划/追踪、用例执行记录、缺陷与复测记录
├── deployment/     # 开发部署与备份恢复手册
└── project/        # 总体实施计划、项目状态与风险记录
```

冻结评审材料、差异处置台账和冻结前置清单暂时分别保留：它们分别承担批准记录、差异依据和门槛追踪职责。SRS 与总体设计也应分开；需求冻结记录不能与测试执行结果混写。

## 4. 模块详细设计与冻结标准

每份 M01—M12 设计应覆盖以下内容：

1. 模块目标与范围；
2. 角色、权限及数据边界；
3. 正常、边界和失败业务规则；
4. 状态、触发动作与合法迁移；
5. 数据字段、关系、约束、索引和历史保留；
6. API 请求、响应、错误、权限与幂等；
7. 事务边界、一致性和并发冲突；
8. 超时、重复请求、越权和数据冲突处理；
9. 可执行的正常、边界、异常、安全和并发用例；
10. 可观察、可复现的验收标准；
11. 跨模块调用方、依赖方和数据关系；
12. 与论文需求分析、设计、实现和测试章节的对应关系。

**模块开工前至少满足：** 相关业务规则已在 SRS 中有结论；核心权限、状态和失败语义明确；所需数据约束和接口契约已审查；关键验收场景已有可执行用例；依赖的 E 专项已达到设计关闭条件；开发环境和初始化数据可复现。模块设计冻结只说明设计可供实现，不代表代码完成或测试通过。

## 6. 阶段门槛与推荐推进顺序

1. **需求基线冻结：** 做最后复核并举行实际评审，填写批准版本、范围、评审人、日期和结论。静态复核不等于批准。
2. **总体设计确认：** 以批准后的 SRS 为准核对 v1.1 候选稿，处理剩余差异，确认模块边界、依赖和公共约束，再标明正式效力。
3. **逐模块设计与开工：** 建好模板/索引，按实际依赖完成模块详细设计、所需数据库/API、关键测试和专项方案；满足该模块门槛即可开工，不必等待所有模块。
4. **编码、测试与集成：** 按冻结设计实现；同步更新设计、迁移、接口、测试、缺陷和状态记录；真实执行模块及集成测试。
5. **系统验收与交付：** 执行适用的 AT-01—AT-41、A-01—A-06，留存部署、适老化、用户走查、性能、恢复等实际证据，再整理论文和答辩材料。

### 当前建议的下一步

1. 依据现有 SRS、冻结前置清单、差异台账和评审材料完成最后一轮冻结前复核，并准备实际 SRS 评审；未经批准不标记正式冻结。
2. 评审批准后，核对并确认总体设计 v1.1 候选稿的版本、生效条件及遗留项；不要重做已经有记录的静态对齐工作。
3. 建立模块设计模板和索引，优先按身份与数据关系等依赖推进 M01、M02，再扩展到核心业务模块；每个模块分别满足开工门槛后编码。

## 7. 开发期间的文档维护规则

- 需求变化记录原因、批准状态和受影响的 BR/FR/NFR、设计、API、数据库及测试；未批准规则不直接进入实现。
- 代码与设计不一致时先判断是实现偏差还是批准后的设计变更，再同步更新对应文档和迁移记录。
- 测试记录用例、需求、前置数据、步骤、预期/实际结果、证据位置、日期和结论；失败记录保留，修复后追加复测。
- 环境配置不记录真实密钥；使用虚构/合成测试数据，并把重置限制在获授权的隔离环境和明确范围内。
- 项目状态使用可区分标签，如未开始、进行中、待评审、已冻结、已实现、测试通过、失败或阻塞；设计完成不能写成实现完成。
- 文档与代码纳入版本控制，需求、API、数据库和测试记录能够追溯到对应版本。
