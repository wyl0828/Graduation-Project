## 1. 目标、范围与非目标

### 1.1 设计目标

1. 定义人工体征和仿真体征的可信来源边界、受控录入路径、字段校验及数据保留规则。
2. 保证体征保存、首次评估任务创建和规则版本固定具有可恢复的一致性；失败重试不更换已固定版本。
3. 将体征记录、健康告警、SOS 求助记录和服务工单建模为不同业务事实，避免状态混用。
4. 落实四类健康告警、固定 30 分钟合并锚点、乱序数据候选选择、告警状态权限和结案结果约束。
5. 保证 SOS 接受成功时，SOS 求助记录与唯一初始紧急工单原子建立；通知失败不回滚已接受求助。
6. 落实 S-01 仿真停止、排队取消、已开始单元原子写入、执行结果留痕及已接受样本继续处理的规则。
7. 为 AT-03/04/10/11/24/25/26/28/30 提供可执行测试入口和证据要求。

### 1.2 本专项负责

- 人工实时/历史体征接入、仿真体征接入、数据来源服务端定型和字段校验。
- 体征幂等、首次评估任务、规则版本固定、评估失败与安全重试。
- 告警类别判定、同类原因归并、活动告警合并、固定锚点与候选排序。
- 健康告警状态、处置权限、结案结果、审计及与普通工单的手动关联契约。
- SOS 接受、幂等、档案停用例外、SOS 与初始紧急工单原子创建。
- 仿真配置、执行单元排队/启动/停止、原子写入、执行结果及审计。
- 对 M11 通知、M06 工单、M12 审计的接口和事务边界约束。

### 1.3 本专项不负责

- 真实医疗设备接入、设备身份注册、设备认证、设备密钥、数据真实性证明或第三方设备协议。
- 医疗诊断、风险预测、药物建议或向用户声称“已诊断/已排除风险”。本期阈值仅用于演示和软件验收。
- 自动将健康告警转为普通工单；健康告警默认由社区核查，之后由本社区管理员手动创建普通工单。
- 用健康告警替代 SOS，或把 SOS 纳入健康告警的 30 分钟合并规则。
- 完整 M06 工单生命周期、M11 通用通知中心、M12 全部配置与审计能力；本专项仅定义所需交互契约。
- 生产级分布式消息平台、复杂微服务拆分或未经批准的业务事件。

## 3. 核心业务不变量

1. **来源可信边界：** 首期只接收人工登记与仿真数据。普通客户端提交 `DEVICE` 或类似标记不得生成可信设备数据；不提供真实设备接入入口。
2. **人工录入角色：** 仅本社区管理员可以录入人工体征，并明确选择“实时录入”或“历史录入”。服务端以受控路由/授权操作固定类别，不按时间差阈值推断。
3. **数据先校验后接受：** 不合法的体征不得写入正式体征记录、不得创建评估任务或健康告警；必须返回字段级校验反馈。
4. **体征与评估分离：** 体征被接受不代表评估成功。已接受体征的评估失败必须留有失败状态，恢复后沿固定规则版本安全重试。
5. **规则版本不可漂移：** 体征接受并创建首次评估任务时，原子固定唯一适用的规则版本。任何重试都不得读取重试时的最新版本覆盖原版本。
6. **历史与实时副作用不同：** 两者均可评估；历史录入不自动触发实时紧急通知或紧急上门工单。历史数据首次建立健康告警时，仅沿用 N-01 已批准的本社区管理员站内通知事件，不新增通知事件或收件角色。
7. **告警不是工单：** 健康告警默认由社区核查，不自动建普通工单。管理员核查后可手动建单；告警与工单分别维护状态、处理记录和结案结果。
8. **告警不被正常值自动关闭：** 后续正常体征独立保存，不自动改变或关闭已有活动告警。
9. **SOS 独立：** SOS 不参加健康告警合并。SOS 接受成功必须同时持久化 SOS 求助记录和一条初始紧急工单；同一请求重试不得重复建单。
10. **仿真停止不撤销已接受事实：** 停止后不启动新执行单元、取消未开始单元；已开始单元可完成当前原子写入。失败不得留下部分提交；已接受样本继续校验、评估与告警处理。
11. **状态冲突可见：** 同键同内容复用原结果；同键异内容返回 HTTP 409 并审计；并发状态操作只允许一个合法结果提交，不得最后写入覆盖。
12. **不夸大医疗含义：** 告警条件只用于首期软件演示与验收，不是医学正常范围、诊断结论或已验证的临床风险模型。

## 4. 架构与职责

本专项按现有 Spring Boot 单体、MySQL 8.0 的技术方向设计。评估任务和仿真任务可使用数据库持久化队列与 `@Scheduled` 工作器；不把 Kafka、RabbitMQ 或微服务作为开工前置条件。

| 组件 | 职责 | 约束 |
|---|---|---|
| `VitalIntakeService` | 受控人工/仿真体征入口、校验、来源定型 | 不信任客户端来源字段；正式保存前完成权限与档案状态检查 |
| `VitalValidationService` | 数值、单位、时间和字段关联校验 | 规则来自冻结 SRS；校验失败不产生正式体征或告警 |
| `RuleVersionService` | 查询和维护不可变告警规则版本 | 版本时间线无重叠；首次评估任务固定版本 |
| `AssessmentTaskService` | 创建、领取、执行和恢复评估任务 | 任务创建与体征接受/版本固定原子一致；重试沿用版本 |
| `HealthAssessmentWorker` | 按固定版本计算四类告警及触发依据 | 幂等；同类多原因归并；不得把正常结果作为告警关闭动作 |
| `AlertCorrelationService` | 查找可合并活动告警并确定唯一目标 | 固定锚点，不滚动窗口；按 G-16 的确定性排序 |
| `HealthAlertService` | 告警查询、开始处理、结案及关联普通工单入口 | 仅本社区管理员能改变状态或结案；默认不自动建单 |
| `SosService` | SOS 请求校验、幂等及初始紧急工单原子创建 | 不调用健康告警合并算法；不因通知失败回滚已接受 SOS |
| `SimulationControlService` | 仿真配置、启停、排队取消、执行单元状态 | 启停与执行领取通过同一数据库控制锁串行化 |
| `SimulationWorker` | 生成一条仿真样本并提交其原子业务输入 | 来源由服务端固定；每个执行单元独立记录结果 |
| `NotificationOutboxService` | 为批准的通知事件写入待发送记录 | 只写数据库，不在业务事务内调用外部网络 |
| `AuditService` | 记录规则、评估、告警、SOS、仿真和状态操作 | 不记录令牌、密码或无关完整健康信息 |

### 4.1 统一锁顺序

本节仅列 E-04 业务对象锁。共享锁前缀遵循集成设计基线 v1.1 §2.4：如采用维护门闩则先取门闩，其后先处理幂等记录，再按本节顺序锁业务对象；最终顺序仍须逐事务核验并进行真实数据库并发测试：

1. 老人档案行，按 `elder_id` 升序；
2. 需要授权关系校验时，亲情关系行按 `link_id` 升序；
3. 规则版本时间线的协调行（仅配置切换/首次版本固定所需）；
4. 体征/评估任务，按不可变主键升序；
5. 健康告警候选事件，按不可变 `alert_id` 升序；
6. 告警触发证据、逻辑通知 outbox 与审计记录。

SOS 建立事务先校验并锁定老人档案及身份状态，再按固定顺序创建 SOS 求助记录和初始紧急工单；它不获取健康告警合并锁。仿真控制行锁只用于执行单元领取或停止，不应在持有控制锁时等待外部网络或执行长时间评估。

## 5. 体征接入路径与字段校验

### 5.1 入口与来源固定

建议将受控录入路径体现为独立路由，避免依赖客户端可自由填写的 `entryMode`：

- `POST /api/v1/admin/elders/{elderId}/vitals/realtime`：本社区管理员人工实时录入；服务端固定 `entry_mode=REALTIME`、`source_type=MANUAL`。
- `POST /api/v1/admin/elders/{elderId}/vitals/history`：本社区管理员人工历史录入；服务端固定 `entry_mode=HISTORY`、`source_type=MANUAL`。
- 仿真入口只由管理员仿真控制/执行服务调用；服务端固定 `source_type=SIMULATION`、`entry_mode=REALTIME` 或由模拟场景配置中确定的受控路径，不允许普通客户端调用仿真内部接口。

上述路由为 API 设计建议；若后续统一成一个入口，服务端仍必须验证显式录入路径，并且由受控服务端上下文写入最终类别。禁止把客户端传入的 `DEVICE`、`REAL_DEVICE` 或类似值写成可信来源。本期不建设真实设备接入、认证或设备注册能力。

### 5.2 字段与范围

| 字段 | 规则 | 失败处理 |
|---|---|---|
| `systolic_mmhg` | 整数 50—300，含端点 | 字段校验失败，不保存正式体征 |
| `diastolic_mmhg` | 整数 30—200，含端点 | 字段校验失败，不保存正式体征 |
| `heart_rate_bpm` | 整数 20—250，含端点 | 字段校验失败，不保存正式体征 |
| 收缩压/舒张压关系 | 收缩压必须大于舒张压 | 字段/关联校验失败，不生成告警 |
| `collected_at` | 必须存在且不晚于服务端当前时间；允许合法历史时间 | 未来时间拒绝；不自动改成当前时间 |
| `entry_mode` | 服务端由受控路径固定为 `REALTIME` 或 `HISTORY` | 普通客户端字段不能覆盖服务端分类 |
| `source_type` | 服务端固定 `MANUAL` 或 `SIMULATION` | 客户端自报 `DEVICE` 不产生可信设备记录 |
| `elder_id` | 必须存在、归属当前社区，档案允许该操作 | 越权/停档拒绝；不静默丢弃 |
| 幂等键 | 对创建体征的写请求必需，通过 `Idempotency-Key` 请求头传入 | 缺失或格式非法返回明确错误 |

上述数值范围仅为软件技术接受范围，不是医学正常范围。所有业务时间以服务端权威时间为准，统一 `Asia/Shanghai`。客户端提供的采集时间可作为测量发生时间，但不能用来决定 `entry_mode`。

### 5.3 档案停用与纠错

- 档案停用后禁止普通新增体征，也不允许将停档前采集但从未入库的数据作为“历史纠错”补录。
- 已接受 SOS、既有健康告警和停档前已保存体征的异步评估继续处理；停档操作不得将这些记录删除或取消。
- 对已经存在的体征纠错必须走独立审计流程，填写原因，保留原始记录/修改前值、修改后值、操作者和时间；不得物理覆盖或删除原始证据。
- 纠错后的数据是否触发重新评估不由普通纠错接口隐式决定。本期默认纠错只新增更正审计事实，不静默重跑或关闭既有告警；如需重新评估，必须经批准的显式流程定义并保持规则版本、历史证据和告警语义可追踪。该技术边界需在 M03 详细设计评审时确认，不扩大已批准业务范围。

## 6. 首次评估任务与规则版本固定

### 6.1 版本时间线

规则版本为不可变快照，至少包含：

- `rule_version_id`、版本号、创建人、创建时间；
- 六项阈值、对应单位与比较方向；
- `effective_from`（含）与 `effective_to`（不含，可为空）；
- 配置变更原因、审计关联 ID 和版本状态。

规则版本只覆盖 SRS 已批准的四类告警及六项比较阈值，不增加新类别。版本区间应无重叠，并保证任意可接受体征在首次评估任务创建时可确定唯一版本。建议用一条规则时间线协调行串行化版本发布和首次版本固定，避免版本切换竞争。

**设计建议：** 规则配置修改通过事务创建新版本，生效时刻由服务端记录。SRS 要求“仅影响生效时间之后新建的首次评估任务”，但没有在业务层冻结未来预约生效的交互规则；本稿不擅自增加复杂的未来定时发布功能。默认方案是新版本在配置事务成功提交时生效；若产品后续要求预约未来生效，需单独明确并评审。

### 6.2 体征接受事务

在一个短数据库事务内完成：

1. 校验当前账号、社区权限、老人档案状态与受控录入路径；
2. 校验数值、时间和必填字段；
3. 从 `Idempotency-Key` 请求头读取键，规范化请求内容并按全局作用域校验幂等；
4. 锁定规则时间线协调行，按服务端接受时刻选出唯一生效版本；
5. 写入正式体征记录（固定来源、录入类别、采集时间、服务端接受时间）；
6. 创建唯一首次评估任务并保存固定 `rule_version_id`；
7. 保存幂等结果与必要审计信息；
8. 一次性提交。

如果规则版本不存在、版本时间线重叠或无法确定唯一版本，**不得接受一个没有固定规则版本的体征任务**。建议回滚本次正式接受事务并返回可识别的配置错误，同时写入独立的技术审计/告警；不返回一个貌似成功但不可评估的体征结果。此处是为落实 G-21 的一致性技术方案，不改变“评估失败时保留已接受体征”的规则：只有事务已成功接受并固定版本的体征，才进入可重试评估队列。

### 6.3 评估任务状态

| 状态 | 含义 | 允许迁移 |
|---|---|---|
| `PENDING` | 体征已接受，首次任务和规则版本已持久化，等待评估 | `RUNNING` |
| `RUNNING` | 工作器已领取，执行租约有效 | `SUCCEEDED`、`FAILED_RETRYABLE`、`FAILED_FINAL` |
| `FAILED_RETRYABLE` | 评估失败，保留错误类别并可重试 | `RUNNING` |
| `FAILED_FINAL` | 达到技术重试上限或发现不可自动恢复的确定性错误 | 经运维/管理员授权的修复重试流程后可重新进入队列；不得更改固定版本 |
| `SUCCEEDED` | 按固定版本完成评估并提交结果 | 终态；不得因后续正常体征而重算/关闭告警 |

`FAILED_FINAL` 的重试上限、退避间隔和人工重新入队权限属于工程参数，须在实现前登记并通过故障恢复测试，不属于新增业务规则。对于数据库暂时不可用、锁超时等可恢复异常采用有限指数退避；字段校验错误不进入评估重试，因为非法数据不应进入正式体征表。

### 6.4 评估结果提交

评估工作器以 `assessment_task_id` 作为幂等执行单位，在事务内：

1. 领取并校验任务仍可执行；
2. 读取体征记录和其固定规则版本，不查询“当前最新版本”替代；
3. 计算触发的告警类别及每类全部触发原因；
4. 对每个类别分别执行告警候选筛选与唯一目标选择；
5. 创建/合并告警和触发证据；
6. 若首次创建告警，按 N-01 生成面向本社区管理员的逻辑通知 outbox 记录；历史体征不创建实时紧急通知或紧急上门工单；
7. 标记评估任务成功并记录结果摘要；
8. 一次性提交。

如果事务失败，体征及首次评估任务仍保持已接受状态；本次告警和触发证据不得部分提交。重试沿用同一任务、同一规则版本、同一体征记录，并依唯一约束防止重复告警或重复触发证据。

## 7. 告警判定与合并算法

### 7.1 固定的四类告警

| 告警类别 | 触发条件 | 同类多原因处理 |
|---|---|---|
| 血压偏高 `BP_HIGH` | 收缩压 ≥160 mmHg 或舒张压 ≥100 mmHg | 同一测量两项均触发时，同一类别事件保留两项原因，不拆成两个事件 |
| 血压偏低 `BP_LOW` | 收缩压 ≤90 mmHg 或舒张压 ≤60 mmHg | 同一测量两项均触发时，同一类别事件保留两项原因，不拆成两个事件 |
| 心率偏高 `HR_HIGH` | 心率 ≥120 次/分钟 | 保留对应阈值与实际值 |
| 心率偏低 `HR_LOW` | 心率 ≤50 次/分钟 | 保留对应阈值与实际值 |

先完成 §5 的技术校验，再执行阈值判定。阈值等号触发。一个测量可以触发不同类别，必须分别建事件或关联各自类别的活动事件；不同类别不能合并成同一告警。以上规则仅用于首期软件演示和验收，不是医学诊断。

### 7.2 固定锚点与合并候选

对于某次体征的某一告警类别，只有同时满足以下条件的健康告警可以成为候选：

1. 同一老人；
2. 同一告警类别；
3. 同一固定规则版本；
4. 告警仍处于活动状态（待处理或处理中，不含已结案）；
5. `abs(vital.collected_at - alert.anchor_collected_at) <= 30 minutes`。

`anchor_collected_at` 固定为该告警首次触发体征的采集时间。后续合并不滚动、不重置锚点，也不因新触发记录改变首次创建时间。SOS 不参与该算法。

### 7.3 多候选确定性选择

若同一体征类别命中多个合格活动告警，按以下顺序只选择一个目标：

1. `abs(collected_at - anchor_collected_at)` 较小者优先；
2. 若相同，告警 `created_at` 较早者优先；
3. 若仍相同，不可变 `alert_id` 按升序优先。

若无合格目标，创建新告警。乱序体征不能改变上述选择规则；每个体征在每个告警类别下最多生成一条触发证据，不能因工作器重试或并发执行重复挂接。

### 7.4 并发实现建议

为避免两个工作器同时看见“无候选”并各自创建告警，建议在告警归并事务中先按集成基线锁序候选先锁老人档案行；具体 SQL 顺序仍须全局核对并通过并发测试，再查询候选并按 `alert_id` 升序锁定；事务内完成候选选择、创建/更新告警、写触发证据和标记评估任务结果。该方案以同一老人粒度串行化告警归并，适合本期演示系统；后续若实测锁竞争过高，可在不改变 G-16 业务规则的前提下优化。

建议数据库约束：

- `assessment_task_id` 唯一；
- `(assessment_task_id, alert_category)` 在触发证据表唯一；
- 触发证据关联的 `alert_id` 必须属于同老人、同类别、同规则版本；
- 告警的 `alert_id` 不可变；`anchor_collected_at` 创建后不可更新；
- 同一幂等请求不得产生第二条正式体征、评估结果或相同类别触发证据。

### 7.5 正常体征和已结案告警

- 正常体征独立保存；不自动改变或关闭已有活动告警。
- 已结案告警不参与活动合并；后续异常按规则创建新事件或匹配其他合格活动事件。
- 告警结案只表示社区核查流程结束，不表示医疗问题已解决。
- 历史录入仍可评估；如首次建立健康告警，仅沿 N-01 已批准的管理员站内通知事件供普通核查，不产生实时紧急通知或自动紧急上门工单。

## 8. 健康告警状态、权限与结案

### 8.1 状态机

| 当前状态 | 操作 | 操作者 | 新状态 | 约束 |
|---|---|---|---|---|
| `PENDING` 待处理 | 开始处理 | 本社区管理员 | `PROCESSING` 处理中 | 必须当前仍有权限，记录操作者和时间 |
| `PENDING` 待处理 | 直接结案 | 本社区管理员 | `CLOSED` 已结案 | 可无工单独立结案；结案结果必填 |
| `PROCESSING` 处理中 | 结案 | 本社区管理员 | `CLOSED` 已结案 | 结案结果必填 |
| `CLOSED` 已结案 | 再次开始处理/结案 | 任何业务角色 | 拒绝 | 已结案不重开；后续异常按新事件规则处理 |

网格员/护工可在授权范围内查看必要信息并提交核查事实，但不能改变健康告警状态或结案。本社区管理员可以从待处理直接结案，不要求额外二次审批。服务端必须校验社区归属和当前角色，不能只靠隐藏按钮。

### 8.2 结案结果契约

必须提交 `result_category` 与 `fact_summary`。允许分类沿用冻结 SRS：

- `CONTACTED_NO_NEW_SERVICE`：已联系核查、暂不需新增服务；
- `ONSITE_CHECK_COMPLETED`：已完成现场核查；
- `ORDINARY_WORK_ORDER_CREATED`：已创建普通服务工单；
- `CHECK_INCOMPLETE_FOLLOW_UP`：未能完成核查、已安排后续跟进；
- `OTHER`：其他。

附加规则：

- `CHECK_INCOMPLETE_FOLLOW_UP` 必须填写 `reason` 与 `follow_up_action`；
- `OTHER` 必须填写 `other_description`；
- 所有结案都必须有事实摘要，不能仅选择分类；
- 不得使用“已治愈”“医疗问题已解决”等未被系统证据支持的结论作为默认结果；
- 结案记录包含告警 ID、前后状态、分类、事实摘要、原因/后续措施（如适用）、操作者、服务端时间和审计关联 ID。

### 8.3 健康告警与普通工单

- 健康告警首次建立时不自动创建普通工单。
- 社区核查后，仅本社区管理员可手动创建关联普通服务工单。
- 同一创建请求必须幂等；重复请求返回原工单，不重复建单。
- 同一告警可以按合法的不同业务请求关联后续任务，但不能因一个请求重放重复创建。
- 工单结案不自动关闭告警；告警结案不自动取消或结案工单。
- SOS 初始紧急工单是独立的原子求助链路，不使用本节普通告警建单接口。

## 9. SOS 求助与初始紧急工单

### 9.1 接受条件

前端在老人首页检测到长按达到 2 秒后提交 SOS 请求；不足 2 秒松开不得发请求。服务端不能从普通 HTTP 请求本身证明用户真实按压了 2 秒，因此 UI 手势行为通过 AT-04 测试；服务端仍须验证登录身份、账号状态、老人身份关联、请求参数和幂等标识。

允许条件：

- 老人账号有效、身份已认证且请求对象归属该老人；
- 档案处于正常状态，或档案虽停用但老人账号仍有效且身份已认证（唯一窄范围 SOS 新业务例外）。

拒绝条件：

- 账号停用、认证无效、对象越权、幂等冲突或请求字段非法。
- 被拒绝时明确告知“未成功提交”，提供备用联系方式入口；不得静默丢弃。

### 9.2 原子创建

SOS 接受事务必须一次性提交以下业务事实：

1. SOS 事件记录（即 BR-05 所要求的 SOS 求助事件事实，与健康告警分离且不可物理删除）；
2. 唯一初始紧急服务工单，初始状态 `PENDING_DISPATCH`；
3. 二者的不可变关联；
4. 幂等请求结果；
5. 通知 outbox 记录及审计事件。

事务任一步失败，SOS 业务记录与初始工单均不得出现“半成功”。事务成功后，即使 HTTP 响应丢失，使用原幂等键重试也应返回同一 SOS 与同一工单。

通知由事务提交后的 M11 工作器异步发送；通知失败不能回滚已接受 SOS。客户端只有在收到服务端成功响应或通过同一幂等请求核实已提交结果后，才能展示“系统已接受”，不得展示“已到场”或“已救援完成”。超时但无法确定提交结果时，显示“未确认成功”，保留同键重试与备用联系方式。

### 9.3 SOS 与健康告警分离

- SOS 不参与 §7 的健康告警合并，不受健康告警的固定 30 分钟窗口影响。
- SOS 求助记录与健康告警记录采用独立业务主体、独立状态与独立审计；SOS 关联的初始紧急工单也不得伪装成普通健康告警自动转单。
- SOS 接受时通知本社区管理员属于 N-01 批准事件；老人端的受理反馈不依赖管理员通知发送成功。
- 档案停用时已接受 SOS 必须继续进入正常紧急调度；停档标记供管理员核查，不将其静默取消。

### 9.4 无效 SOS 管理终止

无效或误触 SOS 必须保留原始求助记录。只有本社区管理员可在关联紧急工单尚未进入 `PROCESSING` 前执行专门的管理终止操作，将工单状态置为 `VOIDED`，并记录原因、依据、操作者和时间；通知当前承接人。进入 `PROCESSING` 后禁止快捷 `VOIDED`，须现场核实并走正常审核。`VOIDED` 与正常完成 `CLOSED` 语义不同，不得物理删除 SOS 或复用预约取消状态。

## 10. API 契约草案

所有路径为本专项建议，须在统一 API 清单中复核后冻结。统一响应建议采用 `{code, message, data, traceId}`；错误响应不包含堆栈或敏感字段。

### 10.1 体征接入与查询

| 方法与路径 | 权限 | 请求要点 | 成功结果 | 关键错误 |

### 10.3 SOS 接受

`POST /api/v1/elder/sos-requests`

- **权限：** 老人本人已认证会话；服务端校验账号、老人对象归属和档案状态窄例外。
- **请求：** `Idempotency-Key` 请求头必填；正文可含用户端生成的非敏感请求上下文，但不能自报可信来源或替代身份验证。
- **成功：** `201`，返回 `sosEventId`（对应 `sos_event`）、`workOrderId`、`acceptedAt`、当前工单状态及可查询进度入口。
- **同键同内容：** 返回原 SOS 与工单结果，不重复建单。
- **同键异内容：** `409 IDEMPOTENCY_KEY_REUSED`，不覆盖原结果，并审计。
- **身份/账号拒绝：** 明确返回拒绝原因和备用联系方式提示，不创建 SOS/工单。
- **事务失败：** 不得存在 SOS/工单半成功；响应不泄露内部堆栈。

### 10.4 规则配置

建议提供 `GET /api/v1/admin/health-alert-rule-versions` 与 `POST /api/v1/admin/health-alert-rule-versions`。写接口仅允许具有规则配置权限的本社区管理员；请求必须包含变更原因及已批准四类告警的六项阈值。服务端校验阈值关系、范围和版本时间线，不接受新增告警类别。配置成功后返回不可变版本 ID、生效时间及审计 ID；旧版本保留。具体参数可配置范围和阈值关系检查应在 M12 规则配置设计中一并冻结。

| `PUT /api/v1/admin/simulation/config` | 本社区管理员 | 校验频率和场景配置；非法配置拒绝且旧配置继续生效 |
| `POST /api/v1/admin/simulation/start` | 本社区管理员 | 开启后允许后续执行单元领取；记录操作者、时间和配置版本 |
| `POST /api/v1/admin/simulation/stop` | 本社区管理员 | 原子置为停止、取消未开始排队单元；返回已开始单元数量及状态提示 |
| `GET /api/v1/admin/simulation/runs` | 本社区管理员 | 查询执行单元、样本、结果、失败原因和审计关联 |

仿真内部执行入口不对普通客户端开放。仿真样本必须使用与人工输入相同的校验、评估和告警链路，来源标记由服务端固定。

## 11. 逻辑数据模型与约束

以下是逻辑模型建议，不代表最终物理表数已冻结。

### 11.1 核心实体

| 实体 | 主要字段 | 关键约束 |
|---|---|---|
| `vital_record` | `vital_id`、`elder_id`、`source_type`、`entry_mode`、数值、`collected_at`、`accepted_at`、`idempotency_record_id`、`simulation_run_unit_id`（可空） | 正式接受后不可物理删除；来源与录入类别由服务端固定 |
| `idempotency_record` | `principal_scope`、`operation_scope`、`idempotency_key`、`canonical_hash`、`result_type`、`result_id`、`created_at` | `(principal_scope, operation_scope, idempotency_key)` 逻辑唯一；同键异内容冲突；字段与匿名安全上下文映射由 D2 冻结 |
| `alert_rule_version` | 版本 ID、六项阈值、`effective_from`、`effective_to`、操作者、原因、审计 ID | 版本不可变；有效时间区间不重叠；首次任务固定版本 |
| `assessment_task` | `task_id`、`vital_id`、固定 `rule_version_id`、状态、尝试次数、租约、失败类别、创建/完成时间 | `vital_id` 唯一（本期每条接受体征一项首次评估任务）；失败重试沿固定版本 |

| `alert_trigger_evidence` | `evidence_id`、`alert_id`、`assessment_task_id`、体征 ID、触发原因列表/快照、采集时间 | `(assessment_task_id, alert_category)` 唯一；证据不覆盖 |
| `alert_action_log` | 告警 ID、前后状态、动作、操作者、时间、原因、结案结果及审计 ID | 状态改变与动作记录同事务提交 |
| `sos_event` | SOS ID、老人 ID、接受时间、停档标记、幂等记录引用、身份校验结果摘要 | 作为 BR-05 的 SOS 事件事实，与健康告警分离；原始求助记录保留；同一请求不产生第二条记录 |
| `simulation_control` | 控制 ID、启停标志、配置版本、代次、更新时间、操作者 | 启停与领取执行单元通过同一控制行锁串行化 |
| `simulation_run_unit` | 单元 ID、配置版本、场景、状态、排队/开始/结束时间、样本 ID、结果、失败原因 | 每单元独立状态；一个单元至多产生一条被接受的样本 |
| `notification_event` | 事件 ID、策略范围、来源对象、事件类型/阶段、唯一去重键、创建时间 | 每个业务逻辑事件只创建一次；业务事务内提交 |
| `notification_delivery` | 投递 ID、事件 ID、目标、渠道、状态、租约、授权复核时间、发送结果 | 按事件/目标/渠道去重；每次发送或重试前复核当前授权；外发失败不回滚业务 |
| `audit_log` | 事件 ID、主体、操作、对象类型/ID、结果、时间、必要前后值摘要、trace ID | 业务用户不可编辑；不记录凭证或无关完整健康信息 |

### 11.2 索引与唯一性建议

- `vital_record(elder_id, collected_at DESC)`：支持老人时间线查询；具体 MySQL 索引语法在 DDL 阶段确定。
- `assessment_task(status, next_attempt_at, task_id)`：支持待评估任务领取。
- `health_alert(elder_id, category, rule_version_id, status, anchor_collected_at)`：支持候选检索。
- `alert_trigger_evidence(assessment_task_id, alert_category)` 唯一，阻止同任务同类别重复挂接。
- `sos_event` 的幂等关联唯一，`work_order` 中 SOS 来源关联唯一，确保每个 SOS 事件至多一条初始紧急工单。
- `simulation_run_unit` 的唯一单元 ID 与样本关联唯一，防止重放执行单元产生重复样本。
- 规则时间线不能只依赖普通唯一索引保证区间不重叠；必须在事务锁和服务层约束中校验。

## 12. 事务、幂等、并发与失败语义

### 12.1 体征接收事务

**原子范围：** 幂等记录（处理中/结果）、体征记录、首次评估任务及固定规则版本、必要审计事实。任何一步失败则不提交正式体征接受结果。规则版本无法唯一确定时拒绝本次接受，不产生“成功但无法评估”的体征。

异步评估与接受事务分离。接受事务成功后评估失败，体征仍保留，评估任务记录失败状态；评估重试不重写体征，不变更固定规则版本。

### 12.2 评估结果事务

一次事务内提交告警创建/合并、触发证据、首次告警逻辑通知 outbox 及评估任务成功状态。事务失败则告警和触发证据不部分落库，评估任务进入可重试状态。通知网络发送在事务提交后执行。

### 12.3 幂等键规范

- 创建体征、SOS、手动建单和会改变告警状态的命令均使用 `Idempotency-Key` 请求头；正文不另设同义幂等字段。
- 规范化内容需包含业务对象 ID、数值/字段、录入路径或操作类型等会影响结果的字段；排除无业务意义的 JSON 字段顺序差异。
- 同键同规范化内容返回已持久化的原业务结果/当前可追踪状态，不重复创建。
- 同键异内容返回 `409 IDEMPOTENCY_KEY_REUSED`，不覆盖原结果、不创建第二个对象，并记录最小必要审计信息。
- 不同真实 SOS 必须使用新键；不能按时间邻近自动合并。

### 12.4 告警合并竞争

告警评估的合并查询和提交必须在同一事务中完成。按集成基线锁序候选先锁老人档案行；具体 SQL 顺序仍须全局核对并通过并发测试，使同一老人相关评估的候选选择串行化；之后锁定候选告警并按 `alert_id` 升序。事务重新验证告警状态、类别、规则版本和固定锚点，再按 G-16 排序。并发失败方重试后重新读取已提交状态，不能复用过时候选快照。

### 12.5 SOS 与工单原子性

SOS 事件记录（BR-05 所要求的 SOS 求助事件事实）、初始紧急工单、关联、幂等结果和通知 outbox 在同一数据库事务提交。通知失败只更新 outbox 投递状态，不回滚 SOS/工单。工单创建失败时，SOS 业务接受事务整体回滚；客户端必须通过原幂等键确认结果，不得自行生成新键盲目重试。

### 12.6 仿真执行单元停止协议

采用持久化控制行和执行单元表，不依赖单个 JVM 的内存布尔值：

1. 工作器领取单元时锁定 `simulation_control`，仅在启用状态下将一个排队单元原子变为 `RUNNING`，写入 `started_at` 与配置版本，然后提交。**领取事务提交时定义为“已开始”。**
2. 停止操作锁定同一控制行，将启用状态置为停止，并在事务中将所有尚未开始的排队单元标记为取消，写停止审计后提交。
3. 停止事务提交后，任何新的领取事务都必须看到停止状态，不得开始新单元。
4. 在停止提交前已成功领取的单元属于已开始单元，可继续完成当前原子写入；不在原子事务内执行网络请求或长时间评估。
5. 单元的样本写入、来源标记、幂等结果及首次评估任务应在同一原子事务中提交。失败则回滚该单元的部分业务写入，并在独立可用事务中记录 `FAILED` 与原因。
6. 已成功接受的样本在停止后仍进入正常评估与告警流程；停止不撤销样本、评估任务、告警或已生成通知记录。
7. 页面明确提示“已停止后续仿真，当前执行中的样本可能完成”。

### 12.7 事务外操作

禁止在持有档案、告警或仿真控制锁时调用外部通知服务、文件服务或执行长时间计算。外部通知通过 outbox 工作器执行；业务提交后通知失败可重试，不能回滚已接受 SOS、体征或告警。所有重试需可追踪且不得重复创建逻辑事件。

## 13. 仿真配置与停止语义（S-01）

### 13.1 配置校验

管理员可启停仿真、配置频率和选择正常/异常样例。配置变更须校验允许范围；非法配置拒绝，旧配置继续生效。每次成功配置记录配置版本、操作者、时间和变更内容。样例名称使用“模拟超阈值”等描述，不宣称医疗诊断。

频率上下限、最大排队数量、单元超时和重试次数未由 SRS 固定，作为工程参数在实现前登记并通过 AT-10/性能测试确认；不得把建议值写成已批准业务规则。仿真数据全部为虚构/合成数据。

### 13.2 执行单元状态

| 状态 | 含义 | 允许迁移 |
|---|---|---|
| `QUEUED` | 已排队但尚未开始 | `RUNNING`、`CANCELLED` |
| `RUNNING` | 领取事务已提交，单元已开始 | `SUCCEEDED`、`FAILED` |
| `SUCCEEDED` | 样本与首次评估任务已原子接受 | 终态；评估任务继续独立运行 |
| `FAILED` | 当前原子写入失败，未留下部分业务样本 | 终态，记录失败原因；重试策略按批准工程参数执行 |
| `CANCELLED` | 停止时尚未开始，已取消 | 终态；不得创建样本 |

如果仿真单元已原子接受样本但后续异步评估失败，该单元仍可为 `SUCCEEDED`，评估任务则独立为 `FAILED_RETRYABLE` 等状态；不得混淆“样本接受”和“评估完成”。

### 13.3 重启与审计

应用进程重启后：

- 未开始的排队单元是否继续执行，取决于当前持久化启停状态；若已停止则不得恢复领取。
- 已开始但未结束的单元应按持久化结果核实是否已提交原子样本；若已提交，不重复写入；若未提交且能确定事务回滚，可按设计的恢复策略记录失败或安全重新入队，必须依单元幂等键防止重复样本。
- 停止动作、排队取消、已开始单元完成/失败、来源标记和失败原因均可追溯。
- 不允许将停止操作解释为回滚已接受样本。

上述重启时对“已领取但进程突然崩溃”的精确租约和恢复策略为技术实现参数，须在编码前明确并以故障注入测试验证，不得改变 S-01 的业务不变量。

### 14.2 审计字段

至少记录：事件 ID、操作者/系统工作器身份、操作类型、业务对象 ID、前后状态、服务端时间、结果、失败类别、请求 trace ID、幂等记录 ID、关联规则版本及必要原因。规则修改记录前后配置摘要；体征纠错保留原始证据；告警结案保留分类和事实摘要；SOS 终止保留原因、依据、操作者和时间；仿真记录启停操作与各单元结果。

审计不得记录密码、会话令牌、激活码明文或无关完整健康信息。一般技术日志使用 ID 与错误类别定位，不输出完整体征内容或敏感个人资料。

### 14.3 安全失败反馈

- `400 VALIDATION_FAILED`：字段/阈值配置校验失败，返回字段级错误，不保存正式业务对象。
- `401 AUTHENTICATION_REQUIRED`：未登录或会话失效。
- `403 ACCESS_DENIED`：角色、社区、档案状态或对象权限不允许。
- `404 RESOURCE_NOT_FOUND`：资源不存在，且对无权用户不泄露对象存在性。
- `409 STATE_CONFLICT`：状态已变化或并发竞争失败；客户端应刷新状态，不得盲目覆盖。
- `409 IDEMPOTENCY_KEY_REUSED`：同键异内容；要求新操作使用新键，不能把原键用于不同业务事实。
- `503 RULE_VERSION_UNAVAILABLE`：不能确定唯一生效规则版本；不得接受无版本评估的正式体征。
- `500/503 INTERNAL_FAILURE`：统一错误消息与 trace ID；不暴露堆栈。是否已提交未知时，客户端使用原幂等键查询/重放确认结果。

## 15. 故障场景与恢复策略

| 故障场景 | 必须保留的事实 | 恢复动作 | 禁止行为 |
|---|---|---|---|
| 体征字段校验失败 | 请求失败审计（最小必要） | 返回字段级错误，修正后使用新请求键 | 保存正式体征、创建告警 |
| 规则版本不存在/时间线重叠 | 配置异常审计 | 拒绝本次接受，修复规则时间线后重试新请求 | 接受无版本体征、猜测使用最新版本 |
| 体征事务提交前失败 | 无正式体征/评估任务半成品 | 使用原幂等键核实并安全重试 | 创建孤立评估任务 |
| 评估工作器崩溃 | 已接受体征、固定版本和任务 | 根据任务状态/租约重新领取，幂等重试 | 改用当前最新规则版本 |
| 告警合并事务失败 | 不产生部分触发证据或半成告警 | 重试相同评估任务，重新按 G-16 选择 | 重复告警、滚动锚点 |
| 告警并发结案 | 单一合法状态和对应审计 | 失败方返回 409，刷新告警详情 | 最后写入覆盖已提交结案结果 |
| SOS 工单写入失败 | 不存在半成功 SOS/工单 | 整个接受事务回滚；同键重试核实 | 保留 SOS 却无初始紧急工单 |
| SOS 响应丢失 | 数据库提交结果可按幂等键查询 | 同键重放/查询 | 新建新键导致重复求助 |
| 通知发送失败 | 已接受 SOS/告警及 outbox 记录 | M11 按策略重试并在发送前复核权限 | 回滚 SOS、增加矩阵外通知 |
| 仿真停止与领取竞争 | 以控制行事务先后为准 | 停止后取消未开始单元，允许已开始单元完成当前原子写入 | 停止提交后仍启动新单元 |
| 仿真原子写入失败 | 执行失败结果及原因 | 回滚本单元部分业务写入，记录 `FAILED` | 留下体征但缺评估任务/来源标记 |
| 停止后已有样本评估失败 | 已接受样本与固定版本 | 按评估任务恢复流程继续重试 | 因停止仿真撤销样本或告警 |
