## 1. 本轮目标与结论

本轮统一三类跨模块契约：

1.  **API 契约：** 路径前缀、响应结构、追踪标识、幂等键、版本冲突和 HTTP
    错误语义。
2.  **状态机契约：**
    每个业务对象只有一个状态真源；预约、工单、告警、SOS、申请、文件、通知、重置作业及备份/恢复作业不能混用终态。
3.  **数据库并发契约：** 定义跨模块锁顺序、请求入口如何取得目标
    ID、事务边界、外部 IO 与事务的分离、死锁重试条件。

核心结论：

-   所有 HTTP API 统一使用 `/api/v1` 前缀；E-01
    中未显式写前缀的认证路径也必须加上此前缀。
-   JSON 成功/错误响应统一包含
    `code`、`message`、`data`、`traceId`；E-05 的 `requestId` 改为
    `traceId`，`currentState` 等安全可见的冲突详情放入 `data`。
-   数据库字段使用 `trace_id`，API 字段使用 `traceId`；不得混用
    `requestId`、`request_id` 作为同义追踪字段。
-   所有会创建业务事实、推进业务状态或触发副作用的命令接口必须支持幂等；统一使用
    `Idempotency-Key` 请求头和请求内容摘要。查询接口不需要幂等键。
-   所有可变业务聚合根使用 `expectedVersion`
    做乐观并发校验；过期版本不能被静默覆盖。
-   对象级无权限访问统一使用 `404 RESOURCE_NOT_FOUND_OR_NOT_ACCESSIBLE`
    以避免对象枚举；已知可访问对象上的角色/动作不允许，返回
    `403 ACTION_NOT_ALLOWED`。
-   全局锁顺序采用固定的资源等级；只锁事务实际需要的行，并按主键升序。事务从业务请求
    ID 开始时，先以普通只读查询定位关联
    ID，再按全局顺序加锁，禁止"先锁子记录、再反向锁聚合根"。
-   `service_reservation.status`、`work_order.status`、`health_alert.status`、`sos_event`
    的生命周期和取消/中止申请状态相互独立。`CLOSED`、`CANCELLED`、`REJECTED`、`VOIDED`、`SERVICE_STOPPED`
    不能互相替代。

## 2. 统一 API 契约

### 2.1 路径、命名和编码

  ------------------------------------------------------------------------------------------------------------------------------
  项目                                统一规则
  ----------------------------------- ------------------------------------------------------------------------------------------
  API 根前缀                          `/api/v1`

  路径命名                            kebab-case 资源名；路径参数可用 `{elderId}`、`{requestId}` 等 camelCase

  JSON 字段                           camelCase，例如 `traceId`、`expectedVersion`、`elderId`

  数据库字段                          snake_case，例如 `trace_id`、`expected_version`、`elder_id`

  请求/响应编码                       UTF-8 JSON

  时间瞬间                            ISO-8601，必须携带时区；建议响应使用 UTC `Z`

  业务自然日                          `YYYY-MM-DD`，按 `Asia/Shanghai` 解释

  追踪字段                            API `traceId`，数据库 `trace_id`

  版本字段                            统一 `expectedVersion`；不再另用 `expectedRequestVersion`、`expected_version` 作为 JSON
                                      请求字段

  幂等键                              HTTP 请求头 `Idempotency-Key`；不把同义键重复放进 JSON body

  不可信输入                          用户、角色、社区、对象状态、文件路径、可信来源、当前承接人等不得由客户端自报作为授权依据
  ------------------------------------------------------------------------------------------------------------------------------

E-01 原接口清单中的 `/auth/login`、`/admin/users/...`
等路径，实际落地时均补齐 `/api/v1` 前缀，例如
`POST /api/v1/auth/login`。E-02---E-07 已有 `/api/v1`
的路径继续保留，不因统一契约而改变业务语义。

### 2.2 统一成功响应

``` json
{
  "code": "OK",
  "message": "操作成功",
  "data": {
    "resourceId": "业务资源标识"
  },
  "traceId": "服务端生成的请求追踪标识"
}
```

约束：

-   `code` 为稳定机器可读编码；成功固定为 `OK`。
-   `message` 为用户可理解的提示，不作为客户端分支判断依据。
-   `data` 保存业务结果；无业务返回内容时为 `null`。
-   `traceId` 由服务端生成并贯穿
    API、业务日志、通知投递、审计和作业记录。
-   建议同时在响应头返回 `X-Trace-Id`，其值与 JSON 的 `traceId` 相同。
-   HTTP 状态码与业务 `code` 必须语义一致，不得一律返回 200 再依赖 JSON
    判断失败。

### 2.3 统一错误响应

``` json
{
  "code": "RESERVATION_STATE_CONFLICT",
  "message": "预约状态已发生变化，请刷新后重试",
  "data": {
    "currentState": "CANCELLED",
    "currentVersion": 4
  },
  "traceId": "服务端生成的请求追踪标识"
}
```

约束：

-   `data` 可为 `null`；只有调用者有权查看时才返回
    `currentState`、版本、字段错误等安全详情。
-   E-05 的 `requestId` 不再作为响应追踪字段；如需返回业务申请 ID，放在
    `data.requestId`，不得与 `traceId` 混淆。
-   不返回 SQL、Java 堆栈、内部文件路径、密码哈希、验证码、激活码、会话
    token、服务商凭据或其他社区的对象信息。
-   未知异常统一转为 `500 INTERNAL_ERROR`，返回 `traceId`
    供定位；不得把原始异常文本直接返回客户端。
-   业务失败必须有稳定 `code`；禁止仅依赖中文 `message` 或 HTTP 500
    表达所有失败。

### 2.4 HTTP 状态码约定

  -------------------------------------------------------------------------------------------------------------------------------------------------------
                            HTTP 使用场景                                                     统一规则
  ------------------------------ ------------------------------------------------------------ -----------------------------------------------------------
                        `200 OK` 查询成功、已有资源的状态命令成功                             返回统一成功 envelope

                   `201 Created` 创建业务资源成功                                             `data` 返回新资源 ID/编号和必要初始状态

                  `202 Accepted` 已创建受控异步作业，作业尚未完成                             例如演示重置作业；返回 `jobId` 和初始状态，不宣称作业已成功

               `400 Bad Request` JSON/字段结构错误、缺字段、格式错误                          使用 `VALIDATION_ERROR` 或具体字段校验码

              `401 Unauthorized` 未登录、会话过期/撤销、登录凭据不正确                        认证失败；登录入口使用通用凭据错误，避免泄露账号是否存在

                 `403 Forbidden` 已识别且可安全暴露的资源上，当前角色/动作不允许              使用 `ACTION_NOT_ALLOWED` 或明确的权限错误码

                 `404 Not Found` 资源不存在，或对象级权限不足且需防枚举                       使用 `RESOURCE_NOT_FOUND_OR_NOT_ACCESSIBLE`

                  `409 Conflict` 状态/版本冲突、唯一约束冲突、重复活动业务、幂等键复用        使用具体领域错误码

         `413 Content Too Large` 上传内容超出限制                                             `FILE_TOO_LARGE`

    `415 Unsupported Media Type` 实际文件格式不允许                                           `FILE_TYPE_NOT_ALLOWED`

     `422 Unprocessable Content` 结构合法但不符合业务规则，例如预约时间窗口、激活码验证失败   使用具体业务错误码

         `429 Too Many Requests` 登录冷却、验证码/激活码/敏感操作限流                         返回可安全展示的冷却信息，不泄露账号状态

     `500 Internal Server Error` 未预期服务端错误                                             `INTERNAL_ERROR`，不暴露内部异常

       `503 Service Unavailable` 必需依赖不可用、规则版本不可确定、有限重试耗尽               返回明确可重试/需人工处理语义；客户端不得盲目生成新幂等键
  -------------------------------------------------------------------------------------------------------------------------------------------------------

`403` 与 `404` 的区分规则：

-   如果用户对某个已知且可展示的操作没有角色资格，返回 `403`。
-   如果通过某个对象 ID
    查询、修改或读取文件时，用户不在对象授权范围内，为防止枚举，返回
    `404 RESOURCE_NOT_FOUND_OR_NOT_ACCESSIBLE`。
-   不得因统一错误码改变 SRS 已批准的拒绝结果或泄露范围。

### 2.5 幂等键契约

#### 统一请求头

所有创建业务事实、状态迁移、审批、文件业务提交、SOS、预约、打卡、档案更正、重置作业创建/执行等命令接口必须使用：

``` http
Idempotency-Key: <客户端为本次用户意图生成的唯一值>
```

查询 `GET`
不需要幂等键。普通文件内容传输、验证码校验等是否单独使用上传会话 ID/挑战
ID，必须在对应接口表中明确；不能因此产生第二套不同的幂等语义。

#### 键作用域

幂等记录逻辑上至少按以下组合隔离：

`principal_scope + operation_scope + Idempotency-Key`

其中 `principal_scope` 为认证主体，或由服务端从一次性票据/安全挑战中识别的匿名安全上下文；客户端不能任意指定该范围。`operation_scope` 由 HTTP 方法与版本化规范路由模板组成，规范化请求摘要还须覆盖会改变业务结果的路径标识和请求内容。

同时保存规范化请求摘要、处理状态、原业务资源定位、原 HTTP
状态码和可重放响应所需的最小数据。

#### 重放规则

  --------------------------------------------------------------------------------------------------------
  情况                                   结果
  -------------------------------------- -----------------------------------------------------------------
  同键、同规范化请求内容、原请求已完成   返回原业务结果；不创建第二条业务事实

  同键、同内容、原请求正在执行           返回明确处理中状态/资源定位，或按接口约定等待；不能并行重复执行

  同键、不同规范化请求内容               `409 IDEMPOTENCY_KEY_REUSED`；不覆盖旧记录、不创建新业务对象

  客户端网络超时、不知道是否成功         用原键重放或查询结果；不得直接生成新键盲目重试

  不同真实用户意图                       必须生成新键；不能仅按时间接近合并真实 SOS 或业务事件
  --------------------------------------------------------------------------------------------------------

建议使用统一 `idempotency_record`
逻辑契约。物理实现是否全部单表化由数据库设计决定，但所有模块的作用域、摘要和重放语义必须一致。幂等键不能代替领域唯一约束，例如
`UNIQUE(task_id)`、预约时段唯一性或一个预约最多关联一个执行工单。

### 2.6 版本与并发冲突

-   所有有并发覆盖风险的修改请求使用 `expectedVersion`。
-   服务端在事务中重新读取当前版本，并执行条件更新。
-   更新影响行数不是 1 时，不继续执行后续状态、审计、通知或文件副作用。
-   版本冲突返回 `409` 及对应领域错误码，安全范围内可返回
    `currentVersion`/`currentState`。
-   `expectedVersion`
    是技术并发保护，不代表客户端有权操作该资源；权限仍须在提交前重新校验。
-   不得把幂等重放和版本冲突混为一谈：同键同请求重放返回原结果；新键但旧版本操作返回状态/版本冲突。

### 2.7 分页与列表响应

列表 API 统一采用：

``` json
{
  "code": "OK",
  "message": "查询成功",
  "data": {
    "items": [],
    "page": 1,
    "pageSize": 20,
    "total": 0
  },
  "traceId": "服务端生成的请求追踪标识"
}
```

-   `page` 从 1 开始，`pageSize` 有服务端上限；默认值和上限在全局 API
    清单统一配置。
-   `total=0`
    只表示成功查询后没有符合条件的记录；查询失败不得伪装成空列表或 0。
-   所有列表都在服务端按当前用户、角色、社区、老人对象、亲情授权和文件关联范围过滤；不能先返回跨社区数据再由前端筛选。

## 4. 全局数据库锁顺序

### 4.1 原则

1.  仅锁定当前事务实际需要的行，不为了"全局统一"扩大锁范围。
2.  多模块事务按本节的资源等级由低到高获取锁；同一资源类型的多行按主键升序。
3.  从子资源 ID（例如
    `requestId`、`taskId`、`workOrderId`、`uploadId`）进入的接口，可先通过普通只读查询定位其聚合根
    ID；获得锁后必须重新读取并验证全部关键条件。
4.  不允许在已锁定较高等级资源后，再反向获取较低等级资源的排他锁。
5.  外部短信/通知发送、文件网络
    IO、长时间计算不得在持有业务行锁的事务中执行。
6.  事务中任何关键条件必须在加锁后重新验证；前置的普通查询只用于定位，不能作为最终授权或状态判断。
7.  审计/outbox 在业务事务中只追加必要记录；通知投递工作器不得持有
    outbox 行锁再反向锁业务聚合根。
8.  数据库唯一约束与条件更新是最终防线；Java `synchronized`
    或前端按钮禁用不能替代跨线程/多实例的数据库一致性控制。

### 4.3 锁顺序的使用规则

-   **只读定位不等于加锁：** 例如先
    `SELECT reservation_id, elder_id FROM reservation_cancel_request WHERE id=?`，该查询用于定位。真正写事务开始后仍须按全局顺序锁
    `elder_profile`（如该流程确实需要）、`elder_family_link`（如需要授权关系锁）、`service_reservation`、取消申请、执行关联、工单，并重新验证。
-   **从工单入口也不能反向锁预约：**
    若工单关联预约，先通过非锁定查询定位预约 ID；随后按预约 →
    取消/中止申请（需要时）→ 执行关联 →
    工单的顺序加锁。若没有预约关联（普通工单或 SOS
    工单），只锁实际需要的工单/相关 SOS 资源。
-   **档案停用：**
    档案先锁定；检查未结工单/交接时按较高等级锁相关工单并重新验证。不得先锁工单再锁档案。
-   **档案/关系授权写入：**
    若业务事务需要在提交前持有当前亲情关系锁，必须先锁档案，再锁关系，再锁申请/业务对象。若只是读取授权，不需要排他锁的地方可以普通读取，但必须根据
    SRS 规则在提交前可靠复核。
-   **用药打卡：**
    先锁老人档案，再锁当日任务，之后处理打卡记录；若事务不涉及子女授权，不额外锁
    `elder_family_link`。
-   **告警评估：** 先按 E-02
    规则锁老人档案，再按评估任务/候选告警等级处理；多个候选告警按
    `alert_id` 升序，重新验证状态、类别、规则版本和固定锚点。
-   **预约取消与接单：** 两个事务都按预约 → 取消/中止申请（如需）→
    执行关联 →
    工单顺序；取消与接单必须在同一数据库事务内条件更新，只有一方能成功。
-   **文件业务提交：**
    如果结果属于工单，先锁业务工单，再锁上传会话、资产、物理对象元数据、版本和业务关联。不能先锁上传会话再反向锁工单。
-   **演示重置：**
    先取得环境维护门闩排他锁，再冻结重置清单和作业状态，然后按全局资源顺序处理目标对象；不允许任意
    SQL 或不受限级联删除。
-   **备份：**
    如选择暂停写入的一致性窗口，先取得同一维护门闩排他锁，等待既有写事务结束后再形成数据库/文件一致性点；完成备份校验后恢复写入。若采用其他一致性机制，须通过实际并发测试证明数据库与文件引用不会错配。

### 4.4 仿真控制的独立短事务

E-04 的 `simulation_control` 与执行单元领取应使用短事务：

1.  领取事务只锁 `simulation_control`
    和相应排队执行单元，验证启用状态，写入
    `RUNNING`、开始时间与配置版本并提交。
2.  停止事务只锁
    `simulation_control`，把启用状态设为停止并取消尚未开始的排队单元后提交。
3.  已领取单元的业务写入在独立事务中执行，按本节全局业务资源顺序锁档案、体征、评估任务等。
4.  **禁止在持有 `simulation_control` 锁时再锁老人档案或业务实体。**
    领取提交即视为已开始；停止提交后不得再领取新单元，已开始单元可按 SRS
    规定完成当前原子操作。
5.  停止不回滚已接受体征、评估任务、告警、SOS 或已生成的通知逻辑事件。

该隔离规则避免把仿真控制行变成所有业务事务的长期全局锁。

### 4.5 事务外操作

以下动作必须在业务数据库事务提交后执行，或先写入 outbox/job
再由工作器执行：

-   短信、站内通知实际发送；
-   文件上传/下载、对象存储移动、缩略图生成、外部存储删除；
-   长时间评估计算、耗时外部请求；
-   备份文件复制与恢复过程中的大文件 IO；
-   其他不能由 MySQL 同一事务回滚的副作用。

工作器模式统一为：**领取/租约事务提交 → 在事务外执行 IO →
短事务记录结果。** 对需每次投递前复核授权的通知，不能持有
`notification_delivery`
行锁再去锁低等级授权资源；应先提交领取租约，再在独立事务中复核当前授权，然后执行发送，最后更新投递结果。

### 4.6 死锁与锁等待重试

-   只允许对明确可恢复的数据库死锁/锁等待错误做有限的整事务重试。
-   推荐初始实现最多重试 2 次（共最多 3
    次事务尝试），使用短随机退避；这是工程建议参数，不是 SRS 冻结值。
-   每次重试必须从事务起点重新开始，重新读取状态、权限、对象版本、审批条件、当前分配与幂等结果；不能只重放上一次
    SQL。
-   如果状态已由竞争方提交，返回对应领域状态冲突或原幂等结果；不得覆盖成功方。
-   外部 IO
    不得在事务内执行，因此重试不会重复发送外部消息或重复写入外部文件。
-   达到重试上限后返回 `503 INTERNAL_RETRY_EXHAUSTED`，并记录
    `trace_id`、错误类别、尝试次数和必要诊断信息；不向客户端返回原始数据库异常。
-   任何重试都不得放宽 SRS 的权限、状态、时段、授权有效性或审批条件。

`CONFIRMED` 是预约侧状态；`PENDING_DISPATCH` 是工单侧状态。两者不能塞入同一字段，也不应仅通过状态名称转换来实现。预约确认、M06 初始 `PENDING_DISPATCH` 工单及唯一执行关联必须同事务提交；任一步失败整体回滚。不得异步补建，也不得留下已确认但无执行关联的预约。

#### 预约取消申请与服务中止申请

  -----------------------------------------------------------------------------------------------------------------
  申请类型                状态                    迁移与结果
  ----------------------- ----------------------- -----------------------------------------------------------------
  取消申请                `PENDING_REVIEW` →      仅在预约仍有效且执行未接单时批准；预约进入 `CANCELLED`
                          `APPROVED`              必须同事务完成

  取消申请                `PENDING_REVIEW` →      原因必填；预约保持原有效状态；通知申请人
                          `REJECTED`              

  服务中止申请            `PENDING_REVIEW` →      仅允许规则规定的已接单/执行中路径；预约与工单中止终态同事务提交
                          `APPROVED`              

  服务中止申请            `PENDING_REVIEW` →      工单保留原合法状态；原因和审核历史保留；通知申请人
                          `REJECTED`              
  -----------------------------------------------------------------------------------------------------------------

取消与接单竞争的唯一裁决：

-   取消事务先成功：预约 `CANCELLED`，后续接单必须失败。
-   接单事务先成功：不得再批准普通取消；必须走独立服务中止流程。
-   两个请求都不能成功，也不能出现预约已取消但工单已接单的部分状态。

#### 未接单执行记录的技术终止状态

如果取消预约时已经生成了 M06 执行记录但尚未接单，E-05 提出的
`TERMINATED_PRE_ACCEPTANCE` 可作为技术候选状态。它不是 SRS
单独冻结的枚举，必须在 M06
设计中明确批准/采用后才可写入代码。若取消时尚未生成工单，则不需要创建一条工单再将其终止。

### 6.6 文件生命周期与演示重置

#### 文件

  ---------------------------------------------------------------------------------------------------------
  状态                        含义/允许迁移                      约束
  --------------------------- ---------------------------------- ------------------------------------------
  `UPLOAD_INITIATED`          上传意图创建                       尚不是文件证据

  `STAGED`                    内容进入非公开暂存区               不对业务证据列表可见

  `VALIDATING`                校验中                             不可作为有效证据

  `VALIDATED`                 格式、大小、摘要、可读性校验通过   仅说明文件有效，不等于业务提交成功

  `ATTACHED_PENDING_COMMIT`   等待业务结果事务提交               仍不可对外显示为已提交证据

  `ACTIVE`                    业务关联已提交、可按权限访问       作为有效证据仍需业务状态/权限检查

ACID。业务关联与结果提交应在数据库同一事务内完成；事务外文件操作使用可恢复作业/补偿状态。

#### 演示重置作业

`REQUESTED → PREPARED → RUNNING → DB_APPLIED → FILES_RECONCILED → VERIFYING → SUCCEEDED`

异常终态/中间状态：

-   `REJECTED`：环境、权限、范围或一致性检查失败。
-   `PARTIAL_FAILURE`：部分步骤成功、部分失败；不得宣称成功。
-   `FAILED_NEEDS_RECOVERY`：不能自动安全恢复，需人工处置。
-   `CANCELLED_BEFORE_START`：任何破坏性步骤前经授权取消。

`RUNNING`
之后不能假定"取消作业"会自动回滚数据库与文件。必须根据检查点、安全清单、保留范围和审计记录进行受控恢复。重置仅允许隔离开发/测试/演示环境中明确标记的虚构/合成数据。

### 6.7 通知、备份与恢复作业

#### 通知逻辑事件与投递

-   `notification_event` 记录业务逻辑事件；`notification_delivery`
    记录逐接收目标投递。
-   业务状态、逻辑事件和必要投递任务在同一数据库事务中提交。
-   投递状态建议：`PENDING`、`SENDING`（租约中）、`RETRY_WAIT`、`SENT`、`SKIPPED`、`FAILED`。
-   `SENT` 只表示发送通道接受，不表示用户已读。
-   N-01 的事件和接收角色严格按 SRS 白名单；FZ-02 换号安全通知单独使用
    `policy_scope=FZ02_SECURITY`，不得扩展 N-01。
-   每次实际发送/重试前复核当前授权；无有效收件人、失权、失败和跳过均需留痕；通知失败不回滚已提交业务状态。

#### 联合备份作业

备份状态建议：`REQUESTED → PRECHECKING → QUIESCING → CAPTURING_DATABASE → CAPTURING_FILES → CAPTURING_CONFIG → VERIFYING → VALIDATED`；失败为
`FAILED` 或 `PARTIAL_FAILURE`。

只有 `VALIDATED` 的备份集可用于正式恢复演练。每日保留最近 7
份已验证每日备份；新备份未验证前不淘汰旧有效备份。重大变更前备份单独标识。

#### 联合恢复作业

恢复状态建议：`REQUESTED → PRECHECKING → PREPARED → RESTORING_DATABASE → DATABASE_RESTORED → RESTORING_FILES → FILES_RESTORED → VERIFYING_REFERENCES → VERIFYING_APPLICATION → SUCCEEDED`。

失败为 `REJECTED`、`PARTIAL_FAILURE` 或
`FAILED_NEEDS_RECOVERY`。数据库恢复成功但文件/关联/权限验证失败，整体不能标记成功。RPO
≤ 24 小时、RTO ≤ 4 小时须实际演练测量，不能由配置或文档宣称。

## 8. API 清单需要固定的字段

以下是所有写 API 的公共字段规则，不替代各业务端点自己的业务参数。

  --------------------------------------------------------------------------------------------------------------
  字段/机制                           规则
  ----------------------------------- --------------------------------------------------------------------------
  `traceId`                           由服务端生成，响应返回；数据库统一存 `trace_id`

  `Idempotency-Key`                   对命令接口通过请求头传入；数据库保存摘要/作用域，不记录不必要明文

  `expectedVersion`                   对可变聚合根更新/审批/状态迁移使用；服务器必须在事务中校验

  `reason`                            业务要求原因的动作必须服务端校验非空；具体原因码/说明按业务接口定义

  `actorUserId` / `roleCode` /        由服务端认证上下文解析，不接受客户端作为可信授权输入
  `communityId`                       

  `status`                            只在响应中返回当前业务对象状态；普通资料编辑接口不接受客户端任意设置状态

  `createdAt` / `updatedAt`           ISO-8601 带时区；服务端时间权威

  `currentState` / `currentVersion`   仅在调用者有权查看的冲突响应中返回，放在 `data` 内

  `fieldErrors`                       只返回字段名与可理解的校验原因，不包含 SQL、内部堆栈或敏感值

  `communityId` 范围                  必须由服务端按当前角色/对象权限判定；不能只信任查询参数
  --------------------------------------------------------------------------------------------------------------

## 9. 并发状态操作的统一裁决表

  -----------------------------------------------------------------------------------------------------------------------------------------------------------------
  并发场景                          唯一合法裁决                                                                   失败方反馈
  --------------------------------- ------------------------------------------------------------------------------ ------------------------------------------------
  同一激活 ticket 被并发使用        最多一个激活事务成功；ticket 消费、身份关联、角色和审计原子提交                已使用/原幂等结果/状态冲突；不重复关联

  同一手机号被两个账号并发换入      数据库唯一约束只允许一个成功                                                   `409 PHONE_ALREADY_IN_USE`

  亲情关系冻结/解绑与授权写入竞争   提交前按统一档案/关系锁顺序复核；只有满足最终提交条件的写入成功                授权失效冲突，不得沿用旧权限

  档案停用与普通新业务创建竞争      两者按档案锁顺序串行化；停用成功后普通新业务被拒；停用前已提交的合法业务保留   明确状态冲突，不出现停用后仍新建普通业务

  两个不同请求并发打卡同一任务      唯一打卡约束只允许一条有效记录                                                 `409 TASK_ALREADY_CONFIRMED` 或按幂等返回原结果

  两个评估任务并发合并同一告警      档案行/告警候选锁定和条件更新保证单一合并结果；按不可变告警 ID 顺序            重试方重新读取后合并到既有结果或创建合法新事件

  同一真实 SOS 被网络重放           相同幂等键返回原 SOS/工单；不重复建单                                          原结果/处理中状态

  不同真实 SOS 请求                 视为不同用户意图，必须使用不同幂等键，不按时间邻近自动合并                     各自独立业务记录

  预约确认与原申请人取消并发        只有一个状态迁移成功                                                           `RESERVATION_STATE_CONFLICT` 或原幂等结果

  预约取消审批与接单并发            取消先成功则拒绝接单；接单先成功则拒绝普通取消并转独立中止流程                 `EXECUTION_ALREADY_ACCEPTED` /
                                                                                                                   `RESERVATION_STATE_CONFLICT`

  两个管理员同时审批同一申请        申请行版本/状态条件更新保证只有一个终态成功                                    已处理原结果或对应申请终态冲突

  工单处理结果与文件替换并发        文件版本和工单状态按固定顺序校验；只接受明确版本的证据                         `FILE_VERSION_CONFLICT` / 工单状态冲突

  文件对象损坏与审核结案竞争        结案前验证必需证据状态；缺失/隔离文件不得作为有效证据通过                      `FILE_NOT_AVAILABLE`，不伪报审核成功

  仿真停止与工作器领取并发          控制行决定唯一先后；停止提交后不能领取新单元；已开始单元可完成当前原子操作     返回停止状态与已开始单元数

  演示重置与业务写入并发            维护门闩/等效机制阻止范围漂移；重置期间拒绝或等待新写入                        明确维护中状态；不部分重置后继续对外提供服务

  备份与业务写入并发                使用已验证的一致性窗口/快照协议；数据库与文件清单对应同一一致性点              备份标记失败，不把不一致集合标记 `VALIDATED`
  -----------------------------------------------------------------------------------------------------------------------------------------------------------------
