# 社区管理员工账号与角色管理 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 为每个社区提供经授权的工作人员账号与角色管理闭环，并使护工仅能查看和处理本人当前承接的工单。

**Architecture:** 后端从当前有效 `COMMUNITY_ADMIN` 会话派生社区范围，以事务创建账号、角色、审计并撤销受影响账号的全部会话。`CARE_WORKER` 复用工单执行工作台，但授权以当前社区和当前承接人双重约束，绝不加入网格员的社区级读取范围。管理端提供员工/角色页面，使用现有 Web Cookie、CSRF 和 API 客户端。

**Tech Stack:** Java 17、Spring Boot 3.5、MyBatis-Plus、MySQL/Flyway、JUnit 5/Mockito；Vue 3、TypeScript、Vue Router、Element Plus；PowerShell 临时 MySQL/HTTP 验收。

**Spec:** `docs/superpowers/specs/2026-10-26-社区管理员工账号与角色管理设计.md`；当前权威要求：`docs/current/需求与范围.md` FR-M01-04/07、FR-M06-01、FR-M12-03 与 AT-17。

## Global Constraints

- 管理员只能操作当前会话所属社区；请求体不得指定社区、授权人或账号类型。
- 工作人员初始密码由管理员设置，至少 8 个字符；仅保存安全哈希，密码不得写入响应、审计或日志。
- 可分配角色为 `COMMUNITY_ADMIN`、`GRID_WORKER`、`CARE_WORKER`。管理员可与一种工作人员角色有条件兼任；拒绝 `GRID_WORKER + CARE_WORKER`、家庭角色/工作人员混用、运维角色和未知角色。
- `CARE_WORKER` 只能访问本人、当前社区内、当前有效分配的工单与执行所需字段；不可访问社区老人列表、看板、全社区健康/档案数据或已改派工单。
- 角色变更在事务中保留分配历史、记录审计并撤销目标用户所有现有会话，原因为 `ROLE_CHANGED`；撤销后重新授予也不得使旧 token 复活。
- 拒绝撤销本社区最后一个有效管理员；失败事务不得留下孤立账号、部分角色或成功审计。
- 所有写入/联调只使用脚本创建的随机 loopback MySQL 和合成数据；短信/激活/找回不在本计划范围。
- 不访问 `.env.local`，不修改原有用户数据，不提交或推送；不使用 `git add .`。

## Review Focus

1. 管理员伪造其他社区 ID 或修改跨社区员工：返回拒绝且员工/角色/会话/审计事实不变。**Task 1、4**。
2. 家庭账号、未知角色、网格员与护工并存、过短密码：在写入前拒绝。**Task 1、4**。
3. 角色修改后目标账号的 Web 与 MINIAPP 旧会话均 401；重新授予后旧 token 仍 401。**Task 1、4**。
4. 护工查询未分配、被改派、跨社区工单或社区列表/看板：无数据泄露、无副作用。**Task 2、4**。
5. 创建/角色变更事务失败、审计记录和初始密码：没有半提交、明文秘密或虚假 UI 成功。**Task 1、3、4**。
