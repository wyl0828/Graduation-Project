# 社区管理员工账号与角色管理设计

## 意图

为满足 FR-M01-04、FR-M01-07、FR-M12-03 与 AT-17，社区管理员需要在本社区工作台内创建工作人员账号、分配或撤销工作人员角色，并能查到谁在何时执行了变更。角色变化必须立即生效，撤销目标账号的全部旧会话，使其重新登录后只能使用仍有效的角色。

用户已选择完整闭环：管理员页面、受限 API 与审计一起交付。当前代码只有 `/api/v1/auth/switch-role`，只能切换账号已有角色；没有员工列表、工作人员创建或角色分配入口。数据库已有 `sys_user`、`sys_user_role`、`auth_session`、`audit_log`。管理端目前没有员工页面，只允许 `COMMUNITY_ADMIN` 与 `GRID_WORKER` 进入。

## 目标

- 社区管理员可查看当前社区工作人员、创建工作人员账号，并显式分配、调整、撤销工作人员角色。
- 每次请求从服务端当前会话取得管理员和社区范围；客户端不能指定或覆盖 `community_id`、授权人或目标社区。
- 角色组合和账号类型按现行第 3.1 节与 FR-M01-07 检查；家庭身份不得与工作人员角色并存，运维身份不进入业务分配流程。
- 创建、分配、撤销与旧会话撤销在同一数据库事务中完成；保留已撤销分配记录和可追溯审计，不把密码写入审计、日志或响应。
- 角色变更后目标账号的所有现有会话立即失效；后续登录和角色切换只能读取当前有效分配。

## 非目标

- 手机短信邀请、手机号核验、子女注册、老人首次激活和找回/换号路径；这些依当前执行计划仍保持关闭或未测。
- 通过员工页面手动创建 `ELDER` 或 `CHILD` 权限；家庭身份继续由激活、注册及亲情关系流程建立。
- 运维账号、底层数据库用户、跨社区迁移和完整工作人员账号恢复流程。
- 建设与角色管理无关的社区成员审批或复杂特权审批平台。

## 现状与约束

- `sys_user_role` 记录角色、社区、授权人及撤销信息；员工角色必须限定到社区。
- 当前账号体系把老人和子女均保存为 `FAMILY`，`ELDER` 由激活流程授予，`CHILD` 由注册流程授予。员工管理 API 不得把家庭账号升级为 `STAFF`。
- 工作人员由本社区管理员创建；密码至少 8 字符并安全哈希存储。当前密码恢复、会话与角色上下文已有服务实现。
- 允许“老人 + 子女”；“网格员/护工 + 社区管理员”按实际岗位有条件允许并禁止自审；家庭与工作人员角色不能兼任；运维身份不能并入业务角色。
- 当前 `CARE_WORKER` 仅出现在需求/数据库枚举中，业务控制器、执行服务和管理端没有对应运行路径。用户已确认本批一并接入最小受限工单执行流程；它只能查看和操作明确分配给自己的工单及执行所需信息，不能继承网格员的社区级读取范围。
- 不读取工作区 `.env.local`；集成写入和角色组合验收仅使用脚本创建的隔离 MySQL 与合成数据。未经用户明确要求不提交、不推送。

## 方案比较

| 方案 | 做法 | 取舍 |
| --- | --- | --- |
| 受限 API + 审计 | 增加仅本社区管理员可调用的创建/角色管理 API；通过隔离 HTTP 验收，不增加 UI | 范围较小，但管理者不能从产品界面操作，不满足用户选择的完整管理闭环 |
| 管理端纵向闭环（已选） | 增加工作人员管理 API、事务审计、旧会话撤销、管理端页面，并补上 `CARE_WORKER` 的本人分配工单执行路径 | 一次完成真实使用入口和服务器保护；比只做角色登记范围更大，但保留护工只处理本人分配工作的授权边界 |

## 提议的交互与接口

管理页面放在管理工作台的“工作人员与角色”入口，只对当前 `COMMUNITY_ADMIN` 显示。页面列出本社区工作人员（手机号脱敏、当前有效角色、状态），提供“创建工作人员”和“调整角色”操作。修改前说明会立即退出目标账号的已有会话；撤销操作要求填写原因。创建表单包括手机号、初始密码及角色选择。初始密码由管理员设置、长度不少于 8；服务端只存 BCrypt 哈希，响应仅返回账号 ID 和已分配角色。管理员通过系统外的受控方式把初始密码交给员工；员工之后使用现有改密流程。表单不把初始密码写入 localStorage、URL、审计或运行日志。用户已确认 `CARE_WORKER` 在本批可分配，并进入仅限本人分配工单的工作台路径。

建议 API：

- `GET /api/v1/admin/staff`：只列出当前管理员所属社区的工作人员。
- `POST /api/v1/admin/staff`：创建 `STAFF` 账号并按请求分配允许的角色。
- `PUT /api/v1/admin/staff/{userId}/roles`：替换目标账号在当前社区的工作人员角色集合；允许空集合以明确撤销该社区角色，账号记录保留。

创建/更新请求不接受 `communityId`、`grantedBy`、`accountKind` 或任意角色代码。服务端从当前有效管理员会话派生范围，并拒绝跨社区目标、未知角色、家庭角色混用、重复分配及矩阵不允许的组合。允许单独分配 `COMMUNITY_ADMIN`、`GRID_WORKER` 或 `CARE_WORKER`；只有社区岗位需要时允许管理员与一种工作人员角色兼任；当前需求未确认 `GRID_WORKER + CARE_WORKER` 组合，故拒绝该组合。保留撤销分配行并填入撤销时间、操作者和原因。可将 API path 和 DTO 命名留给实施者，但授权约束不能放宽。

`CARE_WORKER` 使用执行工作台，但其后端列表、详情、接单、开始、提交结果和文件证据均要求当前用户是对应工单的有效承接人；不得把护工加入社区老人列表、全社区统计或与执行无关的健康/档案入口。派单可将工作分配给当前社区中带有效 `CARE_WORKER` 的账号。

```mermaid
flowchart LR
  Admin[本社区管理员] --> UI[工作人员与角色页面]
  UI --> API[员工管理 API]
  API --> Scope[校验当前会话与本社区范围]
  Scope --> Tx[事务内写账号/角色/会话撤销/审计]
  Tx --> Result[返回角色摘要并提示重新登录]
```

## 事务与审计

- 创建时验证手机号唯一、密码长度、账号类型与允许角色；账号、角色记录和成功审计同事务提交。
- 角色替换时锁定或以事务/版本机制保护目标角色集合；保留历史分配，更新/插入当前角色，并撤销目标用户的全部会话，原因标记为 `ROLE_CHANGED`。
- 校验失败或数据库失败不得留下半个账号、部分角色或成功审计。审计至少包含操作者、目标用户、社区、动作、变更前后角色摘要、结果和时间，不包含明文密码、完整令牌或不必要的手机号。
- 若变更后操作者自己失去管理角色，服务端仍完成事务并返回结果；管理端清除本地会话状态并转到登录页。
- 设计选择：拒绝移除社区唯一的有效管理员角色，防止社区失去可管理账号；只有另有管理员仍有效时才允许撤销最后一个管理员。

## 验收

- HTTP：匿名和非管理员不能读取/创建/调整员工；跨社区管理员不能读写目标；正常管理员可读取和创建当前社区工作人员。
- 角色矩阵：覆盖 `GRID_WORKER`、`CARE_WORKER`、`COMMUNITY_ADMIN` 单角色，以及条件允许的管理员+一种工作人员组合；验证家庭/工作人员混用、管理员+网格员+护工、运维角色和未知角色拒绝；不明确的组合不得由实现者自行扩大。
- 护工授权：本人被派单后可读取和处理该工单及执行所需证据；未分配、已改派或跨社区工单均不可读写；护工不能查询社区档案列表或社区看板。
- 副作用：失败创建/角色调整前后核对 `sys_user`、`sys_user_role`、`auth_session`、`audit_log` 与相关业务事实；不能留下孤立账号、半更新或虚假成功审计。
- 会话：修改目标角色后，目标用户所有现有 Web 与小程序 token 返回 401；新登录读取最新角色；旧 token 不得因后来重新授予某角色而复活。
- 审计：成功创建、授予、撤销能查询到对应审计摘要；拒绝请求不写角色变更成功审计。
- UI：管理员可用员工页面创建及调整角色；网格员/其他业务角色不能通过直接 URL 进入；API 错误时页面保留表单并显示明确失败，不能显示成功或清空输入。
- 实际联调仅针对临时 MySQL 与合成账号；短信、真机和生产账号路径继续未测。

## 实施边界待定

1. 初始密码采用管理员设置并线下交付（本设计提议）；若需求方要求员工自助设置，则需另有不依赖未启用短信服务的受控首登通道。
2. `CARE_WORKER` 受限工单路径已由用户确认纳入本批，不得复用网格员的社区级数据读取授权。
3. 唯一管理员保护是基于可恢复管理能力的实现选择，现行需求没有明确这一限制；如保留，应在 UI 解释为什么无法撤销最后一个社区管理员。

## 批准后交付的实现计划

获批后先写服务/API/数据库集成测试，再实现事务服务和受限 API；然后接入最小管理页面与路由守卫。通过隔离 HTTP 测试验证权限、组合、审计、会话撤销和失败副作用，再运行前端相关验证。具体文件和测试命令在获批后按仓库当前结构确定。
