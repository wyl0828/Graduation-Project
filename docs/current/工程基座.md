## 4. 仓库和目录方案

D1 初始化在当前项目根目录 `D:\Graduation Project` 使用单一 Git 仓库；保留已有 `README.md`、`docs/`，并建立源码和运行目录：

```text
D:\Graduation Project\
├── README.md
├── pom.xml                      # Maven reactor root
├── .editorconfig
├── .gitattributes
├── .gitignore
├── .env.example
├── .mvn\wrapper\                 # Maven Wrapper
├── apps\
│   ├── elder-family\             # Uni-app + Vue 3：老人端/子女端
│   └── admin-web\                # Vue 3 + Element Plus + ECharts
├── services\
│   └── api\                       # Spring Boot 单体分层后端
│       └── src\main\resources\db\migration\  # Flyway 版本迁移
├── database\
│   └── seed\                      # 仅含虚构/合成开发数据
├── ops\
│   └── windows\                   # PowerShell 初始化、检查和启动脚本
├── docs\                          # 已有设计基线、追踪与项目文档
└── .local-data\                   # 本机上传文件/临时运行数据，Git 忽略
```

不创建嵌套 Git 仓库。`.local-data/` 和 `.env.local` 不入库；`docs/` 与源码共享同一个版本历史。

## 5. 数据库初始化与迁移

1. 通过本机 MySQL 服务建立独立的演示数据库和最小权限应用账号；数据库名、端口和账号从本地环境变量读取。
2. 首次启动时由 Flyway 从空库执行 `services/api/src/main/resources/db/migration/` 中的有序 SQL 迁移，记录版本和校验值。
3. 已执行的迁移只追加新版本，不直接改写；需要修复时新增迁移脚本并留下变更说明。
4. `database/seed/` 只放虚构/合成的演示初始化数据，和结构迁移分开；重置脚本必须显式指定开发库名并再次确认目标环境。
5. 数据库使用 `utf8mb4`；业务时区遵从总体基线 `Asia/Shanghai`。连接地址、端口、库名和凭据均可配置。

在**新建的本机隔离演示环境**中，先以本机 MySQL 管理员核对目标库和账号均不存在，再执行以下建库授权；将独立生成的强密码只写入被忽略的 `.env.local`，不写进命令行参数或仓库文件。此演示账号需要在应用启动时运行 Flyway，因此 DDL 权限仅限定在演示库；后续环境可拆分迁移账号和运行账号。

```sql
CREATE DATABASE `elderly_care_demo` CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
CREATE USER 'elderly_app'@'127.0.0.1' IDENTIFIED BY '<本机独立强密码>';
GRANT SELECT, INSERT, UPDATE, DELETE, CREATE, ALTER, DROP, INDEX, REFERENCES
  ON `elderly_care_demo`.* TO 'elderly_app'@'127.0.0.1';
```

执行 `./ops/windows/check-demo-db.ps1` 检查连接和目标库；后端首次启动迁移后再加 `-RequireMigration` 核验 Flyway 历史。脚本拒绝非本机主机、其他库名和 root 运行账号，也不会输出密码。当前 V1 迁移只检验流水线，不创建业务表。

## 6. 配置、文件和启动

- `.env.example` 只提供变量名和非敏感示例；`.env.local`、真实数据库凭据和本机路径加入 `.gitignore`。
- Spring 配置通过 `application-local.yml` 读取环境变量，不在已提交文件写入密码、令牌或个人数据。
- 上传文件写入配置项 `APP_STORAGE_ROOT` 指向的 `.local-data/files/`；数据库只保存文件元数据、校验值和业务关联。仓库源码不承载上传文件。
- Windows 初始化脚本负责检查 JDK/Node/npm/Git/MySQL 版本、建立本地数据目录、提示必需配置，并在缺项时明确报错；不得自动覆盖已有数据库。
- 启动方式：后端用 `./ops/windows/start-api.ps1`；两个前端分别执行 `npm ci` 后按各自 README 运行或构建。相对 `APP_STORAGE_ROOT` 由启动脚本解析到仓库根目录，避免 Maven 子模块工作目录造成路径漂移。
- 小程序首期目标为微信。Uni-app 使用 DCloud `uni` CLI 工作流；目前无微信 AppID，因此 D1 只验证 `mp-weixin` 编译和 H5 本机预览，不将开发者工具或真机测试写成已通过。

## 7. D1 验收门槛

代码仓库建立后，D1 只有满足以下条件才算完成并允许进入共享支撑模块开发：

1. 新克隆目录中可通过仓库脚本核对 Git、JDK、Node、npm、Maven Wrapper 和 MySQL 版本；脚本不依赖开发者个人绝对路径。
2. 按 `.env.example` 建立本地配置后，脚本可检测 MySQL 服务和目标库；不得输出数据库密码。
3. 空白演示库可从头完成 Flyway migration；再次启动不会重复建表，`flyway validate` 通过。
4. 当前 V1 只有 Flyway 历史表，没有业务表，故**没有可初始化的业务种子数据**。D1 验证目标库检查脚本会拒绝其他库；首个业务模块的 D2/G1 必须补合成种子和安全重置步骤，不能把本项写成已执行的业务重置。
5. 后端可启动并通过健康检查；两个前端均可安装锁定依赖并启动/构建。
6. 文件目录在首次启动时创建，相对路径以仓库根目录为准；可在忽略目录中完成合成文件写读及 SHA-256 校验且不进入 Git。数据库文件元数据/业务关联属于 M11 的 D2/G1，尚无相关物理表或上传接口，不以 D1 占位验证冒充完成。
7. 干净环境初始化步骤、实际版本和失败处置已写入文档；初始化验证有命令输出或截图留证。
8. 对集成基线中的维护门闩或覆盖全部写入口的等效方案作出 D1 工程决策；决策记录不等于锁序已通过并发验证。

这些是 D1 验收标准和两个明确的业务表前置项。实际通过状态以带命令、环境、版本和结果的验收记录判断；骨架构建不能代替数据库连接、应用运行或前端构建。

## 8. D1 后的推进顺序

1. 完成 D1 方案核对，处理 MySQL 8.0.34 的本地环境边界并确认独立演示库参数。
2. 已开始按本方案在项目根目录初始化单仓库和工程骨架；此阶段不写业务模块。
3. 实现最小环境检查、配置模板、Flyway 空库迁移入口和本地启动说明，并执行 D1 验收。
4. D1 通过后建立共享支撑：统一认证上下文、API 错误与追踪、幂等服务、审计和通知 outbox。
5. 补齐 M06 普通工单专项后，按既定依赖顺序推进模块设计、实现和验收。

## 11. D1 维护门闩工程决定（2026-10-25）

本机演示环境采用 **MySQL 单例维护门闩**。后续 D2 建立 `environment_maintenance_gate` 单行表；普通业务写事务先对该行取得兼容的共享锁，再按[跨模块设计](./跨模块设计.md)的全局顺序锁定领域数据。演示重置和需要数据库、文件保持同一静默窗口的备份操作取得该行排他锁。后台调度、通知 outbox、文件关联和管理员入口也必须纳入全部写入口清单，不能绕过门闩。

此处只是 D1 **机制选型**：单行表、SQL、事务范围及失败释放规则在 D2/D3 落地；每个写入口的覆盖、并发等待、超时和回滚须在 G2/G3 实测。未完成这些验证前，不得声称锁顺序或备份一致性已经通过。演示重置仍须先检查目标库名和文件根目录的真实路径。
