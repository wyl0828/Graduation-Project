> **现行工作文档。** 本文件依据 [需求与范围说明书 (SRS)](./需求与范围.md)、[跨模块设计基线](./跨模块设计.md) 及系统全部业务 Controller、DTO 源码编制。

## 1. 契约约定与全局规范

### 1.1 通信协议与路由规范
* **协议与基础路径**：所有业务 API 统一使用 HTTPS（本地开发支持 HTTP），路由强制采用 `/api/v1` 前缀。
* **数据格式**：请求体与响应体默认统一采用 `application/json;charset=UTF-8`。
* **时间与时区标准**：
  * 时间戳瞬间采用 ISO-8601 格式带时区（如 `2026-10-27T14:30:00+08:00`）；
  * 业务日期采用 `YYYY-MM-DD`（如 `2026-10-27`），业务时钟统一固定为 `Asia/Shanghai`。
* **文件上传**：工单履约凭据采用 `multipart/form-data`，只允许 JPEG/PNG；扩展名、声明 MIME 与实际图片格式必须一致，单张不超过 5 MiB、每次提交最多引用 5 张。

### 1.2 统一响应报文结构（`Result<T>`）

#### (1) 通用成功响应（HTTP 200）
```json
{
  "code": "OK",
  "message": "操作成功",
  "traceId": "trace-4a9b-8f1c-20261027143000",
  "data": { ... }
}
```

#### (2) 通用分页列表响应（`PageResult<T>`）
```json
{
  "code": "OK",
  "message": "查询成功",
  "traceId": "trace-4a9b-8f1c-20261027143000",
  "data": {
    "records": [ ... ],
    "total": 45,
    "size": 10,
    "current": 1,
    "pages": 5
  }
}
```

#### (3) 通用业务错误响应（HTTP 4xx / 5xx）
```json
{
  "code": "ORDER_STATUS_INVALID",
  "message": "当前工单状态不支持接单操作",
  "traceId": "trace-4a9b-8f1c-20261027143000",
  "data": null
}
```

### 1.3 幂等控制规范 (`Idempotency-Key`)
对于核心写操作（如服药打卡 `/tasks/checkin`、预约提交 `/service-reservations`、SOS 触发 `/emergency/sos/trigger`、录入体征 `/health/vitals`）：
- 客户端可在请求头附带 `Idempotency-Key: <UUID>`；
- 服务端校验相同 key 且规范化请求摘要（SHA-256）一致时，直接重放原成功响应报文；
- 若相同 key 携带不同请求内容，服务端拒绝并返回 `HTTP 409 Conflict`。

## 3. 核心 API 端点详细契约

### 3.1 M03 健康体征监测
#### (1) 手动录入老人健康体征
- **端点**：`POST /api/v1/health/vitals`
- **角色**：`COMMUNITY_ADMIN`
- **请求体 (JSON)**：
  ```json
  {
    "elderId": 1001,
    "vitalType": "BLOOD_PRESSURE",
    "valuePrimary": 145.0,
    "valueSecondary": 92.0,
    "unit": "mmHg",
    "recordedAt": "2026-10-27T10:30:00+08:00",
    "remark": "网格员入户例行体检"
  }
  ```
- **成功响应**：`{ "code": "OK", "data": 5001 }`（返回生成的 `vitalId`）
- **副作用**：写入 `vital_record` 表，同事务内触发异步 `assessment_task` 预警评估。

---

### 3.2 M04 日常用药与打卡
#### (1) 创建长辈用药计划
- **端点**：`POST /api/v1/medication/plans`
- **角色**：`CHILD`
- **请求体 (JSON)**：
  ```json
  {
    "elderId": 1001,
    "medicineName": "硝苯地平缓释片",
    "dosage": "1片 (20mg)",
    "usageMethod": "口服，早饭后",
    "frequencyType": "DAILY",
    "startDate": "2026-10-28",
    "endDate": null,
    "reminderTimes": [
      { "reminderTime": "08:00:00", "timeLabel": "早饭后" }
    ]
  }
  ```
- **业务规则**：新建用药计划默认次日零点正式生效并排产生成任务，避免当日任务冲突。
- **停用档案规则**：停用老人不能新建计划，也不补建当日缺失任务或发送新的普通关怀提醒；仍有效的子女可维护已有计划，但不能请求刷新当日待服任务。重新启用后按当前有效版本生成任务，不追补停用期间的日期。

#### (2) 老人今日服药打卡
- **端点**：`POST /api/v1/medication/tasks/checkin`
- **角色**：`ELDER`
- **请求体 (JSON)**：
  ```json
  {
    "taskId": 8001,
    "checkinMode": "SELF_CONFIRMED"
  }
  ```
- **成功响应**：返回打卡后的 `MedicationTaskVO`，状态置为 `CONFIRMED`。
- **并发控制**：`medication_checkin.task_id` 建立唯一索引，同一任务仅能打卡一次。

### 3.3 M06 服务预约与 M07 调度协调
#### (1) 子女发起服务预约
- **端点**：`POST /api/v1/service-reservations`
- **角色**：`CHILD`
- **请求体 (JSON)**：
  ```json
  {
    "elderId": 1001,
    "serviceType": "CLEANING",
    "serviceDate": "2026-10-29",
    "slotCode": "MORNING_1",
    "serviceAddress": "幸福阳光小区2栋1单元301",
    "contactPhone": "13800138000",
    "specialNotes": "老人腿脚不便，请自备鞋套"
  }
  ```
- **成功响应**：返回 `reservationId`。
- **并发防冲突**：依赖 `uk_active_elder_service_slot` 唯一索引拦截重复冲突时段预约。

#### (2) 管理员受理预约并原子派生工单
- **端点**：`POST /api/v1/admin/reservations/{reservationId}/confirm`
- **角色**：`COMMUNITY_ADMIN`
- **成功响应**：`{ "code": "OK", "data": 9001 }`（返回派生的 `workOrderId`）
- **事务保证**：
  1. `service_reservation.status` 变更为 `CONFIRMED`；
  2. 生成 `work_order` 记录（状态 `PENDING_DISPATCH`，工单编号唯一）；
  3. 写入 `reservation_execution_link` 映射；
  4. 记录 `work_order_action_history` 建单流水。

#### (3) 取消待确认预约或申请取消已确认预约
- **端点**：`POST /api/v1/service-reservations/{reservationId}/cancel`
- **角色**：原预约申请人 `CHILD`
- **请求体 (JSON)**：`{ "reason": "长辈改期" }`（1–247 个字符）
- **状态规则**：`PENDING_CONFIRMATION` 可直接转为 `CANCELLED`；`CONFIRMED` 且关联工单仍为 `PENDING_DISPATCH` 或 `DISPATCHED` 时创建待审批取消申请；工单已接单或服务中时，应走服务中止审批。
- **管理员审批**：`GET /api/v1/admin/reservations/cancel-requests/pending` 查询队列；`POST /api/v1/admin/reservations/cancel-requests/{cancelId}/review` 请求体为 `{ "decision": "APPROVE", "reviewReason": "同意取消" }`，`decision` 支持 `APPROVE` / `REJECT`。批准会在同一事务内取消预约并终止未接单工单；拒绝保留预约与工单。写操作要求 `Idempotency-Key`，成功重放不重复新增历史或通知。

### 3.4 M08 护工现场服务与工单履约
#### (1) 护工接单
- **端点**：`POST /api/v1/work-orders/{workOrderId}/accept`
- **角色**：`CARE_WORKER`, `GRID_WORKER`
- **校验逻辑**：`current_assignee_id == currentUserId` 且状态为 `DISPATCHED`，否则拒绝。
- **状态变迁**：状态跃迁至 `ACCEPTED`。

#### (2) 护工现场开始服务
- **端点**：`POST /api/v1/work-orders/{workOrderId}/start`
- **角色**：`CARE_WORKER`, `GRID_WORKER`
- **状态变迁**：仅当前承接人可将 `ACCEPTED` 工单转为 `PROCESSING` 并记录服务开始时间。

#### (3) 申请并审核预约服务中止
- **申请端点**：`POST /api/v1/work-orders/{workOrderId}/service-stop-requests`
- **申请人**：原预约申请人（`CHILD` / `ELDER`）或当前工单承接人（`CARE_WORKER` / `GRID_WORKER`）；仅支持预约派生且状态为 `ACCEPTED` 或 `PROCESSING` 的工单。
- **请求体 (JSON)**：
  ```json
  {
    "stopReason": "老人身体不适，无法继续服务",
    "completedContent": "已完成室内扶手检查",
    "incompleteContent": "尚未完成浴室防滑处理",
    "followUpPlan": "家属陪同就医后重新预约"
  }
  ```
- **管理员端点**：`GET /api/v1/work-orders/{workOrderId}/service-stop-requests` 查看本社区申请；`POST /api/v1/work-orders/{workOrderId}/service-stop-requests/{stopId}/review` 请求体为 `{ "action": "APPROVE", "reviewComment": "同意中止并安排后续回访" }`。
- **结果**：批准将预约与工单一并置为 `SERVICE_STOPPED` 并记录审核/执行人、时间、已完成与未完成内容及后续安排；拒绝保留预约和工单原执行状态。申请与审核写操作均要求 `Idempotency-Key`。

#### (4) 人员撤权后的工单责任交接
- **管理员申请端点**：`POST /api/v1/work-orders/{workOrderId}/handoffs`，请求体为 `{ "toUserId": 2002, "reason": "原承接人员离岗" }`。
- **指定人员接受端点**：`POST /api/v1/work-orders/{workOrderId}/handoffs/{handoffId}/accept`，请求体可包含 `{ "responseComment": "已确认接手" }`。
- **指定人员拒绝端点**：`POST /api/v1/work-orders/{workOrderId}/handoffs/{handoffId}/reject`，请求体为 `{ "responseComment": "当前无法承担该工单" }`。只有被指定且当前仍具有效社区工作人员角色的目标可以拒绝。
- **状态与权限**：管理员只能指定同社区、仍具有效 `CARE_WORKER` 或 `GRID_WORKER` 角色的其他人员；只有被指定人员可以接受。原人员角色撤销会先留 `REASSIGNMENT_REQUIRED`，随后由管理员指定接手人并转为 `REQUESTED`。
- **目标调整与交接范围**：管理员可将待确认目标替换为其他有效工作人员；旧请求记录为 `CANCELLED`，保留原接收人、原因、时间和调整说明。目标拒绝后也可重新发起交接。当前支持 `DISPATCHED`、`ACCEPTED`、`PROCESSING`、`PENDING_RESULT_REVIEW`；接受后只变更当前承接人及交接/派单历史，工单状态、执行结果、照片和既有提交历史保持原值。申请、接受、拒绝写操作均要求 `Idempotency-Key`。

#### (5) 上传履约凭据照片
- **端点**：`POST /api/v1/files/upload`，`multipart/form-data` 字段为 `file` 和 `workOrderId`。
- **角色与状态**：当前承接的 `CARE_WORKER` / `GRID_WORKER` 在工单 `PROCESSING` 时可上传；`COMMUNITY_ADMIN` 可上传同社区处于 `PROCESSING` 的工单。
- **内容校验**：仅 JPEG/PNG，扩展名、声明 MIME 和实际解码格式必须一致；单张上限 5 MiB，超过 4000 万像素拒绝。上传时落库资产 UUID、不可变版本、大小、MIME、SHA-256、上传人及工单暂存关系；暂存记录还不是结案凭证。
- **响应关键字段**：`data.assetUuid` 是后续提交引用的资产 ID；`data.url` / `data.filename` 仅供受权读取和界面预览。读取 `/api/v1/files/view/{filename}` 需要当前用户有对应工单凭证权限，响应不允许公共缓存并设置 `nosniff`。

#### (6) 护工提交完成并上传凭据
- **端点**：`POST /api/v1/work-orders/{workOrderId}/execution`
- **角色**：`CARE_WORKER`, `GRID_WORKER`
- **请求体 (JSON)**：
  ```json
  {
    "resultSummary": "已完成长辈居家保洁与日常清理",
    "evidenceAssetUuids": ["a91d4c74-4fc8-4edc-8c7f-f3b22bf5db55", "b14a726e-903c-40b5-8e58-6d4a596c9276"],
    "isExemptPhoto": false,
    "photoExemptionReason": null
  }
  ```
- **业务校验**：若工单要求拍照凭据（`result_photo_required = 1`），则必须提供 1—5 个不同且预先上传到本工单的 `evidenceAssetUuids`，或合法的 `photoExemptionReason`。服务端解析资产 UUID，校验工单归属、文件大小与 SHA-256，并在与状态变更相同的事务中创建 `business_file_link`、固定确切版本 ID 到提交历史；裸 `photoUrls` 仅供历史显示，不作为新提交凭据。
- **状态变迁**：进入 `PENDING_RESULT_REVIEW`（待审核结案）。

#### (7) 管理员终审结案
- **端点**：`POST /api/v1/work-orders/{workOrderId}/review`
- **角色**：`COMMUNITY_ADMIN`
- **请求体 (JSON)**：
  ```json
  {
    "action": "APPROVE",
    "reviewComment": "现场服务合规，凭证完整，予以结案归档"
  }
  ```
- **审批动作**：`action` 支持 `APPROVE` 和 `REJECT`。
- **自保护约束**：若工单由当前管理员兼任护工执行，则系统**严厉拦截自审操作**，要求其他管理员审核。

### 3.5 M09 社区数据看板
#### (1) 社区综合指标概览
- **端点**：`GET /api/v1/dashboard/community/summary?communityId=1`
- **角色**：`COMMUNITY_ADMIN`, `GRID_WORKER`
- **响应体 (JSON)**：
  ```json
  {
    "code": "OK",
    "data": {
      "todayServiceCount": 18,
      "pendingAlertCount": 3,
      "activeSosCount": 0,
      "medicationComplianceRate": 94.5,
      "avgResponseMinutes": null
    }
  }
  ```
- **多租户隔离**：服务端强行比对 `communityId` 与当前登录者 Token 中的管辖社区，跨社区访问抛出 403 Forbidden；空样本比率安全返回 `null`。

#### (2) 七日图表与首次接单响应（Q09-04）
- **端点**：`GET /api/v1/dashboard/community/charts?period=7D`；社区范围由服务端按当前身份约束。
- **响应字段**：`data.workOrderTrend` 为全部工单趋势；`data.workOrderTrendByCategory.ORDINARY` 与 `.SOS` 分别为普通工单和 `source_type=SOS` 工单趋势，结构一致：

  | 字段 | 含义 |
  | --- | --- |
  | `dateList` | 上海时间今天及前六个自然日，按升序排列的 `MM-dd` 标签 |
  | `dispatchedCounts` | 当日创建的工单数（保留既有字段名，包含取消和管理终止记录） |
  | `closedCounts` | 当日 `reviewed_at` 对应的当前 `CLOSED` 工单数，单独按结案日统计 |
  | `acceptedCounts` | 当日创建且截至统计时有有效首次接单历史的工单数，包括接单后拒单、重接或终止的记录 |
  | `unacceptedCounts` | 当日创建、无有效接单历史，且当前仍为 `PENDING_DISPATCH`、`DISPATCHED` 或 `PENDING_ACCEPT` 的工单数 |
  | `avgResponseMinutes` | 当日创建的有效样本的平均首次接单响应分钟数，保留一位小数；无样本为 `null`，页面显示“无数据” |

- **统计边界**：使用注入的 Clock，并固定 `Asia/Shanghai`；创建时间区间为 `[今天−6日 00:00, 明天 00:00)`。每个日桶也采用左闭右开边界。
- **首次有效接单**：从 `work_order_action_history` 取最早的合法 `to_status=ACCEPTED` 事件；普通接单为 `ACCEPT`（`from_status=DISPATCHED`），SOS 自动接单为 SOS 工单的 `TRIGGER_SOS`（`from_status=PENDING_DISPATCH`）。剔除事件时间早于建单或晚于当前统计时点的记录，责任交接等其他动作不作为首次接单。
- **计算规则**：按每个有效工单的 `首次有效接单时间−created_at` 计算，保留秒的精度后求平均、四舍五入一位小数；拒单重接仍取第一次。不得使用可覆盖的 `accept_time`、服务起止时间或审核时间计算响应；无接单且已取消/终止的工单不计入平均值或仍未接单有效数。普通/SOS 可在页面单独筛选。该指标只代表社区接单响应。

### 3.6 M10 老人一键 SOS 紧急求助
- **端点**：`POST /api/v1/emergency/sos/trigger`
- **角色**：`ELDER`
- **请求体 (JSON)**：
  ```json
  {
    "elderId": 1001,
    "pressDurationMs": 2500,
    "locationAddress": "幸福阳光小区2栋1单元301",
    "longitude": 116.407526,
    "latitude": 39.904030
  }
  ```
- **强校验**：`pressDurationMs` 必须大于等于 2000 毫秒（防误触）；
- **响应体**：返回 `SosEventVO` 及关联紧急工单编号；
- **停用档案例外**：SOS 是停用档案允许的新业务例外。受理事务先锁定并重读档案；`SosEventVO.elderInactiveAtAcceptance` 在新事件上固定为 `true` 或 `false`，停用时为 `true`，供管理员在 SOS 列表复核。字段为 `NULL` 的历史事件表示受理时档案状态未知。
- **实时副作用**：同事务内建单并向 WebSocket 通道广播突发大屏声光警报。

## 4. 业务状态机流转速查矩阵

### 4.1 服务预约生命周期状态机 (`service_reservation.status`)
```text
[发起预约] --> PENDING_CONFIRMATION (待确认)
                    |
      +-------------+-------------+
      |                           |
[管理员确认受理]            [管理员驳回 / 子女主动取消]
      |                           |
      v                           v
  CONFIRMED (已确认受理)       REJECTED / CANCELLED
      |                         (终态/时隙槽释放)
      +-- [未接单取消申请批准] --> CANCELLED
      |
      +-- [已接单服务中止批准] --> SERVICE_STOPPED
```

### 4.2 社区工单全生命周期状态机 (`work_order.status`)
```text
[建单] --> PENDING_DISPATCH (待派单)
               |
         [管理员指派护工]
               |
               v
            DISPATCHED (已派发)
               |
         [护工手机端接单]
               |
               v
            ACCEPTED (已接单)
               |
         [护工上门开始服务]
               |
               v
          PROCESSING (服务执行中)
               |
      [拍照上传凭据并提交完成]
               |
               v
     PENDING_RESULT_REVIEW (待审核结案)
               |
         [管理员终审通过]
               |
               v
           CLOSED (已结案归档)
```

工作人员角色撤销时，仍由其承接的未结工单保留当前状态并进入 `REASSIGNMENT_REQUIRED`；管理员指定有效接手人后为 `REQUESTED`，指定人员接受后记录新承接人，工单业务状态与已有履约进度不变。

## 5. 核心业务错误码速查表

| HTTP 状态码 | 业务错误码 (code) | 中文释义 / 发生场景 |
| :---: | :--- | :--- |
| **400** | `PARAM_VALIDATION_FAILED` | 请求参数格式错误或必填项缺失 |
| **400** | `VITAL_VALUE_OUT_OF_RANGE` | 体征录入值超出物理生理极限（如体温 50 度） |
| **401** | `UNAUTHORIZED` | 凭证缺失、Token 过期或会话已被即时撤销 |
| **403** | `FORBIDDEN` | 越权访问：如普通护工试图查看全社区数据大屏 |
| **403** | `COMMUNITY_CROSS_TENANT_VIOLATION` | 跨社区访问数据隔离越权 |
| **403** | `WORK_ORDER_SELF_REVIEW_FORBIDDEN` | 管理员不可自审本人作为护工执行的工单 |
| **404** | `RESOURCE_NOT_FOUND` | 目标工单、预约、体征或长辈档案不存在 |
| **409** | `CONCURRENCY_CONFLICT` | 乐观锁 CAS 失败，工单已被其他人先一步处理 |
| **409** | `ORDER_STATUS_INVALID` | 状态机不合法跃迁（如对已结案工单执行接单） |
| **409** | `RESERVATION_SLOT_OCCUPIED` | 所选预约日期与时段已被同长辈有效预约占用 |
| **409** | `MEDICATION_TASK_ALREADY_CHECKED` | 今日该时点任务已完成打卡，禁止重复提交 |
| **409** | `IDEMPOTENCY_HASH_MISMATCH` | 相同幂等键附带了不同请求内容，安全冲突拒绝 |
| **500** | `INTERNAL_SERVER_ERROR` | 服务端未捕获异常或数据库底层连接异常 |
