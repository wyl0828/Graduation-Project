## 一、按交付物看：十类工作

这十类工作是**项目最终要交付什么**，并非必须一类全部完成才开始下一类。原型、数据库、API 和测试设计可随模块迭代；对应模块满足 G1 后即可编码。

| 阶段 | 主要交付物 | 当前状态 |
| --- | --- | --- |
| 1. 需求与范围 | 角色、权限、业务规则、非本期边界和验收目标 | 已有经确认的 SRS v1.0；[现行需求](./需求与范围.md)持续维护。业务实现未开始 |
| 2. 总体设计 | 架构、模块划分、依赖和关键流程 | 已有经复核的 v1.1 来源稿；[现行总体设计](./总体设计.md)可随实现修订 |
| 3. 原型与交互 | 核心业务流程、页面入口、字段、按钮、权限、加载/空/失败状态 | 尚无独立完整交付物；小程序[代码架构工作稿](./小程序代码架构.md)仅提供候选结构 |
| 4. 数据库设计 | ER 图、数据字典、物理 DDL、约束、索引、迁移和合成数据 | 有[跨模块逻辑模型](./跨模块设计.md)；物理 DDL、迁移执行和演示库未完成 |
| 5. API 与状态契约 | 端点、请求响应、权限、错误、幂等、状态、事务和文件规则 | 有共享规则；模块完整字段契约与运行契约测试未完成 |
| 6. 测试设计 | AT/A 场景的步骤、数据、预期结果和需求—用例追踪 | 有[需求追踪](./需求追踪.md)和初始 AT 入口；可执行用例待补，运行结果未测 |
| 7. 分模块开发 | 后端、老人/子女小程序、管理端及模块测试 | 只有后端工程骨架；两个前端是占位目录，业务模块未开始 |
| 8. 集成与系统验收 | 完整业务链、权限、失败、并发、性能和适老化测试 | 未开始；AT/A 运行结果均未测 |
| 9. 部署与恢复验证 | 干净环境启动、运行说明、日志、备份及联合恢复演练 | 已有部分脚本；D1 复现、部署和恢复验收未通过 |
| 10. 论文与答辩 | 论文、系统图、测试证据、PPT 与演讲材料 | 随真实实现积累素材；不能把设计目标写成实测结果 |

## 二、按工程门槛看：D0—D3 与 G1—G3

这些编号是[跨模块设计 §5](./跨模块设计.md)的**数据/API 确认点与验收门槛**，用于管理上面十类工作的先后关系。编号不能重新定义为另一套阶段。

| 门槛 | 确切含义 | 当前判断 |
| --- | --- | --- |
| D0 逻辑模型 | 共享实体、关系、状态和保留语义 | 文档口径已有；锁序仍须逐事务验证 |
| D1 工程基座 | 仓库、工具链、隔离数据库、迁移、配置、文件路径、前端骨架与干净初始化 | 进行中；未验收 |
| D2 物理数据库 | 表/列类型、索引、外键、唯一约束、迁移与种子数据 | 未完成；随相关模块落地 |
| D3 API/状态契约 | 每端点方法、路径、字段、权限、版本、幂等、错误、事务与 outbox | 未完成；随相关模块落地 |
| G1 模块开工 | 该模块需求、权限、状态、D2/D3、测试步骤与环境足够明确 | 首批业务模块尚未达到 |
| G2 模块验收 | 对应 AT 实际通过，权限、失败及并发路径有证据 | 未开始 |
| G3 全系统验收 | AT、NFR、部署及恢复目标有真实执行证据 | 未开始 |

共享能力（认证上下文、统一错误、幂等、审计、通知 outbox 和文件基础能力）属于**工程实现任务**，在 D1 后优先建设，并与相应 D2/D3 契约共同推进；它不是“D2”的定义。D2/D3 可按模块逐步确认，不必等待全系统所有接口完成才写第一项业务代码。

## 三、现在的下一步

1. **完成 D1：** 处理配置模板中的明文密码样例；建立隔离演示库和应用账号；执行 Flyway，启动后端并验证健康接口；建立并构建老人/子女小程序与管理端；核对文件目录和干净环境初始化。结果写入新的执行记录，不把旧记录改成“通过”。见[工程基座方案](./工程基座.md)和[D1 初始化记录](../validation/D1工程基座初始化记录_2026-10-25.md)。
2. **同步补首批可执行设计：** 做登录/授权与老人档案的关键页面低保真流程；确定 M01/M02 所需物理表、接口、权限、失败语义和 AT 步骤。原型、D2、D3、测试设计可与 D1 余项并行准备，但业务编码须满足 G1。
3. **开始首批实现：** D1 通过且 M01/M02 达到 G1 后，先建共享能力和身份/档案闭环；M06 开工前补完整工单专项。随后按依赖推进 M03/M05/M10、M04/M11、M07/M06 联动、文件与审计、M08/M09，逐模块完成 G2。
4. **最后做联合验收与交付：** 跨模块事务和并发、AT/A、性能与适老化、部署复现、备份恢复均保留真实记录，达到 G3 后整理论文和答辩材料。

进度只按代码、页面、构建和真实运行证据更新。[变更记录](./变更记录.md)只记录改变需求范围、权限或关键业务规则的决定；普通设计细化直接更新现行工作文件。

## 四、执行任务清单

下面的编号是任务编号，不改变 D0—D3/G1—G3 的含义。每项完成后保存实际命令、环境、版本、结果和问题；遇到失败先修复再复测。任务可交错进行，但不能越过对应依赖和验收门槛。

### C. 分批实现和验收

1. 先实现最小共享支撑（认证上下文、统一错误/追踪、幂等、审计、通知 outbox 与文件基础），再完成 M01/M02 的后端、老人/子女端和管理端闭环；对应 AT 实际通过后记录 G2。
2. 补 M06 完整工单专项，并为其完成交互、D2、D3、测试设计和 G1；随后实现工单核心与调度。普通健康告警与工单关系、SOS 原子建单及预约确认建单分别验证，不能只凭时序图认定事务成立。
3. 按依赖推进 M03/M05/M10 健康、告警与仿真；M04/M11 用药、通知与文件；M07/M06 预约工单联动；再完成 M08 帮助与进度、M09 看板、M12 配置与审计的剩余业务能力。每批都执行相同的“交互 → D2/D3 → 用例 → G1 → 代码 → G2”循环。
4. 最后完成跨模块失败与并发、权限隔离、AT/A、性能与适老化、干净部署、备份恢复和演示走查；真实记录满足 G3 后，再写论文结论及答辩材料。
