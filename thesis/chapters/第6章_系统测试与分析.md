# 第 6 章 系统测试与分析

## 6.1 测试目标与环境搭建

### 6.1.1 软件与硬件测试环境

为保证测试结果的真实性、可复现性与客观性，系统在独立的软硬件测试环境中搭建了隔离的自动化验证基准。

| 环境维度 | 配置参数 / 规格标准 |
| :--- | :--- |
| **操作系统** | Windows 11 专业版 (64 位) / Ubuntu 22.04 LTS (对照验证) |
| **处理器 (CPU)** | 12th Gen Intel(R) Core(TM) i7-12700H @ 2.30 GHz (14 核 20 线程) |
| **内存 (RAM)** | 32 GB DDR4 3200 MHz |
| **数据库** | MySQL Community Server 8.0.36 (InnoDB 引擎) |
| **Java 运行环境**| OpenJDK 17.0.10 (Temurin-17) |
| **Node.js 环境** | Node.js v20.18.0 / npm 10.8.2 |
| **自动化测试框架**| JUnit 5 / Mockito / Spring Boot Test / Playwright / Apache JMeter 5.6 |

### 6.1.2 依据规范与质量特性体系

测试执行严格遵循国家标准 **GB/T 25000.51—2016《系统与软件工程 系统与软件质量要求和评价（SQuaRE）第 51 部分：就绪可用软件产品（RUSP）的质量要求和测试细则》**，重点围绕以下四大软件质量特性展开系统性检验：
1. **功能性（Functionality）**：核心业务功能实现的正确性与完整性，重点验证服药打卡、一键求助、工单全流程履约闭环；
2. **安全性与数据隔离性（Security）**：基于角色的访问控制（RBAC）、社区属地数据隔离、亲情授权撤销即时性以及敏感档案防越权渗透能力；
3. **并发可靠性与容错性（Reliability）**：工单有限状态机的非法跃迁拦截、行级乐观锁抗并发竞态保护及事务一致性；
4. **性能效率（Performance Efficiency）**：高频接口在多并发线程负载冲击下的平均响应时延（RT）与系统吞吐量（TPS）。

## 6.3 核心流转机制与安全并发测试

### 6.3.1 工单非法状态逆向转移拦截测试

针对有限状态机（FSM）的严密性进行逆向渗透测试：
- **测试场景 1（跳跃流转）**：工单处于 `PENDING_DISPATCH`（待派单）时，攻击者直接调用 `reviewOrder` 接口试图强行结案；
  - *实测响应*：服务端抛出 `IllegalStateTransitionException: 当前状态不允许执行结案操作`，事务终止，数据库状态保持不变。
- **测试场景 2（终态修改）**：工单处于 `CLOSED`（已结案）时，护工再次调用 `submitReview` 试图伪造更新凭证；
  - *实测响应*：服务端断言判定该工单已达终态，拒绝修改，有效防止了历史审计凭证被篡改。

### 6.3.2 乐观锁防止工单重复派发并发测试

在隔离临时 MySQL 环境下，通过多线程并发测试套件模拟两名管理员同时指派同一工单的高并发竞争场景：
- **测试设计**：启动 2 个并发线程，同时读取工单主键 `id = 1` 且版本号 `version = 1` 的同一张工单。
  - 线程 1 尝试将工单派发给护工 A；
  - 线程 2 尝试将工单派发给护工 B。
- **实测执行结果**：
  - 线程 1 优先获取数据库行锁，执行 `UPDATE work_order SET assigned_to = 'A', version = 2 WHERE id = 1 AND version = 1`，受影响行数 `rows = 1`，派发成功；
  - 线程 2 随后执行，此时数据库中 `version` 已经递增为 2，条件比对不匹配，受影响行数 `rows = 0`；
  - 服务端精准捕获并抛出 `BusinessException(ErrorCode.CONCURRENT_CONFLICT)`，线程 2 事务回滚，向客户端友好提示“工单已被其他管理员处理，请刷新”。
- **测试结论**：行级乐观锁彻底消除了双重指派与脏数据问题，并发控制正确无误。

## 6.4 模拟高并发性能测试与分析

### 6.4.1 核心业务接口高并发压测方案

为检验系统在极端高峰负荷（如突发公共卫生事件或大规模集中体征上传）下的运行稳定性，利用 Apache JMeter 搭建了高并发负载测试场景：
- **压测目标接口**：
  1. `POST /api/v1/health/records`（体征数据批量上报与规则评估接口）；
  2. `GET /api/v1/work-orders/care-worker`（护工移动工作台工单列表高频拉取接口）；
- **压测配置**：设置线程组并发用户数为 20、50、100，每个虚拟用户持续发送 100 次循环请求（总样本量 10,000 次），启动 Ramp-Up 时间设定为 5 秒。

### 6.4.2 响应时延与系统吞吐量分析

压测实测数据统计汇总如下表：

| 并发线程数 (Users) | 压测目标接口 | 总请求数 (Samples) | 吞吐量 (TPS / req/s) | 平均响应时间 (Avg RT / ms) | 95% 分位时延 (95% Line / ms) | 错误率 (Error Rate) |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| **20 并发** | 体征上报与规则评估 | 2,000 | 284.6 | 68.4 | 112.0 | 0.00% |
| **20 并发** | 护工工作台工单拉取 | 2,000 | 412.3 | 47.2 | 78.5 | 0.00% |
| **50 并发** | 体征上报与规则评估 | 5,000 | 368.1 | 132.8 | 215.4 | 0.00% |
| **50 并发** | 护工工作台工单拉取 | 5,000 | 520.4 | 93.6 | 158.0 | 0.00% |
| **100 并发** | 体征上报与规则评估 | 10,000 | 392.5 | 248.2 | 430.6 | 0.00% |
| **100 并发** | 护工工作台工单拉取 | 10,000 | 565.8 | 172.5 | 310.2 | 0.00% |

#### 性能测试结果综合分析：
1. **吞吐量与时延表现**：在 50 并发（接近典型社区日常高峰负荷峰值）冲击下，体征上报接口吞吐量达到 $368.1\text{ req/s}$，平均响应时间仅为 $132.8\text{ms}$；读密集型的工单拉取接口吞吐量超过 $520\text{ req/s}$，95% 的请求在 $160\text{ms}$ 内完成响应。
2. **系统健壮性与稳定性**：在提升至 100 极限并发线程冲击时，系统未出现任何 HTTP 500、连接池枯竭或数据库死锁报错，整体请求错误率始终保持在 **0.00%**。
3. **性能瓶颈评估**：性能瓶颈主要集中在体征规则评估时的复杂医学多维条件匹配，但平均时延仍远低于 $500\text{ms}$ 的交互容忍上限，完全能够胜任大型智慧社区居家养老的常态化高效运行需要。
