## 逐章映射与内容实施方案

### 第 1 章 绪论
- **写作依据**：`thesis/论文参考文献工作包.md` 中的 A、B、C、D 四大文献组。
- **核心要点**：
  1. 准确引用国家卫健委“9073”居家养老格局（文献 [A7]）与失能、空巢老人看护断层现实（文献 [D1]）。
  2. 引用工信部适老化通用规范（工信厅信管函〔2021〕67号，文献 [A1]）及《中华人民共和国无障碍环境建设法》（文献 [A2]），立下合规设计基调。
  3. 梳理国内外现有系统（文献 [C1]–[C4]），剖析现有平台存在的**三大核心痛点（研究缺口）**：
     - *缺口 1*：重被动健康数据展示，轻线下网格化服务调度闭环；
     - *缺口 2*：适老化改造流于表面（单纯字体变大），缺乏认知负荷理论指导和量化验收；
     - *缺口 3*：老人、子女、网格员、社区四方数据权限边界混乱，缺乏严格的数据隔离与亲情授权。
  4. 阐述本系统的研究内容：构建覆盖“健康监护 $\to$ 异常告警 $\to$ 线上代办 $\to$ 网格调度 $\to$ 线下履约 $\to$ 审核结案”全链路的适老化社区养老服务系统。

---

### 第 2 章 相关技术与理论基础
- **2.1 核心技术框架**：
  - Spring Boot 3：约定优于配置、自动装配机制、单体分层架构（Controller - Service - Mapper - Scheduler）。
  - Vue 3 + Uni-app：一套代码构建多端小程序与后台 Web，响应式组合式 API（Composition API）。
- **2.2 关键技术与机制（突出核心创新点）**：
  - **有限状态机（FSM）理论**：阐述状态机在离散事件驱动系统中的状态、事件、动作转移模型，为第 4.7 节工单流转奠定理论支撑。
  - **社区网格化治理与权限矩阵模型**：阐述 RBAC（基于角色的访问控制）结合属地多租户隔离（Community Data Isolation）的设计原理。
  - **行级乐观锁（Optimistic Locking）**：阐述基于数据库 `version` 字段的无锁并发控制模型，避免分布式锁带来的复杂运维成本。
  - **Flyway 数据库演进**：平滑演进与脚本版本化治理机制。
- **2.3 适老化设计的理论基础**：
  - **认知负荷理论（Sweller, 1988/2011，文献 [B1][B2]）**：内在认知负荷、外在认知负荷与相关认知负荷。重点论证如何通过简化单向流程、大触控热区、高色度对比度、减少冗余文字来削减外在认知负荷。
  - **国家标准依据**：GB/T 37668—2019 互联网内容无障碍可访问性技术要求。

---

### 第 3 章 系统需求分析
- **3.1 核心业务流程分析（绘制三张标准 UML 泳道流程图）**：
  - 老人日常体征监测与异常评估流转。
  - 老人一键 SOS 触发 $\to$ 系统原子创建告警与紧急工单 $\to$ 社区优先响应调度。
  - 子女线上代预约 $\to$ 社区指派网格员/护工 $\to$ 线下上门服务与存证 $\to$ 社区审核。
- **3.2 角色划分与职责定义**：
  - 老年人（适老客户端，受助方）；
  - 监护子女（家属客户端，监护与代办方）；
  - 网格员/护工（移动工作台，履约处置方）；
  - 社区管理员（Web 运营端，组织协调与质量监督方）。
- **3.3 系统用例分析**：
  - 绘制 4 个角色的 UML 用例图，给出核心用例的前置条件、基本流程、异常流程及后置条件。
- **3.4 非功能需求分析**：
  - 适老化量化标准（最小正文字号 $\ge 18\text{pt}$，操作热区 $\ge 48\times 48\text{dp}$，色彩对比度 $\ge 4.5:1$）；
  - 安全合规性：密码安全散列存储、会话自动超时撤销、身份激活码 24 小时一次性机制；
  - 性能要求：常规接口响应时间 $\le 500\text{ms}$，工单并发更新原子性保障。
- **3.5 可行性分析**：技术、经济、操作、法律社会四维论证。

---

### 第 4 章 系统设计
- **4.1 系统设计原则**：可用性第一、职责分层明确、数据严格隔离、状态机强一致性。
- **4.2 总体架构设计**：
  - 展示客户端层（Uni-app 小程序 + Element Plus Web）、应用层（RESTful API 分层）、数据层（MySQL 8.0 + 本地存储 + 定时调度）。
- **4.3–4.5 模块结构与交互设计**：
  - 梳理老人端、子女端、护工端与管理端的功能模块树。
- **4.6 数据库系统设计**：
  - 概念模型：绘制核心实体 E-R 图（用户账号、老人档案、亲情绑定、体征数据、用药计划、服务预约、服务工单、流转历史、照片存证）。
  - 逻辑模型：列出 10 张核心业务表字段、类型、主外键、唯一约束与默认值（如 `work_order`、`work_order_action_history`、`work_order_assignment_history`、`elder_profile` 等）。
  - 数据库迁移：说明 Flyway V1 至 V3.3 的表结构增量迁移策略。
- **4.7 核心特色机制详细设计（全篇最大学术与工程亮点）**：
  - **4.7.1 统一工单创建模型**：阐述预约工单（异步预约触发）与 SOS 紧急工单（同步原子创建）的适配统一设计。
  - **4.7.2 有限状态机设计**：
    - 状态定义：`PENDING_DISPATCH`（待派单）、`DISPATCHED`（已派单/待接单）、`ACCEPTED`（已接单）、`IN_PROGRESS`（处置中）、`SUBMITTED`（已提交待审）、`CLOSED`（已结案）、`REJECTED`（已驳回/已拒单）、`VOIDED`（已作废）。
    - 给出状态转移矩阵（State Transition Matrix），严格限定不同角色允许触发的动作转换。
  - **4.7.3 网格化数据隔离与派发校验**：
    - 网格员/护工只能被指派给同社区工单；
    - 护工角色受限于本人分配范围（`requireCareWorkerOrder`），杜绝越权访问全社区老人的隐私档案。
  - **4.7.4 基于乐观锁的并发调度控制**：
    - 引入 `version` 字段，执行 `UPDATE ... WHERE id = ? AND version = ?`；
    - 详细剖析多人并发接单、并发派单时的竞态预防，并在更新失败时抛出业务异常保障状态一致性。
  - **4.7.5 照片履约存证与防篡改机制**：
    - 照片文件上传独立校验，服务端记录文件 Hash 与元数据；
    - 必须在工单处于 `IN_PROGRESS` 且由当前分配护工操作时方可关联照片，提交审核时强制校验照片数量与完整性。
