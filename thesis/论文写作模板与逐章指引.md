## 2. 逐章写法

### 第 1 章 绪论

```
1.1 研究背景与意义
1.2 国内外研究现状
    1.2.1 智慧居家养老系统的研究与实践
    1.2.2 适老化交互设计研究
    1.2.3 研究现状评述
1.3 主要研究内容与工作
1.4 论文组织结构
```

**要点**
- 1.1 走"宏观 → 中观 → 微观"三段：老龄化规模（9073）→ 社区居家照护的现实断层 → 本系统的切入点。
- 1.2 不是文献罗列，是**按主题分组 + 每组末尾给一句小结**。三组各 400 字左右。
- 1.2.3 是整章最重要的地方，写出 3 条研究缺口，每条都指向你论文后面要做的事。
- 1.4 用一段话交代七章各写什么，**不要写成目录的复制**。

**常见错误**：1.1 大段抄政策原文；1.2 变成"某某做了……某某又做了……"的流水账；1.3 写成了系统功能列表。

---

### 第 2 章 相关技术

```
2.1 Spring Boot 框架
2.2 MyBatis-Plus 与 MySQL
2.3 Vue 3 与 Element Plus
2.4 Uni-app 跨端框架
2.5 适老化设计相关规范
```

**要点**
- 每节结构固定：**是什么 → 为什么选它 → 在本系统中用在哪**。第三点最容易被漏，也最能体现你不是在抄技术文档。
- 2.5 单独成节：引工信部两份规范（工信厅信管函〔2021〕67 号）与 GB/T 37668—2019，说明"本系统的字号、热区、交互路径据此设定"。这一节是你和普通 CRUD 毕设的分水岭。
- 全章控制 1800 字以内。技术介绍写太长会被认为凑字数。

**常见错误**：把官方文档的"特性列表"整段搬过来；五节之间没有逻辑关系，像五篇独立小作文。

---

### 第 3 章 需求分析

```
3.1 可行性分析
3.2 用户角色与用例分析
3.3 功能需求分析
    3.3.1 身份认证与权限管理（M01）
    3.3.2 老人档案与亲情绑定（M02）
    3.3.3 健康档案与体征记录（M03）
    3.3.4 用药计划与服药打卡（M04）
    3.3.5 健康告警与紧急求助（M05/M10）
    3.3.6 社区工单与服务调度（M06）
    3.3.7 助老服务预约（M07）
    3.3.8 数据看板与系统配置（M09/M12）
3.4 非功能需求
3.5 关键业务约束
```

**要点**
- 3.2 放**用例图**（一张总图 + 可选四张角色图）。角色表直接来自需求与范围 §2。
- 3.3 的八个小节，每节结构：**业务场景一句话 → 功能点列表 → 关键规则 2–3 条**。不要给 41 条验收场景全列出来，选代表性的。
- 3.4 抄需求与范围 §7，但要改写为"响应时间、并发、可用性、安全性、适老化"五类。
- 3.5 从 13 条业务不变量（BR-01—BR-13）里挑 5–6 条最体现设计难度的：如 BR-01（逐次权限检查）、BR-05（SOS 原子性）、BR-07（幂等）、BR-10（并发冲突）。**这一节是答辩时最能加分的地方**，因为它证明你想过边界情况。

**常见错误**：功能需求写成界面清单（"首页有 5 个按钮"）；没有非功能需求；业务规则一条不写，导致后面的设计像凭空冒出来的。

### 第 4 章 系统设计（最重的一章）

```
4.1 总体架构设计
    4.1.1 分层架构
    4.1.2 技术选型与依据
    4.1.3 部署结构
4.2 功能模块设计
    4.2.1 模块划分
    4.2.2 模块依赖关系
4.3 数据库设计
    4.3.1 概念结构设计（E-R 图）
    4.3.2 逻辑结构设计（表结构）
    4.3.3 关键字段与约束说明
4.4 接口设计
    4.4.1 接口规范
    4.4.2 关键接口定义
4.5 关键业务流程设计
    4.5.1 SOS 紧急求助流程
    4.5.2 健康告警流程
    4.5.3 服药打卡流程
    4.5.4 工单状态机
4.6 适老化界面设计
```

**要点**
- 4.1 放**分层架构图**（总体设计 §4 的结构改画即可）。必须解释"为什么选单体分层而不是微服务"——因为你文档里已明确不引入微服务/Kafka，这个决策要给出理由（规模、部署成本、可维护性）。
- 4.3 是评阅重点。**E-R 图必须有**（可以用 draw.io 画），表结构用三线表列出主要字段，不要贴完整 45 张表，选 8–12 张核心表。
- 4.5 放**时序图**：SOS 一条链路（老人长按 → 服务端校验 → 创建告警+工单 → 通知网格员 → 接单 → 结案），这张图是整篇论文的"技术含量担当"。
- 4.6 这一节别写成"界面截图展示"，那是第 5 章的事。这里写**设计依据**：字号、热区、颜色对比度、交互路径长度，每条挂上规范条款。

**常见错误**：架构图是网上下载的通用图；数据库只有表没有关系；接口设计只列 URL 不写参数和返回。

### 第 5 章 系统实现

```
5.1 开发环境与运行环境
5.2 后端关键功能实现
    5.2.1 统一响应与全局异常处理
    5.2.2 身份认证与会话管理
    5.2.3 权限拦截与数据范围控制
    5.2.4 幂等控制
    5.2.5 事务边界与状态一致性
5.3 前端关键功能实现
    5.3.1 老人端适老化组件
    5.3.2 长按 SOS 交互实现
    5.3.3 子女端体征趋势图
5.4 系统界面展示
```

**要点**
- 5.2 每小节配**核心代码片段（10–20 行）+ 文字说明"这段代码解决了什么问题"**。代码不要超过半页，贴关键部分。
- 5.2.4 幂等、5.2.5 事务，这两个是你文档里写得最细的（模块设计 E-01—E-07），也是最容易写出深度的点，别浪费。
- 5.3.1 适老化组件：字号换算、点击热区、对比度的具体实现，配一段代码和一张对比图。
- 5.4 界面展示只放**关键页面**，6–9 张，每张配两句说明"这个页面解决什么"。

**常见错误**：整页贴代码；界面截图没有说明；实现章节和第 4 章设计对不上。

### 第 6 章 系统测试

```
6.1 测试环境与测试方法
6.2 功能测试
6.3 性能测试
6.4 适老化可用性验收
6.5 测试结果分析
```

**要点**
- 6.1 说明测试方法依据（GB/T 25000.51—2016 的质量特性分类），黑盒为主。
- 6.2 **用表格**：用例编号、测试项、前置条件、步骤、预期结果、实际结果、结论。选 15–25 条有代表性的，从需求与范围 §8 的 AT-01—AT-41 里挑。
- 6.3 给真实数据：并发数、响应时间、错误率。**没有实测数据就写"未测"，不要编。** 你文档 §29 已经标了"未测"，保持这个诚实，评阅老师反而认可。
- 6.4 这一节是亮点：引 GB/T 37668—2019 的测试方法 + 文献 B5 的启发式评价清单，设计一张适老化检查表（字号、热区、对比度、操作步数、误触率），逐项打勾。
- 6.5 不要只写"全部通过"，写**发现的问题与修复**，哪怕两个小 bug，也证明你真的测了。

### 第 7 章 总结与展望

**要点**：总结写"做成了什么"（三条，对应 1.3 的三点工作），展望写"没做什么"（直接抄总体设计 §35 待专项事项：真实设备接入、生产级数据保留、性能压测）。**展望部分诚实列出局限，比吹嘘更有分。**

## 3. 学术语体与示范段落

### 3.1 口语 → 论文表达对照

这是本科生最常扣分的地方。同一件事，两种写法：

| ✗ 口语/工程文档腔 | ✓ 论文语体 |
| :-- | :-- |
| 做了个登录功能，密码加密存 | 系统采用手机号加密码的身份认证方式，密码经安全哈希后存储 |
| 老人点错了会误报 SOS | 针对老年用户误触率较高的特征，紧急求助采用长按 2 秒触发机制以降低误报 |
| 工单状态不能乱改 | 工单状态迁移受状态机约束，非法迁移请求返回 409 冲突 |
| 数据库有一张体征表 | 体征数据以独立实体存储，与告警、工单形成一对多关联 |
| 我们用 Spring Boot 写的 | 后端基于 Spring Boot 构建单体分层架构 |
| 页面字很大 | 界面字号按适老化规范放大至基准字号的 1.4 倍，点击热区不小于 44×44 px |
| 测试了一下没问题 | 依据 GB/T 25000.51—2016 对功能性指标进行验证，用例通过率为 xx% |

**另外 6 条硬规则**：

1. 不用"我""我们"，用"本文""本系统"。
2. 不写"大概""可能""应该"（除非是展望里的推测）。
3. 术语全文统一：老人 / 老年人 二选一；工单 / 任务 二选一；网格员 / 护工 二选一（建议列一张术语表放在附录或第 1 章末尾）。
4. 图表正文必须"如图 4-3 所示"，不能只有图没有引用。
5. 时态：已完成的功能用"实现了"，设计中的方案用"拟采用"。
6. 数字与单位：中文正文用阿拉伯数字，单位与数字间不加空格（44px 写成 44 px 或 44px，全文统一）。

### 3.2 四个示范段落

下面四段是**按你的系统写的**，不是抄的别人的，所以不会造成查重问题。用途是让你看到"成品长什么样"——**请对照改写，直接复制会与你系统的实际细节不符**。

---

**示范一：1.1 研究背景（约 200 字，注意三段递进）**

> 　　我国人口老龄化程度持续加深，居家养老始终是绝大多数老年人的现实选择。据国家卫生健康委员会 2021 年新闻发布会介绍，我国养老呈"9073"格局，即约 90% 的老年人居家养老、7% 依托社区支持养老、3% 入住专业机构。这一格局意味着，社区的支撑能力直接决定了绝大多数老年人晚年生活的质量。然而在社区居家场景中，照护链条存在明显断层：独居与空巢老人缺乏日常健康监测手段，异地子女难以掌握父母的真实身体状况，社区工作人员则因缺乏有效的信息化工具，往往只能在突发事件发生之后被动介入。现有的健康类应用多以数据采集与展示为核心，对"发现问题之后由谁处理、如何处理、如何留痕"缺乏完整支撑；其适老化设计也往往停留在放大字号的层面，缺少可量化的设计依据与验收口径。

*可学的地方*：先给权威数据 → 再指出断层（三个角色各一句）→ 最后点出现有系统的两个不足。**这两个不足正好是你 1.2.3 要展开的缺口**。

---

**示范二：3.3.5 功能需求（约 180 字，注意"场景 → 功能 → 规则"结构）**

> 　　紧急求助功能面向独居老人在突发不适时无法及时联系他人的场景。老人通过长按首页底部求助按钮触发求助，服务端在完成账号状态与档案状态校验后，于同一事务内创建健康告警与紧急服务工单，并将待办推送至所属社区工作人员，由网格员接单、上门处置并上传现场照片，经管理员审核后结案。考虑到老年用户手指震颤、误触率较高的特点，该功能采用长按计时配合环形进度提示的交互方式，松手即取消，以降低误报概率；同时要求告警与工单必须同时创建，任一写入失败则整体回滚，不允许出现仅有告警而无工单的情形。

*可学的地方*：一句话讲场景，中间讲流程，最后两条讲"为什么这么设计"。**"考虑到……因此……"是论文里最值钱的句式**，它把设计决策和依据绑在一起。

---

**示范三：4.5.1 流程设计（约 190 字，注意状态与异常分支）**

> 　　紧急求助流程涉及健康告警与服务工单两类业务对象，二者的一致性由事务边界保证。老人发起求助后，服务端首先校验账号是否有效、老人档案是否处于可用状态；对于档案已停用但账号仍有效的老人，系统按窄范围例外规则仍予受理，并在工单中标记档案状态供管理员核查。校验通过后，服务端在同一事务内写入告警记录与初始紧急工单，随后由异步任务完成站内通知的下发；通知失败不回滚已创建的业务对象，而是记录失败结果并进入可重试状态。工单创建后处于"待派单"状态，经管理员派单、网格员接单后迁移为"处理中"，提交处理结果与现场照片后进入"待审核"，管理员审核通过方转为"已结案"。已结案的工单不可直接编辑重开，如需追加处理须新建关联工单。

*可学的地方*：把"正常路径"和"异常路径"交织着写，而不是只写顺利的那条。**异常分支才是评阅老师判断你是否真做过系统的依据**。

---

**示范四：6.2 测试结果（约 160 字，注意"用例 + 数据 + 结论"）**

> 　　针对紧急求助链路设计用例 TC-05 至 TC-09，分别覆盖正常求助、档案停用状态下的求助、重复提交与网络重试四类情形。测试结果显示，正常求助场景下告警与工单均被正确创建，平均响应时间 320 ms；档案停用场景下系统按例外规则受理并正确标记档案状态；重复提交场景中，携带相同幂等标识的请求返回首次创建的原工单，未产生重复记录；携带不同请求内容的同标识请求返回 409 状态冲突，并写入最小必要审计信息，与 BR-07 的设计预期一致。

*可学的地方*：**每句都有具体对象和具体结果**，没有一句"测试通过，功能正常"。数字哪怕只有一个响应时间，也证明你跑过。

## 5. 去哪找真范文（这一步你自己做，30 分钟）

我拿不到，但你能拿到。按性价比排序：

1. **学长的往届论文（最有用）**
   同校同专业的往届毕设，体例和学校格式要求完全一致，比任何公开范文都准。问导师或辅导员要 1–2 份。

2. **知网学位论文库**
   检索式：`智慧养老 + 系统`，来源类别选"硕士学位论文"，时间 2021—2026，取 2–3 篇。
   看什么：**目录结构、章节字数分配、图表密度、测试章节的表格形式**。不要看内容，看骨架。

3. **学校图书馆的本科优秀毕业论文库**
   多数学校内部有，问图书馆参考咨询部。

4. **万方学位论文库**
   知网找不到时的补充。

**看范文的正确方法**：只看三样东西——目录、图表清单、第 6 章测试表格。内容是别人的，结构是通用的。

**不要做的事**：淘宝买论文包、用 AI 生成整篇、把范文改几个字交上去。查重系统对语义改写也有识别，而且答辩时讲不出细节，比查重不过更致命。

## 7. 最后一句

本科论文的评阅逻辑不是"你做了多难的东西"，而是**"你做的东西和你写的东西是否一致、是否说得清"**。

你现在的文档体系已经比 90% 的本科毕设严谨了。真正要小心的是：论文里写的每一条，代码里都得有；代码里有的，论文里最好也提到。**不一致才是最大的扣分项**，比技术简单严重得多。
