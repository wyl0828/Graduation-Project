## 逐章撰写指引与技术素材

### 摘要 / Abstract

- **撰写要点**：简述人口老龄化背景下社区居家养老面临的“老人操作门槛高、子女无法实时感知、网格员巡访效率低、护工履约缺乏留痕”等痛点；介绍本系统的技术架构（Spring Boot 3 + Vue 3 + Uni-app + MySQL 8）；概括核心功能（长辈适老化关怀、子女亲情共管、一键 SOS、网格员调度、护工工单履约、社区数据看板）；强调权限隔离机制与 176 项自动化测试验证的高可靠性。
- **英文 Abstract 核心词**：Community Home-based Elderly Care, Spring Boot, Vue 3, Multi-role Authorization, Concurrency Control, Age-friendly Design.

### 第 1 章 绪论

#### 1.1 研究背景
- **核心要点**：我国“9073”养老格局（90% 居家、7% 依托社区、3% 机构养老），银发经济与智慧养老政策驱动；传统人工台账与电话巡访模式存在响应慢、易疏漏等不足；数字鸿沟问题突出，传统移动端 UI 缺乏适老化考虑。

#### 1.2 研究意义
- **1.2.1 实践意义**：
  - 降低老年群体数字化使用门槛（大字体、高对比度、大热区、语音辅助）；
  - 实现老人、子女、网格员、护工、社区管理五方协同闭环；
  - 提供数字化履约凭证（拍照存证、服务前后状态校验），提升社区服务规范度。
- **1.2.2 理论意义**：
  - 探索多角色与强社区多租户隔离在 Spring Boot 与 MyBatis 环境下的统一设计范式；
  - 验证基于状态机与乐观锁（`row_version`）保障线下履约一致性的软件工程实践。

#### 1.3 研究现状
- **1.3.1 国外研究现状**：欧美及日本养老信息化起步早，侧重于物联网传感器集成与商业化养老保险联动（如日本 Care Management 体系）；但由于社会结构差异，无法完全照搬至我国以街道社区为核心的网格化管理模式。
- **1.3.2 国内研究现状**：国内主流平台多数偏向机构养老（ERP 模式）或纯商城类家政服务，缺乏深入街道社区、兼顾亲情绑定与适老化大字版的全流程开源闭环方案。

#### 1.4 研究内容与方法
- **1.4.1 研究内容**：
  1. 社区居家养老业务全流程需求分析与适老化交互模型；
  2. 基于 Spring Boot 的后端 RESTful API 与多租户权限引擎；
  3. 基于 Uni-app 的移动端（小程序/H5）与基于 Vue 3 + Element Plus 的 Web 管理端开发；
  4. 数据库安全性设计与高一致性测试验证体系。
- **1.4.2 研究方法**：
  - 文献调研法（检索最新养老服务规范与适老化国标 GB/T 37668-2019）；
  - 敏捷驱动开发（基于 Spec 驱动、小步快跑迭代）；
  - 测试驱动与自动化验证（Maven 全量单测与集成测试、Playwright 浏览器端到端校验）。

### 第 2 章 相关技术与理论基础

#### 2.1 核心技术框架
- **2.1.1 Spring Boot 框架**：采用 Spring Boot 3.x，自动配置、无 XML 配置开箱即用；整合 Spring MVC、Spring Validation、MyBatis-Plus 提供标准企业级后端支撑。
- **2.1.2 Vue 3 框架与 Uni-app 跨端方案**：
  - 管理端：Vue 3 组合式 API（Composition API）、TypeScript、Vite 构建工具、Element Plus UI 库、Pinia 状态管理；
  - 移动端：Uni-app 框架，一次编写即可适配微信小程序与移动 Web H5。
- **2.1.3 前后端分离架构**：前后端通过 RESTful JSON 协议交互，解耦界面渲染与服务端逻辑；利用 CORS 与反向代理统一网关出口。

#### 2.2 关键技术
- **2.2.1 JWT 鉴权与服务端会话撤销**：
  - Token 采用 SHA-256 签名，Payload 携带用户 ID、手机号、社区 ID 与角色列表；
  - 创新结合服务端 `auth_session` 表与黑名单机制：在角色变更或管理员主动停用账号时，触发即时会话撤销，解决纯无状态 JWT 无法主动失效的痛点。
- **2.2.2 WebSocket 实时预警推送技术**：
  - 用于紧急 SOS 求助与体征突发异常告警；建立全双工持久连接，管理端与网格员工作台毫秒级告警弹窗与声光提示。
- **2.2.3 PBKDF2 密码散列与敏感数据脱敏技术**：
  - 密码存储采用带盐 PBKDF2-HMAC-SHA-256 算法，迭代次数达标；
  - 激活码使用 6 位数字 HMAC-SHA256 摘要存库，单次消费作废；
  - 身份证号码与敏感体征在接口返回时自动掩码脱敏。
- **2.2.4 适老化交互设计准则**：
  - 老人端遵循 WCAG 2.1 AA 级标准；最小字号 ≥ 18px，核心操作按钮高度 ≥ 48px，采用清晰色块与图标结合，杜绝深层嵌套菜单与滑块验证码等高门槛交互。

#### 2.3 数据库技术
- **2.3.1 MySQL 关系型数据库与 InnoDB 引擎**：
  - 采用 MySQL 8.0，统一字符集 `utf8mb4`、排序规则 `utf8mb4_0900_ai_ci`；
  - 行级锁保证高并发操作互斥，事务隔离级别为可重复读（RR）。
- **2.3.2 Flyway 数据库版本化迁移技术**：
  - 数据库 DDL 与基础数据采用 Flyway 进行版本化演进（`V1` 初始化基座、`V2` 身份与档案、`V3` 核心业务、`V3.1` 登录防刷、`V3.2` 预约时段去重、`V3.3` 工单照片凭证留痕），保证多环境部署的一致性与可回溯性。

### 第 3 章 系统需求分析

#### 3.1 业务流程分析
论文应包含 3 大核心业务流程图（可直接引用 Mermaid 图绘制在论文中）：
1. **老人激活与亲情绑定业务流**：管理员线下采集建档并签发 6 位数字激活码 -> 老人小程序输入手机号与激活码首次认证绑定 -> 子女注册账号并提交亲情关系申请 -> 管理员审核或老人确认 -> 关系确立并授予健康查看权。
2. **居家上门服务预约与履约闭环流程**：子女/老人提交预约需求 -> 社区管理员审核派单至护工 -> 护工手机端接单 -> 上门开始服务 -> 拍照上传服务凭证并提交结案 -> 管理员审核通过并归档。
3. **体征监测与一键 SOS 应急闭环流程**：老人录入体征（或设备仿真）/ 触发 SOS -> 服务端阈值评估 -> 触发告警记录并同步生成初始工单 -> WebSocket 推送网格员与管理端大屏 -> 现场核实与结果结案。

#### 3.2 角色划分
系统细分 5 类角色，各自职责与边界如下：
1. **老人（`ELDER`）**：大字版交互、查看用药提醒并打卡、查看预约服务、一键触发 SOS 求助。
2. **子女（`FAMILY_MEMBER`）**：远程查看父母体征与用药合规率、代长辈预约养老服务、申请绑定与档案更正。
3. **网格员（`GRID_MEMBER`）**：负责本辖区网格老人的日常上门关怀、走访核实、处理健康预警流。
4. **护工（`CARE_WORKER`）**：专属工单工作台，仅查看和执行本人分配的工单，现场打卡与拍照上传凭证。
5. **社区管理员（`COMMUNITY_ADMIN`）**：本社区员工账号与角色分配、长辈档案管理、亲情审批、预约审核调度、全屏数据看板查看。

#### 3.3 系统用例分析
绘制用例图（Use Case Diagram）并逐节说明：
- **3.3.1 普通用户用例**：UC01 账号注册与登录、UC02 激活码绑定、UC03 亲情申请与解除、UC04 今日服药打卡、UC05 体征数据填报、UC06 服务预约申请、UC07 一键 SOS。
- **3.3.2 客服与履约人员用例**：UC08 实时告警查看、UC09 预警核查处理、UC10 待办工单查看、UC11 工单接单响应、UC12 服务开始确认、UC13 上传服务图片凭证与提交审核。
- **3.3.3 管理员用例**：UC14 社区员工账号维护、UC15 角色分配与撤销、UC16 档案新增与状态维护、UC17 亲情关系审批与争议冻结、UC18 预约工单派单与改派、UC19 工单结案终审、UC20 社区看板与统计分析。

#### 3.4 非功能需求分析
- **安全性**：全链路参数校验、SQL 注入拦截、XSS 防御、CSRF 保护、明文密码禁存。
- **数据一致性**：多方写入采用乐观锁版本控制（`row_version`），并发冲突返回 409。
- **性能与响应时间**：常规查询接口平均响应时间 < 200ms，P95 < 500ms；WebSocket 预警下发延迟 < 1 秒。
- **可用性与适老化**：老人端页面遵循高对比度色彩（对比度 ≥ 4.5:1）、防误触按钮间距、大字排版。

#### 3.5 可行性分析
- **3.5.1 技术可行性**：Spring Boot 3 + Vue 3 技术成熟，生态完备，开源组件丰富。
- **3.5.2 经济可行性**：系统全部基于开源框架构建，零授权费用；服务端单体架构硬件成本低。
- **3.5.3 操作可行性**：管理端后台界面贴近社区工作人员操作习惯；移动端高度适老化，老人与子女易学易用。
- **3.5.4 法律可行性**：严格遵守《个人信息保护法》，敏感健康数据最小化采集，敏感信息加密脱敏。

#### 4.3 普通用户模块设计
- 老人与子女端界面导航设计；

- 护工本人工单状态流转设计（`DISPATCHED` -> `ACCEPTED` -> `IN_SERVICE` -> `PENDING_REVIEW` -> `COMPLETED`）；

#### 4.5 管理员模块设计
- 辖区员工账号生命周期管理；
- 角色动态分配与会话强踢机制设计。

#### 4.6 数据库设计
- **4.6.1 数据库设计思路**：统一以主键自增 `BIGINT` 标识记录，业务 UUID 对外暴露，状态变更追加审计领域事件历史。
- **4.6.2 概念模型设计**：绘制核心 E-R 图（包含社区、用户、角色、长辈档案、亲情绑定、用药计划、预约记录、工单、告警等实体及其关系）。
- **4.6.3 逻辑模型设计（物理表结构）**：列出核心数据表的字段、类型、主外键及约束：
  1. `sys_user`（系统账号表）
  2. `sys_user_role`（用户角色分配表）
  3. `auth_session`（用户活跃会话表）
  4. `elder_profile`（长辈档案表，含 `row_version`）
  5. `elder_family_link`（亲情绑定关系表）
  6. `medication_plan` 与 `medication_task`（用药计划与每日任务表）
  7. `health_record` 与 `emergency_alert`（体征记录与告警表）
  8. `service_reservation` 与 `work_order`（预约申请与工单履约表）

#### 4.7 核心功能模块详细设计
